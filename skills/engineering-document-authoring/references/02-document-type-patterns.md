# Document Type Patterns

## Project overview

Why the project exists, who it serves, what it is, current boundary, major value, non-goals and reading path.

## Product / PRD

User/problem, desired outcome, scenarios, scope, capability, acceptance, risks, non-goals and evidence. Do not turn a PRD into an architecture implementation guide.

## Architecture

Drivers, system boundary, components/contexts, relations and flows, trust/state ownership, current implementation versus target, decisions, risks and evidence. Complex relationships require a formal visual block.

## ADR

Context, decision, alternatives, consequences, status, evidence and supersession. ADR explains why; it does not duplicate the full technical design.

## Technical design

Problem, constraints, proposed design, contracts/data, failure/security, rollout/migration, validation and open risks.

## Runbook

Preconditions, safe commands, expected output, failure classification, stop/recovery, rollback and evidence. Keep tool-specific operating detail outside general Skills.

## Experiment / incident

Question, setup, controls, procedure, evidence, result, limitations, conclusion and next decision. Separate observation from causal inference.

## README / navigation

Purpose, contents, boundary, usage and related sources. A README is an index or local entry, not a second full article.

## Portfolio

Problem, contribution, difficult decisions, architecture, verifiable results, evidence, limitations and interview narrative. Never overstate unimplemented capability.
