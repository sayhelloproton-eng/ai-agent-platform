# engineering-insight-distillation v0.1.1 — 第一轮真实 Pilot Eval

    ## 1. 结论

    本轮使用 7 个来自真实 MVP 过程的问题案例执行同题对照：

    - 无 Skill 基线：只要求“提炼可复用工程经验”；
    - Skill 版本：应用 v0.1.1 的七个 Checkpoint、Schema、质量门和治理约束；
    - 使用同一固定 Rubric 评分；
    - Skill 输出全部通过自身 `distillation-result` JSON Schema 校验。

    平均得分：

    - 基线：**5.7/16**
    - 使用 Skill：**14.7/16**
    - 平均提升：**9.0 分**
    - Skill 输出平均长度约为基线的 **52.1 倍**

    判断：**Skill 的目标可行，第一轮已证明其主要价值不是“想出一句更聪明的经验”，而是稳定补齐证据纪律、适用边界、成熟度、生命周期、查重状态和治理动作。**

    ## 2. 方法

    本轮遵循官方 Skill Creator 的核心循环：

    1. 使用已经存在的 Skill 草案；
    2. 选择真实任务案例；
    3. 对同一案例生成无 Skill 和有 Skill 两组结果；
    4. 使用固定 Rubric 做定性与定量比较；
    5. 将真实失败类型加入负例与证据不足例；
    6. 根据结果识别下一版改进项。

    这是一轮受控人工 Pilot，不是独立模型盲测：

    - 当前环境没有调用外部模型 API，也没有消耗用户本地 Codex Token；
    - 两组输出由同一个模型在不同约束下构造；
    - 没有独立 comparator 子 Agent；
    - 因此分数用于发现结构性差异，不应解释为统计显著的模型性能结论。

    ## 3. 案例与结果

    | Case | 主题 | 基线 | Skill | Skill 处置 | 长度比 |
    |---|---|---:|---:|---|---:|
    | EVAL-01 | 外部智能调用者生成内部控制字段 | 8/16 | 15/16 | insight_proposed | 46.0× |
| EVAL-02 | 自动验证覆盖了相似内部接口而非真实用户入口 | 8/16 | 15/16 | insight_proposed | 52.4× |
| EVAL-03 | 探索性公网方案持续追加补丁但偏离 MVP 目标 | 6/16 | 15/16 | insight_proposed | 52.3× |
| EVAL-04 | 把公网访问、API 认证和用户审批当成同一种权限 | 8/16 | 15/16 | insight_proposed | 66.6× |
| EVAL-05 | 窄修复后仍重复要求全量审计 | 6/16 | 15/16 | insight_proposed | 64.7× |
| EVAL-06 | 一次无法复现的偶发超时 | 2/16 | 14/16 | needs_evidence | 42.0× |
| EVAL-07 | 一次性文件名拼写错误 | 2/16 | 14/16 | rejected | 35.3× |

    ## 4. 主要发现

    ### 4.1 Skill 明显提升的部分

    1. **证据纪律**
       对无法复现的偶发超时，基线直接建议日志、重试和缓存监控；Skill 正确返回 `needs_evidence`，拒绝把恢复相关性伪装成根因。

    2. **价值筛选**
       对一次性文件名拼写，基线制造了“命名规范和自动检查”经验；Skill 正确 `rejected`，避免经验库膨胀。

    3. **抽象边界**
       对公网路线切换，基线容易落入“不要用复杂边缘方案、改用 Tunnel”；Skill 提炼为“阶段目标匹配 + 退出条件”，并明确长期生产场景可能有不同结论。

    4. **治理和成熟度**
       所有单一事件洞见均保持 `candidate` 或 `provisional`，未因真实修复成功就自动升级为跨场景正式规范。

    5. **可执行化**
       Skill 输出设计动作、测试规则、审计问题和停止条件，而非只有一句原则。

    6. **真实失败处置**
       Skill 能分别输出 `insight_proposed`、`needs_evidence` 和 `rejected`，这比“所有案例都强行总结一条经验”可靠。

    ### 4.2 基线仍然做得不错的部分

    基线在高证据、机制明显的案例中也能提炼出较好的核心原则，例如：

    - 外部调用者不应构造内部控制字段；
    - 自动验收应覆盖真实入口；
    - 权限应分层。

    所以 Skill 的价值不是替代模型的一般推理能力，而是提供**稳定且可治理的输出纪律**。

    ### 4.3 Skill 的成本

    Skill 输出平均长度约为基线的 52.1 倍。

    因此它不应在每个小问题后自动运行。适合触发于：

    - 重大问题已解决；
    - 技术路线切换；
    - 里程碑复盘；
    - 重复返工；
    - 假设被证据推翻；
    - 需要形成正式工程规则前。

    ## 5. 当前通过项

    - 7/7 Skill 输出通过实际 v0.1.1 Result Schema；
    - 5 个高价值事件形成受治理洞见建议；
    - 1 个证据不足事件被正确阻断；
    - 1 个低价值事件被正确拒绝；
    - 所有正例均保留适用条件与排除条件；
    - 无正例被自动标记为 `repeated` 或 `established`；
    - 无索引条件下全部诚实标记 deduplication `unverified`。

    ## 6. 暂未验证

    1. **自动触发准确率**
       已准备 20 条 should-trigger / should-not-trigger 查询，但没有安装到真实 Skill 客户端执行自动选择。

    2. **独立盲评**
       没有第二个独立 Agent 隐藏 A/B 标签进行比较。

    3. **多次采样稳定性**
       未对同一案例进行 3–5 次重复运行和方差分析。

    4. **真实查重能力**
       本轮没有连接受治理的 engineering insight index，因此只能验证“无索引时不声称唯一”。

    5. **跨领域迁移**
       本轮来源都来自同一 MVP，尚未使用性能、数据、产品或运维类事件验证。

    ## 7. v0.1.2 建议

    第一轮不需要推翻 Skill，建议下一版只补四项：

    1. 增加 `screening` 与 `full` 两种运行模式，降低小规模筛选的 Token 成本；
    2. 增加正式 `insight index` 查询接口契约，才能真实验证查重与 occurrence 合并；
    3. 增加可执行 Eval Harness，对 Schema、结果状态、绝对化措辞和成熟度进行确定性评分；
    4. 在真实 Agent Skills 客户端运行 20 条触发查询，并基于误触发/漏触发优化 description。

    ## 8. 是否进入正式经验资产阶段

    可以进入，但应保持以下边界：

    - 当前五条正例只是**洞见提案**；
    - 不直接升级为 established；
    - 先人工审阅标题、抽象、边界和落位；
    - 经确认后再写入 Git 正式知识资产；
    - 后续不同项目再次出现时，更新 occurrence 和成熟度，而不是创建近义重复条目。
