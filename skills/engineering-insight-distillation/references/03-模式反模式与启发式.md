# 模式、反模式与启发式

## 1. 目的

洞见类型用于选择最合适的表达形式，不是文档目录，也不是为了增加标签数量。每条洞见必须选择一个 `primary_type`，可选少量 `secondary_types`。

## 2. Judgment

工程判断回答：

> 在信息不完整或目标冲突时，应优先判断和保护什么？

适合：

- 技术选型；
- 风险权衡；
- 验证顺序；
- 范围收缩；
- 是否继续投入或退出。

好的 Judgment 应包含触发条件和判断依据，不能只是价值观。

## 3. Pattern

Pattern 是在明确上下文和作用力下可重复采用的问题解决结构，建议包含：

- Context；
- Problem；
- Forces / Constraints；
- Solution Structure；
- Consequences；
- Applicability；
- Verification。

模式不是固定代码模板。它描述稳定关系和职责结构，允许不同实现。

## 4. Anti-pattern

Anti-pattern 描述一种看似合理、短期可能有效，但容易造成系统性风险、重复返工或事实失真的做法。

必须同时说明：

- 为什么它有吸引力；
- 在什么条件下产生问题；
- 典型症状；
- 更可靠的替代做法。

只写“不要做 X”不构成完整反模式。

## 5. Heuristic

Heuristic 是没有唯一答案时使用的经验性判断规则。

它必须：

- 明确适用条件；
- 承认例外；
- 给出观察信号；
- 允许后续证据修正；
- 不伪装成安全底线或数学定律。

## 6. Checklist

Checklist 是在任务开始、执行、复审或验收时可以直接检查的动作列表。

高质量检查项应：

- 可回答是/否或提供证据；
- 指向明确责任人或阶段；
- 能阻止具体失败；
- 避免“注意”“确保质量”等不可验证措辞；
- 数量受控，优先高风险项。

## 7. 类型选择

优先使用：

- 需要决定优先级或是否继续：`judgment`；
- 形成可复用结构：`pattern`；
- 识别高风险错误做法：`anti_pattern`；
- 信息不完整下的经验判断：`heuristic`；
- 需要直接执行和验收：`checklist`。

同一洞见可以从 Pattern 派生 Checklist，但主类型仍应反映其核心价值。

## 8. 组合方式

常见组合：

- `judgment` → 决定何时采用某个 `pattern`；
- `anti_pattern` → 解释错误路径和替代 `pattern`；
- `heuristic` → 在证据不足时选择最小行动；
- `pattern` → 派生 `checklist` 和 acceptance gate。

禁止为了“完整”让每条洞见同时拥有所有类型。

## 9. 从洞见到可执行资产

每条洞见至少派生一种：

- 设计检查；
- 测试规则；
- 验收门；
- 评审规则；
- 退出条件；
- Prompt 约束；
- 架构模式；
- 反模式警告；
- 运维检查单。

如果无法转化为任何动作，洞见很可能仍过于抽象或缺少机制。
