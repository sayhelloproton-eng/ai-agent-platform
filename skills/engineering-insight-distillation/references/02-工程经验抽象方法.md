# 工程经验抽象方法

## 1. 抽象目标

工程经验的价值不在于删除细节，而在于保留**决定结果的机制**，去掉只属于单次事件的偶然实现。正确抽象应同时满足：

- 能迁移到相似场景；
- 能解释为什么有效或失败；
- 能指导下一次行动；
- 有明确适用边界；
- 可以被证据反驳或修订。

## 2. 六层抽象链

### Layer 1：事件

记录具体目标、现象、影响和修复。此层允许项目、产品和接口细节。

### Layer 2：机制

识别真正影响结果的结构，例如：

- 信任边界；
- 控制流或信息流；
- 身份、权限和审批层；
- 状态所有权；
- 依赖不确定性；
- 可观察性；
- 可逆性；
- 决策顺序；
- 角色职责；
- 故障恢复；
- 验证路径。

### Layer 3：上下文与作用力

说明该机制为何在当前条件下重要：

- 生命周期阶段；
- 风险和后果；
- 调用方可信程度；
- 外部依赖可控程度；
- 变更成本；
- 时间约束；
- 数据敏感度；
- 失败是否可恢复。

### Layer 4：原则

将机制表达为一个能够指导判断的陈述。原则应回答“以后面对同类条件时，优先保护什么或先判断什么”。

### Layer 5：动作

把原则转化成设计检查、验证顺序、退出条件、评审规则或操作清单。

### Layer 6：验证

定义如何判断该经验被正确应用，以及什么证据会要求修订它。

## 3. 抽象提问法

对具体事件依次提问：

1. 如果移除产品名和接口名，问题仍然是什么？
2. 哪个角色拥有不该拥有的控制权，或缺少必要控制权？
3. 哪个状态、权限、决策或证据没有明确所有者？
4. 失败发生在输入、转换、执行、验证还是治理环节？
5. 哪个假设最先被事实推翻？
6. 修复改变的是表象，还是底层机制？
7. 哪些条件变化后，当前结论会失效？
8. 下一次最早可以在哪个检查点阻止同类问题？
9. 该结论能否转化为一个可观察的验收规则？

## 4. 抽象质量测试

### Transfer Test

把洞见放到另一个技术栈或项目中，仍能解释和指导相似问题。

### Mechanism Test

洞见说明了为什么，而不是只说某个实现好或坏。

### Actionability Test

团队能够据此执行一个动作或做出一个决策。

### Boundary Test

至少能说出一个不适用场景或反条件。

### Counterexample Test

能够描述什么新证据会要求缩小、修订或废弃该洞见。

### Compression Test

删除偶然细节后没有删除关键机制；增加通用词汇后没有变成空话。

## 5. 正向表述优先

反模式可以描述风险，但最终输出应尽量给出正确做法。例如：

- 只有“不要让外部调用者控制内部字段”仍不够；
- 应补充“外部只表达必要意图，受信任边界负责映射、补全和校验”。

## 6. 控制抽象层级

### 抽象不足

表现：结论仍依赖某个供应商、接口路径或一次错误码。

修正：找到决定结果的信任、状态、顺序、验证或依赖机制。

### 抽象过度

表现：结论变成“做好测试”“保持简单”“注意安全”。

修正：补充触发条件、具体动作、证据和失败门槛。

### 错误绝对化

表现：从一个事件推出“永远”“所有场景”“唯一正确”。

修正：明确适用阶段、前置条件、排除条件和证据强度。

## 7. 多洞见拆分

一次事件可能暴露多个独立机制。只有在以下条件同时满足时拆分：

- 每条洞见有不同的 generalized problem；
- 每条洞见有独立可执行动作；
- 合并会导致适用边界混乱；
- 各自能够单独查重和演进。

不要为增加数量把同一机制拆成近义条目。

## 8. 经验不是事实替代品

抽象后的洞见必须保留 `source_references`。正式洞见不能替代原始事件、测试或决策记录；它只说明如何从这些证据中获得可复用判断。
