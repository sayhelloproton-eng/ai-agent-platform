# 运行模式与成本控制

## 1. 目的

完整工程洞见包含证据、机制、边界、成熟度、生命周期、Occurrence、查重和治理信息，成本明显高于普通总结。

因此本 Skill 分为：

- `screening`：快速判断是否值得进入长期经验体系；
- `full`：对通过筛选的事件执行完整提炼；
- `auto`：根据请求和输入完整度选择前两种模式。

## 2. Screening Mode

### 适用情况

- 用户只问“是否值得沉淀”；
- 一次输入包含多条事件，需要先筛选；
- 证据明显不完整；
- 事件可能只是一次性操作错误；
- 尚不需要正式洞见、成熟度和下游落位。

### 读取范围

Screening 优先只读取：

- `SKILL.md`；
- `references/01-输入资格与证据规则.md`；
- 本文件；
- `screening-result` Schema。

不执行完整模式分类、查重或成熟度治理。

### 输出

使用 `assets/schemas/screening-result.schema.json`：

- `proceed_full`：具有中高长期价值、可迁移机制和至少部分可用证据；
- `needs_evidence`：可能值得沉淀，但无法可靠识别机制或验证结果；
- `reject`：低影响、一次性、无可迁移机制或会造成经验库膨胀。

Screening 不得：

- 创建正式 `insight_id`；
- 声称已经完成查重；
- 推荐 `validated` 以上成熟度；
- 生成完整工程规范；
- 用冗长正文代替筛选决定。

## 3. Full Mode

### 适用情况

- Screening 返回 `proceed_full`；
- 用户明确要求形成受治理工程洞见；
- 输入已经包含事件、证据、原因分析、修复和验证；
- 需要确定适用边界、成熟度、Occurrence 或下游落位。

### 执行范围

Full 执行七个 Checkpoint，按需读取全部 References，并输出 `distillation-result`。

如果用户明确要求 Full，但证据不足，仍应返回：

```text
result_status: needs_evidence
```

不得为了满足 Full 请求制造完整洞见。

## 4. Auto Mode

默认规则：

1. 明确要求“筛选、判断是否值得沉淀、批量过滤”时使用 Screening；
2. 明确要求“正式提炼、形成洞见、更新已有经验”，且输入完整时使用 Full；
3. 请求模糊、输入批量或证据不充分时先 Screening；
4. 当前会话已经完成 Screening 且结果为 `proceed_full` 时，可以继续 Full；
5. 单纯排错、实现、翻译、项目总结和状态查询不触发本 Skill。

## 5. 成本约束

- Screening 只回答筛选所需字段，避免提前生成完整模式和检查清单；
- Full 只对 `proceed_full` 的事件运行；
- 批量输入先逐条 Screening，再由用户或上游流程确认 Full 范围；
- 共享证据应使用引用，不在每条洞见中复制全部原始材料；
- 同一机制优先更新 Occurrence，不创建近义全文；
- 下游资产只给出落位建议，不在本 Skill 内重复生成完整正式文档。

## 6. 触发边界

应触发：

- 已解决问题的经验提炼；
- 被证据推翻的重要假设；
- 技术路线切换后的工程判断；
- 重复返工或流程缺陷；
- 现有洞见的新证据、反例或冲突；
- 里程碑后筛选值得长期保留的经验。

不应触发：

- 当前状态查询；
- 尚未排查的普通错误诊断；
- 代码实现本身；
- 翻译、摘要或润色；
- 一次性拼写修正；
- 完整项目时间线综合；
- 外部知识发布。

## 7. 模式升级规则

Screening → Full 需要满足：

- retention value 至少为 `medium`；
- transferability 至少为 `medium`；
- evidence readiness 至少为 `partial`；
- 不存在必须先解决的来源授权问题；
- 用户或治理流程接受继续投入完整提炼成本。

`needs_evidence` 不自动升级。补充证据后必须重新 Screening 或明确执行 Full。
