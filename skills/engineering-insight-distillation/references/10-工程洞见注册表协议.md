# 工程洞见注册表协议

## 1. 目的

Skill 保存提炼方法，注册表保存通过治理的工程洞见主记录。二者必须分离：

```text
已解决工程事件
    ↓ screening / full
Engineering Insight Proposal
    ↓ review / deduplication / approval
Engineering Insight Registry
    ↓ retrieve / apply / add occurrence / revise
后续任务、测试、规范与工作流
```

## 2. Canonical Registry

推荐 Git 主归属：

```text
docs/technical/元数据/engineering-insights/
```

注册表不属于 Feishu Knowledge Projection。面向人类的知识页面可以引用或派生检查项，但不得成为成熟度和生命周期的第二真源。

## 3. 必要文件

- `registry.json`：洞见索引和检索摘要；
- `governance.json`：审批、委托、晋级和覆盖规则；
- `relationships.json`：跨洞见关系；
- `insights/<insight-id>.json`：洞见主记录；
- `README.md`：职责、更新流程和边界。

## 4. 写入模式

新候选进入前必须：

1. 运行 Screening；
2. 通过 Full 模式形成受治理提案；
3. 查询当前 Registry；
4. 判断 new / occurrence / evidence / refine / contradiction；
5. 更新现有记录或创建新记录；
6. 同步 Registry 和 Relationships；
7. 执行 Registry 验证；
8. 保存 Revision History。

默认优先更新已有洞见的 Occurrence 和边界，避免标题不同但机制相同的重复条目。

## 5. 任务前应用

在新任务开始前，可按以下字段检索：

- category；
- primary_type；
- contexts；
- underlying_mechanism；
- recommended_actions；
- prevention_checks；
- related_insights。

只加载与当前目标、阶段和风险直接相关的少量洞见，转换为：

- Preflight Checklist；
- Decision Gate；
- Test Requirement；
- Stop / Exit Condition；
- Review Constraint。

## 6. 成熟度与生命周期

- 新建条目默认不高于 `provisional`；
- 新项目再次验证时增加独立 Occurrence；
- `repeated` 需要至少两个独立事件；
- `established` 需要多场景证据和正式批准；
- 反例优先修订边界，不静默覆盖；
- `deprecated` 保留历史和替代关系。

## 7. 审批委托

Project Owner 可以把详细技术复核委托给 Architecture Advisor 或指定 Reviewer。委托必须写入 `governance.json`，记录：

- 委托范围；
- 生效日期；
- 被委托角色；
- 可撤销和覆盖规则；
- 不包含的高风险事项。

被委托人可以批准条目进入注册表，但不能自动批准删除、公开范围变更、密钥与权限变更、历史重写或 `established` 晋级，除非委托明确覆盖。

## 8. 禁止事项

- 不把原始聊天全文放入注册表；
- 不保存 Token、私有 URL、账号或运行缓存；
- 不复制完整项目复盘作为洞见；
- 不把单次成功写成跨项目定律；
- 不为每次事件新建近义条目；
- 不在 Skill 内核中嵌入具体项目经验；
- 不让 Feishu 或其他投影反向覆盖 Registry。
