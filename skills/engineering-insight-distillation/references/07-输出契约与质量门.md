# 输出契约与质量门

## 1. 统一输出包

每次运行必须返回符合 `distillation-result.schema.json` 的结果包。

结果状态只能是：

- `insight_proposed`：关键质量门通过，并包含完整 `engineering insight`；
- `needs_evidence`：证据不足，不生成形式完整但内容虚假的洞见；
- `rejected`：事件无长期价值、来源不合法或请求要求违反治理边界。

结果包必须承载：

1. 输入资格结果；
2. 洞见或空值；
3. 八项质量门；
4. 未解决不确定性；
5. 缺失证据；
6. 下游落位建议；
7. 拒绝原因；
8. 治理摘要。

## 2. Evidence Gate

检查：

- 结论是否有来源支持；
- 事实和推断是否分开；
- 根因是否只是可能解释；
- 修复与验证是否真实发生；
- 来源是否可追溯；
- 是否存在未处理的相反证据。

失败：返回 `needs_evidence` 或更低成熟度，不得补写证据。

## 3. Abstraction Gate

检查：

- 是否仍依赖单个产品、供应商、接口或错误码；
- 是否保留底层机制；
- 是否能够迁移到相似场景；
- 是否退化为空话；
- 是否能解释为什么。

失败：重新抽象；无法修正时不得输出正式洞见。

## 4. Boundary Gate

检查：

- 是否写明 contexts、preconditions 和 exclusions；
- 是否区分生命周期阶段；
- 是否考虑信任、风险、可逆性和可观察性；
- 是否从一次事件使用绝对措辞；
- 是否存在合理反例。

失败：缩小表述或保持较低成熟度。

## 5. Actionability Gate

检查：

- 是否能产生下一次的明确动作；
- prevention checks 是否可验证；
- 是否能定义验收证据或停止点；
- 是否说明由谁或在哪个阶段执行；
- 是否只有观点而没有行为变化。

失败：补充动作和证据要求。

## 6. Deduplication Gate

检查：

- 是否访问相关已有洞见；
- 是否比较 mechanism、principle 和 actions；
- 是否只是同一洞见的新 occurrence；
- 是否建立关系；
- 无既有索引时是否诚实标记 `unverified`。

无索引不必阻止草案，但不得声称唯一或全新。

## 7. Maturity Gate

检查：

- maturity level 是否与证据、occurrence 和人工审批相符；
- lifecycle status 是否与修订历史相符；
- 是否把单一事件误标为 repeated；
- 是否把来源事件验证误当成跨场景验证；
- 是否把 revised / deprecated 错当成成熟度等级。

失败：降低成熟度、修正生命周期或保持审批待定。

## 8. Traceability Gate

检查：

- source references 是否足以回到原始事件；
- occurrence 是否引用真实来源；
- 修订是否引用新证据；
- 关系是否指向稳定 ID；
- 是否包含未经授权的私密材料。

失败：补充来源或停止正式输出。

## 9. Governance Gate

检查：

- 是否试图自动写入正式资产；
- 是否试图自动批准成熟度或生命周期变化；
- 是否修改其他 Skill；
- 是否绕过 Git 或人工审阅；
- 是否把建议伪装成已经采纳的规则。

失败：停止写入，仅输出建议和审批请求。

## 10. 通过标准

只有 Evidence、Abstraction、Boundary、Actionability、Maturity、Traceability 和 Governance 关键门通过，才能使用 `insight_proposed`。

Deduplication 无法验证时可以输出洞见草案，但必须：

- `deduplication.status: unverified`；
- `deduplication.decision: undetermined`；
- 不声称新条目或唯一性；
- 将缺口写入质量门和治理摘要。

## 11. 输出语言

- 明确区分“已验证”“推断”“建议”；
- 避免没有范围的绝对词；
- 使用可执行动词；
- 先说明机制，再说明规则；
- 不夸大一次事件的普遍性；
- 不为了完整性制造不存在的证据。
