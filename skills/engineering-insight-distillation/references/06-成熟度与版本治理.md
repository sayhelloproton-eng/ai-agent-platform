# 成熟度、生命周期与版本治理

## 1. 三个独立维度

- **Evidence strength**：现有证据对当前结论支持有多强；
- **Maturity level**：洞见经过多少验证、重复和治理批准；
- **Lifecycle status**：洞见当前是否处于活跃、修订或废弃状态。

三者不得混用。高证据强度不自动等于高成熟度；`revised` 和 `deprecated` 也不是成熟度高低。

## 2. Maturity Level

### candidate

事件、证据或抽象尚不完整。可以保留来源和待验证问题，不应作为正式行动规则。

### provisional

来源事件已基本确认，抽象机制合理，可在相似场景中谨慎参考。通常是单一事件提炼后的默认上限。

### validated

洞见的机制和建议动作获得直接验证，或在受控应用中证明有效，并完成明确人工审阅。必须记录验证范围。

### repeated

洞见在至少两个相互独立的事件或场景中重复出现。独立性必须由来源和 occurrence 记录支持。

### established

洞见经多场景验证、边界稳定、存在正式治理批准，并已成为稳定工程规则或模式。

推荐迁移：

```text
candidate → provisional → validated → repeated → established
```

禁止：

- 单次事件直接成为 `repeated`；
- 没有验证结果成为 `validated`；
- 没有多场景证据和人工批准成为 `established`；
- 由 Skill 自动完成正式晋级。

## 3. Lifecycle Status

### active

当前表述仍有效，可按其成熟度和治理状态使用。

### revised

新证据要求修改机制、边界、建议或成熟度。必须保留旧版本和修订原因。

### deprecated

环境、技术或证据变化使洞见不再适用。保留历史原因和替代洞见，不作为当前执行依据。

生命周期可以与成熟度组合。例如：

```text
validated + active
repeated + revised
established + deprecated
```

这比把 `revised`、`deprecated` 作为成熟度更准确。

## 4. Occurrence 治理

每个支持洞见的实际事件应记录为 occurrence，至少包含：

- 稳定 occurrence ID；
- 场景摘要；
- 来源引用；
- 是否具有独立证据；
- 可选日期和说明。

同一事件的聊天摘要、执行报告和截图不能被计为多个独立 occurrence。

## 5. 人工审批

以下行为必须人工确认：

- 从 `provisional` 升级到 `validated` 或以上；
- 扩大适用范围；
- 将洞见落入正式工程规范；
- 用新洞见替代旧洞见；
- 标记为 `established` 或 `deprecated`；
- 修改安全、权限或不可逆操作相关规则。

`governance.approval_status` 必须与 `requires_human_approval` 一致：

- 需要审批：`pending | approved | rejected`；
- 不需要审批：`not_required`。

## 6. Revision History

每次重要变化记录：

- 修订号；
- 日期；
- 变更类型；
- 变化摘要；
- 支持来源；
- 审批引用或治理记录。

机制、原则、边界、成熟度、生命周期和建议动作变化必须单独记录。

## 7. Skill 自身版本

Skill 方法版本与具体洞见演进分离：

- Skill 版本记录方法、Schema、质量门和 Fixture 变化；
- 洞见 Revision History 记录某条经验的演进；
- 不因 Skill 升级自动修改已有洞见；
- Schema 变更需要显式迁移说明。

## 8. 从失败反哺 Skill

真实使用暴露错误时，应先新增可复现 Fixture，再修改方法和 Changelog。Skill 不得在一次运行中自行修改自身。
