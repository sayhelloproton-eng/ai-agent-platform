## 2. 用户的长期目标

用户的最终方向不是单纯“在手机上装一个聊天模型”，而是建立一套自己的 AI 内容创作系统。

### 2.1 内容方向

目标聚焦于 AI 影视与内容生产，包括：

- 从小说、文章、剧本或一段对话开始。
- 自动分析故事结构。
- 生成人物设定。
- 拆解场景。
- 生成分镜。
- 生成镜头提示词。
- 生成配音、字幕、素材。
- 进一步生成短视频、广告、直播内容或连续剧式内容。
- 最终形成可批量产出的内容流水线。

### 2.2 核心价值

用户认为真正的价值不只是“生成一个视频”，而是：

- 通过更专业的工作流减少无效工作。
- 减少昂贵模型的无效调用。
- 减少 token 浪费。
- 减少反复试错。
- 提升提示词、镜头、人物、场景的一致性。
- 将昂贵云端视频模型留到最后的高价值生成环节。
- 让低成本本地模型承担前处理、结构化、检查与编排。

### 2.3 长期平台愿景

平台未来应具备：

- 业务与模型解耦。
- 业务与设备解耦。
- 所有能力通过 API 暴露。
- 每个模型、设备、云服务都只是可替换实现。
- 工作流编排独立存在。
- 今天可用手机本地模型，明天可换 Mac、本地工作站或云端模型，而不推倒重来。
- 架构上倾向 DDD、适配器模式、能力接口与任务契约。

## 3. iPhone 作为本地 AI 设备

### 3.1 用户对手机的定位

用户希望：

- 手机本身就是算力。
- 手机可运行离线智能模型。
- 不按 token 付费。
- 手机能承担本地推理与随身使用。
- 手机未来可作为 AI 工作流中的一个节点。
- 手机既可能是交互端，也可能是本地推理节点、验证节点或控制端。

### 3.2 已知设备信息

用户发过一张系统监控截图，截图显示：

- 可识别内存总量约为 7.49 GB。
- 因此该设备可按 8 GB 内存档位理解。
- 设备存储为 512 GB，剩余空间非常充足。
- 截图中的“免费内存”很低，但这不等于设备无法运行模型，因为 iOS 会使用缓存、压缩内存与可回收内存。

### 3.3 对 8 GB iPhone 的实际定位

比较稳妥的范围：

- 1B～3B 参数模型，4-bit 量化：最适合。
- 4B 左右模型，4-bit 量化：可以作为能力优先方案。
- 7B～8B 模型：可能能加载，但发热、耗电、速度、内存压力与闪退风险都会提高。
- 12B 以上：不适合作为这部手机的日常本地主力。

更重要的是：

- 手机本地模型适合做文本分析、结构化、提示词优化、剧本拆解、任务分类、轻量代码辅助。
- 手机不适合本地生成高质量长视频。
- 高质量视频生成仍应主要依赖云端大模型或未来更强的本地工作站。

### 3.4 8 GB 与 12 GB 的讨论

用户曾纠结 iPhone 17 标准版 8 GB 与 17 Pro 12 GB。

形成的共识：

- 12 GB 确实可以加载更大的模型、处理更长上下文，并减少系统杀进程概率。
- 但 8 GB 与 12 GB 不决定整个项目能不能做成。
- 对当前阶段而言，工作流设计、能力解耦、任务契约和项目积累比多 4 GB 内存更重要。
- 如果已经拥有 8 GB 设备，不必因为本地模型参数焦虑而立刻更换。
- 未来真正的硬件升级应由实际瓶颈决定，而不是参数焦虑决定。

## 4. 本地模型选型范围

用户明确不想使用国内模型，因此讨论集中于国际模型生态。

### 4.1 Meta Llama

定位：

- 国际开源模型生态中最成熟的一类。
- 教程多、兼容工具多、社区大。
- 常被视为本地模型生态中的通用基准。
- 适合作为默认助手、学习入口与兼容性优先选择。

适合任务：

- 通用对话。
- 文本理解。
- 基础推理。
- 工作流提示词草拟。
- 生态学习。

可能的缺点：

- 小尺寸版本的复杂推理能力有限。
- 中文表现通常不一定是同尺寸模型中最强。
- 手机上需要选择较小参数和量化版本。

### 4.2 Google Gemma

定位：

- Google 推出的开放模型路线。
- 文本理解与创作能力较均衡。
- 适合剧本、文案、分析、提示词优化。

适合任务：

- 小说与剧本文本理解。
- 文案改写。
- 场景和人物提取。
- 提示词优化。
- 中等复杂度内容生成。

可能的缺点：

- 不同版本、不同量化和不同 App 的支持情况需要实际验证。
- 小尺寸模型仍有推理和事实稳定性边界。

### 4.3 Microsoft Phi

定位：

- 小而精。
- 强调小参数下的任务能力。
- 适合手机、边缘设备与结构化工作流节点。

适合任务：

- 结构化输出。
- JSON。
- 工具调用前的参数整理。
- 代码相关任务。
- 分类、路由、任务拆解。
- 固定格式转换。

可能的缺点：

- 开放式长篇创作、情绪表达和复杂故事感可能不如更偏语言创作的模型。
- 某些版本在不同本地 App 中支持程度不同。

### 4.4 Mistral

定位：

- 欧洲模型路线。
- 开发者生态良好。
- 通常强调效率与模型质量。

适合任务：

- 通用文本。
- 开发辅助。
- 结构化任务。
- 可作为替代实现。

可能的缺点：

- 在手机端本地 App 的模型可用性、优化程度与教程数量可能不如 Llama 普及。
- 具体版本要根据 App 实际模型库判断。

### 4.5 推荐角色分工

不是只押注一个模型，而是按角色划分：

- Llama：默认助手、生态入口。
- Gemma：剧本理解、文本创作、提示词优化。
- Phi：JSON、任务分类、工作流节点、工具参数。
- Mistral：作为补充和替代实现。

但第一阶段不建议同时安装多个模型。应先选一个 2B～4B 左右的小模型，把本地闭环跑通。

## 5. 本地模型 App 与安装思路

对话中曾提到：

- Locally AI。
- PocketPal AI。
- 其他可能支持 GGUF 或 MLX 的本地模型应用。

原则：

- 先安装一个本地模型 App。
- 先下载一个 2B～4B 左右的模型。
- 模型下载后关闭网络测试，确认是真正本地运行。
- 先测试：
  - 中文回答。
  - 剧本拆解。
  - JSON 输出。
  - 长文本稳定性。
  - 发热。
  - 速度。
  - 是否闪退。
- 不要一开始就下载很多模型。
- 不要一开始就追 8B、14B 或更大参数。

待验证事项：

- 当前 iOS 版本下哪些本地模型 App 仍在维护。
- 哪个 App 对 iPhone 17 的芯片与内存优化最好。
- 哪些模型版本能稳定运行。
- 是否支持快捷指令、分享菜单、URL Scheme、文件导入或本地 API。

## 7. AI 视频工作流的初步架构

### 7.1 目标流程

一个可能的完整链路：

1. 输入小说、文章、剧本或对话。
2. 文本清洗。
3. 章节切分。
4. 故事结构分析。
5. 人物识别与人物卡生成。
6. 场景识别。
7. 时间线提取。
8. 情绪和冲突提取。
9. 分镜生成。
10. 镜头语言生成。
11. 画面提示词生成。
12. 角色一致性检查。
13. 场景一致性检查。
14. 云端图片或视频模型生成。
15. 失败镜头重试。
16. 配音。
17. 字幕。
18. 音效。
19. 剪辑。
20. 导出与发布。

### 7.2 节省 token 与成本的策略

- 小模型先做清洗、分类和结构化。
- 本地模型先做低成本预演。
- 规则系统先过滤明显错误。
- 只把最终确认的镜头交给昂贵模型。
- 将上下文拆分成角色卡、场景卡、世界观卡、镜头卡。
- 使用缓存，避免重复生成相同人物与场景信息。
- 对任务进行幂等设计。
- 失败时只重试单个节点，不重跑全流程。
- 对每个模型输出进行验证，再进入下一步。
- 云端视频模型只承担最不可替代的高算力环节。

### 7.3 本地与云端的长期关系

近期：

- 本地负责文字、结构化、工作流、素材管理。
- 云端负责视频生成。

未来：

- 可能逐步把图片生成、短视频生成、配音和部分剪辑迁移到本地工作站。
- 但是否完全本地化应由成本、速度、质量决定。
- 不应为了“全本地”而牺牲效率。
- 平台设计必须允许本地与云端实现随时切换。

## 9. Mac 与 iPhone 如何串联

### 9.1 被否定或弱化的方案

iCloud：

- 用户认为慢、麻烦，不希望作为核心同步方式。

Git 直接作为手机与 Mac 通信：

- 技术上可以在 iPhone 使用 Git 客户端。
- 但不适合承担实时通信。
- Git 适合版本管理，不适合作为任务消息通道。

### 9.2 建议架构

- Git：管理代码、文档、任务定义和版本。
- HTTP API：Mac 与手机之间通信。
- 快捷指令：作为 iPhone 上的简单请求客户端。
- Mac 上启动一个轻量服务。
- 手机通过局域网 HTTP 请求 Mac。
- 未来可加安全组网、身份认证和远程访问。

### 9.3 手机是否需要启动服务

不一定。

最简单模式：

- Mac 是服务端。
- iPhone 是客户端。
- iPhone 用快捷指令、网页、App 或脚本发起 HTTP 请求。
- Mac 返回 JSON、文本、任务状态或结果。

更复杂模式：

- iPhone 也可成为被调用节点。
- 但 iOS 后台限制较多。
- 第一版不应依赖手机长期后台监听。

4. API 契约。
5. 模型选型。

8. Prompt 设计。
9. 实验记录。
10. 技术调研。

12. 问题清单。
13. 失败案例。
14. 版本记录。
15. 下一步计划。

### 11.2 Git 与飞书分工

建议：

- Git：代码、Markdown、接口、版本历史、任务文件。
- 飞书：正式知识库、阅读、协作、评审、沉淀。
- ChatGPT Project：长期讨论背景、规划和协作上下文。
- Codex：本地执行、改文件、写代码、跑命令。

### 11.3 飞书 API

用户认为飞书文档 API 可以实现自动读写，并希望 AI 能固定地查文档、写文档，而不是每天重复说明。

形成的判断：

- 飞书 OpenAPI 理论上可以读写文档。
- 但任何 AI 能否直接调用，取决于运行环境是否提供飞书连接器、API 凭证和授权。
- 飞书应被视为一个适配器，而不是核心领域。
- 可以设计一个 `KnowledgeBasePort`：
  - `readDocument`
  - `writeDocument`
  - `appendSection`
  - `searchKnowledge`
  - `createDocument`
  - `updateDocument`
- 第一版可以由本地脚本或 Codex 调用飞书 API。

## 12. ChatGPT 与 Codex 的讨论

### 12.1 用户的核心诉求

用户希望：

- 在 ChatGPT 中讨论方案、架构和思路。
- 自动把方案交给电脑端 Codex 执行。
- Codex 完成代码、文档、Git、飞书 API 等任务。
- 减少复制粘贴。
- 减少重复说明背景。
- 节省 Codex 编码额度。
- 让 ChatGPT 成为上游思考者，Codex 成为执行者。

### 12.2 使用额度观察

用户实际观察到：

- 手机端普通 ChatGPT 语音聊天没有明显消耗 Codex 编码额度。
- PC 端选择 Codex 模式进行调研或执行任务，会消耗 Codex/编码额度。
- Codex App、VS Code Codex 插件等入口可能共享同类 Codex 使用额度。
- 因此应把大量讨论、需求澄清、架构分析放在普通 ChatGPT。
- 只有明确且可执行的任务才交给 Codex。

### 12.3 ChatGPT 与 Codex 的理想分工

ChatGPT：

- 调研。
- 需求澄清。
- 架构。
- 领域建模。
- 方案比较。
- 任务定义。
- 验收标准。
- 风险识别。
- Prompt 设计。
- 项目上下文维护。

Codex：

- 读代码库。
- 写代码。
- 改代码。
- 重构。
- 写测试。
- 跑命令。
- 修改 Markdown。
- 操作 Git。
- 调用飞书 API。
- 创建项目文件。
- 实现 Bridge。
- 执行明确任务。

### 12.4 当前关键结论

- 普通 ChatGPT 与 Codex 是不同能力入口。
- 即使属于同一账号，也不代表 ChatGPT 对话可自动推送给 Codex。
- 是否能直接打通，取决于官方接口、CLI、任务 API、连接器和本地权限。
- 在未确认官方直接桥接能力前，应假设需要一个自建 Bridge。
- Bridge 第一版应很薄，不负责复杂推理。

## 13. Agent Bridge 第一版

这被用户明确设为首要实现任务之一。

### 13.1 目标

实现：

> ChatGPT 输出结构化任务 → Bridge 接收 → Codex 执行 → 结果保存/回传

### 13.2 Bridge 不应做什么

第一版不应：

- 做复杂推理。
- 替代 ChatGPT。
- 自己决定大规模业务逻辑。
- 过早引入复杂多 Agent。
- 过早做平台化。
- 过早绑定飞书。
- 过早依赖浏览器自动化。

### 13.3 Bridge 应做什么

- 接收结构化任务。
- 校验任务格式。
- 写入任务文件。
- 调用 Codex 可用入口。
- 记录执行状态。
- 保存输出。
- 保存日志。
- 返回结果。
- 支持失败重试。
- 保持任务可追踪。

### 13.4 小模型的位置

用户提出使用本地小模型作为路由。

形成的共识：

- 小模型适合做：
  - 分类。
  - 路由。
  - 格式转换。
  - 参数补全。
  - 判断任务属于 ChatGPT、Codex、本地模型还是云端模型。
- 但第一版 Bridge 甚至可以不用小模型。
- 稳定桥接更适合先用规则和脚本。
- 小模型应是桥后面的智能调度员，不是通信桥本身。

## 14. Task 契约

为了让 ChatGPT、Codex、本地模型和未来 Agent 协作，应定义固定任务格式。

建议任务对象至少包含：

```yaml
task_id:
title:
goal:
background:
inputs:
constraints:
deliverables:
acceptance_criteria:
allowed_actions:
forbidden_actions:
target_repository:
target_files:
execution_mode:
priority:
status:
created_at:
result:
errors:
```

### 14.1 Task 的意义

- ChatGPT 只输出 Task。
- Bridge 只读取 Task。
- Codex 执行 Task。
- 其他模型也可以输出同一格式。
- 后续更换模型时不用改整个流程。
- 可以记录 token、耗时、成本和结果质量。

## 15. Codex Web 与多端能力

用户注意到 Codex 中存在“关联 Codex Web”之类入口，并认为 Codex 手机端和电脑端可以协作。

待确认问题：

- Codex Web 是否可创建任务。
- Codex Web 是否可继续桌面或 IDE 中的任务。
- Codex App、CLI、IDE、Web 是否共享线程、项目和执行状态。
- 手机端是否可审批、查看、发起电脑端任务。
- 是否存在官方外部调用接口。
- 是否有 API、CLI、MCP 或可编程任务入口。
- 是否支持把 ChatGPT Project 上下文传给 Codex。
- 是否能以官方方式避免浏览器自动化。

重要提醒：

- 之前对话中关于 Codex 官方功能的部分描述未经完整核验。
- 后续实现前必须只依赖官方文档和真实产品行为。
- 不应把推测当作已确认能力。

## 16. 浏览器自动化方案

用户提出：

- 在电脑端让另一个 Agent 通过 Chrome/MCP 操作 ChatGPT 网页版。
- Agent 输入任务。
- ChatGPT 生成方案。
- Agent 从网页提取方案。
- 再交给 Codex 执行。

判断：

- 技术上可以通过浏览器自动化实现。
- 但这不是 ChatGPT 与 Codex 的原生直连。
- 本质是第三方 Agent 操作网页。
- 可能存在：稳定性、UI 变化、登录状态、会话定位、安全权限和额度不可预测问题。
- 应优先寻找官方 API、CLI、MCP、插件或任务接口。
- 浏览器自动化可作为最后的临时方案，而不是长期核心架构。

## 17. 项目第一阶段的优先级

### P0：统一上下文

- 建立这份总上下文文档。
- 让任何 AI 或开发者接手时知道目标、原则、设备、限制和讨论历史。

### P1：核验能力边界

重点核验：

- ChatGPT 普通模式与 Codex 模式的额度差异。
- Codex App、Web、CLI、IDE 的关系。
- Codex 是否有外部任务调用能力。
- ChatGPT 是否有官方方式向 Codex 派发任务。
- iPhone 快捷指令是否可调用目标本地模型 App。
- 本地模型 App 是否支持 API、URL Scheme、分享菜单或快捷指令。

### P2：定义任务契约

- 设计 `Task` 格式。
- 设计输入、输出、状态和错误结构。
- 设计最小验收标准。

### P3：实现最薄 Bridge

- 先在 Mac 上运行。
- 先用文件或本地 HTTP。
- 先不使用小模型。
- 先不接飞书。
- 先不做复杂 UI。
- 先打通 Codex 执行。

### P4：接入手机

- 用快捷指令或简单 Web 页面向 Mac 提交任务。
- 查看状态。
- 获取结果。
- 手机先作为客户端。

### P5：接入本地小模型

- 做任务分类。
- 做结构化。
- 做低成本预处理。
- 做路由。

### P6：接入飞书

- 文档读取。
- 文档写入。
- 项目知识库同步。
- 决策记录。

### P7：开始 AI 视频工作流

- 从 Story 领域开始。
- 第一条业务链路建议：输入故事文本，输出人物、场景、章节和结构化 JSON。
- 然后再增加分镜与提示词。
