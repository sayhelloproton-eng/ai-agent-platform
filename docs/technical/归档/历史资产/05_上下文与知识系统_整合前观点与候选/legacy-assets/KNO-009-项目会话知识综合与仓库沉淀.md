# KNO-009 项目会话知识综合与仓库沉淀

## 1. 文档定位

定义如何把长 Chat、Codex 报告和执行记录转化为可审计 Git 知识，而不把原始聊天直接当正式事实。

## 2. 输入分类

先区分已确认事实、决策、假设、用户偏好、执行结果、未解决问题、私人上下文与可复用洞见。

## 3. 流程

`选择会话范围 → 提取 Claim → 对照 Git/证据 → 去重与冲突 → 选择目标资产 → Draft → Review → Registry/Release`。

## 4. 目标资产

当前事实进 Context；长期解释进 Knowledge；决定进 ADR；方案进 Technical；观察进 Experiment；方法进 Skill；经验进 Insight；动态任务进 Task Store。

## 5. 隐私

原始聊天可能含账号、路径、Token 或第三方内容，进入 Public Git 前必须最小化、脱敏、核对知识产权并人工 Review。

## 6. 当前实现边界

当前 Chat / 总控 Planner 负责事实恢复、语义判断和完整正文；Project Knowledge Synthesis v0.1.0 提供结构化请求、Claim 分类、重复/冲突、目标资产、退役和影响报告；Executor 仍只负责冻结文件落盘。

首个 governed Pilot 已用于 `docs/knowledge/00_项目入口/`，把六篇正式文章收敛为三篇并保留归档与 superseded 关系。

## 7. 当前能力与后续边界

当前已具备：

- request / result Contract；
- dependency-free Validator 和 Self-test；
- 目录聚合模式；
- 来源、Claim、冲突、目标资产、链接和 Registry 影响输出；
- 人工审批与 `candidate_only` 写入边界。

尚未实现自动 Provider、跨仓库索引、来源行号抽取、批量 Eval、直接写入和外部发布。Skill 当前状态为 `in_review`，更多目录 Pilot 通过后再评估接受。

## 8. 设计原则

- 原始聊天不是真源
- Claim 分事实/决策/假设
- 动态状态不沉淀为长期知识
- 私人上下文默认不公开
- 正式写入关联证据
