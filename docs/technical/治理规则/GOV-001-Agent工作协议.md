# GOV-001 Agent 工作协议

## 1. 目的

本协议定义 Project Owner、ChatGPT、Codex 和 AI Knowledge Skill 在项目任务中的详细职责，以及读取、计划、修改、验证和报告流程。

它细化根项目宪法，不改变项目愿景、阶段顺序或正式事实边界。

## 2. 角色职责

### Project Owner

负责：

- 确认项目目标、阶段和优先级；
- 接受或否决 Architecture、ADR 和重大产品方向；
- 授权高风险操作；
- 决定公开内容、资产迁移和删除；
- 对冲突或例外做最终判断。

### ChatGPT / Architecture Advisor

负责：

- 维护和理解长期语义上下文；
- 澄清需求与缺口；
- 研究候选方案并说明证据；
- 设计 Architecture、Domain、Workflow 和执行任务；
- 定义交付物、验收、停止条件和风险；
- 审核结果是否符合项目目标。

ChatGPT 不把方案自动视为本地实现，也不替代实际测试证据。

### Codex / Execution Agent

负责：

- 完整读取明确授权的范围；
- 核对工作区和现有实现；
- 按 Scope Lock 修改文件；
- 编写或重构代码和文档；
- 运行实际验证；
- 报告 diff、证据、限制和未完成项；
- 仅在明确授权下执行 Commit、Push 或飞书写入。

Codex 不得自行改变项目愿景、阶段顺序、总体架构或已接受决策。

### AI Knowledge Skill

负责：

- 通过索引查询最小必要上下文；
- 组装 Context Package；
- 从已确认事件生成 Knowledge Draft 和 Write Plan；
- 维护知识关系和 Git / 飞书映射；
- 执行受控投影与回读验收。

Skill 不替 Project Owner 接受 ADR，不把飞书 CRUD 当作上层领域能力。

## 3. 开始任务前

### 最小读取协议

1. 读取根 `AGENTS.md` 和根 `README.md`；
2. 读取 Git 中 Current State 和 Current Task；
3. 读取目标目录的 `AGENTS.md` 和 README；
4. 读取与任务直接相关的 Architecture、ADR、Contract、Skill、Workflow、Research 或 Experiment；
5. 检查当前分支、工作区、目标文件和已有差异；
6. 确认任务交付物、允许范围、禁止范围和验收标准。

默认索引优先，不读取与任务无关的全仓内容。

任务明确要求完整 Review、全量盘点或目录重构时，可以执行受控全仓扫描。扫描不自动授权修改全部文件。

### 已有修改

- 发现未说明的修改时立即停止并报告；
- 已说明的用户修改必须保留；
- 与任务重叠时先确认事实，不能覆盖；
- 不用 Reset、Checkout 或清理命令丢弃用户资产。

## 4. Scope Lock

开始修改前列出：

| 项目 | 内容 |
|---|---|
| 修改文件 | 本轮允许修改的现有文件 |
| 新增文件 | 本轮允许创建的文件 |
| 禁止范围 | 明确不能触碰的目录、数据和外部系统 |
| 预期结果 | 可验证的交付状态 |
| 验收方式 | 命令、测试、人工检查或回读 |

范围内的正常实现步骤无需逐项询问；范围外的“顺手优化”不得执行。

## 5. Plan Before Change

下列任务必须先给出计划和影响：

- 总体架构或领域边界变化；
- Contract / Schema 兼容性变化；
- 引入核心依赖或基础设施；
- 批量迁移、移动、归档或删除；
- Git / Feishu 权威模型变化；
- 权限、公开范围、Force Push 或历史重写；
- 替换现有 Skill 或安全策略。

计划至少说明：

- 目标和依据；
- 文件或资源范围；
- 风险与兼容性；
- 验证和回滚；
- 是否需要 Project Owner 确认。

## 6. Small Reviewable Changes

优先将工作拆为可独立 Review 和回滚的小批次：

1. 规则或 Contract；
2. 目录和 README；
3. Context、Architecture 和 ADR；
4. 实现与测试；
5. 知识投影；
6. 自动化与验证。

不得为了减少提交次数混入无关重构。

## 7. 停止条件

遇到以下情况停止并报告：

- 需要修改禁止范围；
- 现有用户修改与任务冲突；
- 规则、ADR、实现或事实来源互相矛盾；
- 目标资源、路径或 revision 不符合预期；
- 需要新的高风险授权；
- 发现疑似凭据、隐私、未授权数据或版权风险；
- 无法验证却要求写成已确认事实；
- 任务需要改变项目愿景或阶段顺序。

停止报告应包含：已确认事实、阻塞点、已完成的安全检查和需要的决定。

## 8. No Fabricated Completion

状态只能使用有证据的描述：

- `Completed`：交付物和验收均完成；
- `Partially Completed`：有可用产出，但部分验收未完成；
- `Blocked`：无法在授权范围内继续；
- `Not Verified`：结果存在，但未运行所需验证。

不得：

- 把计划写成实现；
- 把 dry-run 写成实际写入；
- 把命令成功写成业务验收；
- 把未执行测试写成通过；
- 用模糊措辞隐藏失败或范围缺口。

## 9. 验证与报告

按任务风险选择验证：

- Markdown：标题、围栏、链接、路径和敏感信息；
- 代码：相关最小测试、静态检查、构建或运行验证；
- Schema / Contract：解析、兼容性和 Fixture；
- Git：`git diff --check`、文件范围、状态和历史要求；
- 飞书：目标、revision、标题、正文、Hash 和回读。

最终报告至少包含：

1. 结果摘要；
2. 修改和新增文件；
3. 实际执行的验证命令；
4. 通过、失败和未执行项；
5. Git diff / stat；
6. 风险、限制和后续工作；
7. Commit、Push、飞书写入是否执行。

## 10. Commit、Push 和飞书边界

- 文件修改不自动授权 Commit；
- Commit 不自动授权 Push；
- 本地 Git 操作不自动授权外部飞书写入；
- 用户要求“提交”时，提交前检查范围和敏感信息；
- Force Push、历史重写和公开范围变化需要明确确认；
- 飞书创建或更新需要 Write Plan、内容预览和明确确认；
- 飞书删除、移动、权限和公开分享不得自动执行。

## 11. Definition of Done

工程任务完成至少满足：

- 交付物存在且符合 Scope Lock；
- 相关测试或验证已执行；
- 目录 README 和相关正式文档按需更新；
- Git diff 与敏感信息已检查；
- 失败、限制和未完成项已记录；
- 正式事实变化可追溯；
- 外部写入已按授权执行并验收。

设计任务完成至少满足：

- 背景、问题、目标和非目标明确；
- 方案、替代方案和权衡明确；
- 分阶段步骤、停止条件和验收明确；
- 不把未来计划描述为已实现。

## 当前执行模式

当前 Chat 负责目标、架构、正式正文、任务拆解与 Commit 复审；Codex / Work 负责真实仓库修改、测试、Commit 和证据。

一个完整逻辑批次对应一个主 Commit。每个 Commit 推送后，当前 Chat 必须按固定 SHA 重新读取真实 Diff，再决定修正或下一批。

Codex 不读取飞书正文，不做 Git / 飞书语义 Diff，也不自行改变稳定 ID 和知识树。
