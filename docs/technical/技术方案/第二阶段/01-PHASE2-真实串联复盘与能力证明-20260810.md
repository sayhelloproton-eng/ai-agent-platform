# Phase 2｜真实串联复盘与能力证明（2026-08-10）

## 1. 原始目标

第二阶段不是为了做一个“自动点击 ChatGPT 的 Chrome 扩展”，而是验证一个最小 Agent Platform：

```text
User Goal
→ Controller Decision
→ Task Control Coordination
→ Local / Browser Capability Execution
→ Approval / Evidence
→ Result
→ Controller Continuation
→ Task Completion
```

Browser Host 的原始定位是受控 Executor / Adapter，而不是工作流大脑。

## 2. 五个 MVP 的实际落地

### Controller

已经真实证明：

- `getTaskDecisionContext`；
- Controller Claim；
- `claimToken` 与正式 Command；
- `REQUEST_ROLE_WORK`；
- Controller 被 Browser-backed Wake 重新触发后继续读取最新状态。

结论：Controller 已经从“聊天角色”升级成平台中的真实决策节点。

### Local Control

已经真实证明：

- Gateway → Local Control 的受控访问；
- Capability Registry / Policy / Adapter；
- Local Result / Evidence；
- 模型没有直接获得 Mac FS / shell 权限。

结论：本机能力可以作为平台 Capability 暴露，而不是直接耦合给 Agent。

### Task Control

已经真实证明：

- Task / Plan / Node；
- Controller Claim；
- WorkItem；
- Dispatch；
- Event；
- Version / Idempotency；
- Result / Failure / Block / Complete；
- Browser 与 Local Work 的真实流转。

结论：任务系统已经进入真实异步协调系统的问题空间。后续问题主要是状态语义精炼，而不是任务系统能力缺失。

### Browser Host Runtime

已经真实证明：

- Extension / Host lifecycle；
- GPT / Conversation Binding；
- 自动 `listPending → claim`；
- Approval Draft；
- 一次性人工 Grant；
- 页面输入；
- send readiness；
- exactly-once Browser submit；
- 真实 `HOST_DISPATCH_DELIVERED`；
- 通过网页 GPT 驱动 Controller 进入下一步。

结论：核心命题“平台是否能通过受控 Browser Runtime 驱动真实网页 GPT”已经得到肯定答案。

### Mobile Model / Execution Flow Runtime 输入

手机端 MVP 仍在独立验证，但已经形成下一阶段的重要架构输入：

- FAST / REASON 双模式；
- MLXHub LAN Server Provider；
- Tool Proposal 与执行权限分离；
- `backend_ref / capability_ref / command_ref` 逻辑引用；
- Runtime-owned provider config；
- in-process / localhost / LAN / remote 的部署无关目标。

这些内容在 Phase 3 中作为公共 Runtime / Provider 架构输入，而不是 Phase 2 收口阻塞项。

## 3. 真实串联验证的关键进展

### Level 2

真实 READ PATH 已完整通过，Task 最终 `COMPLETED`。这证明 CTL / TSK / LCL / BHR 可以通过正式接口形成可观测串行闭环。

### Level 3

Level 3 不是一次通过，而是多轮真实尝试逐段推进。其价值在于逐步证明：

```text
Task Intake
→ Decision Context
→ Claim
→ Browser Work
→ Dispatch Poll
→ Approval Draft
→ Human Grant
→ Browser Submit
→ Delivery
→ Controller Conversation continuation
```

最终 `phase2-l3-final-20260810-1018-10` 已经形成真实 `HOST_DISPATCH_DELIVERED`，同时再次暴露 post-delivery response lifecycle 的设计问题。这一证据足以说明 Browser mutation 能力已经成立，后续问题属于生命周期边界，而不是“Browser Host 还不能工作”。

## 4. 实际研发流程的演进

早期：

```text
现场失败
→ 立即诊断
→ 小补丁
→ 同一 Task retry
```

后期逐渐收敛为：

```text
真实证据冻结
→ 旧 Task 封存
→ ChatGPT stop/go
→ 源码审计
→ Frozen Overlay
→ Codex 三方兼容核对
→ 机械落库
→ 自动化门禁
→ commit / push
→ Reload
→ 全新干净 Task
```

这个流程本身也是 Phase 2 的重要工程资产。Phase 3 应继续保持“真实 Browser 只做最终 Acceptance，不做主要状态机 debugger”的原则。

## 5. 用户体验差距

最终产品期望：

```text
用户给目标
→ 平台自动协调
→ 需要危险动作时用户批准一次
→ 平台继续
→ Task 完成
```

Phase 2 测试阶段实际用户承担了大量：

- Reload；
- Binding 检查；
- Poll 检查；
- Approval Draft 回读；
- Dispatch / Journal 回读；
- Action Allow；
- 页面状态判断。

这说明当前用户在验收阶段充当了人工 orchestrator / debugger。Phase 3 的目标之一就是把这些内部状态重新收回平台，仅把真正的人类决策留给用户。
