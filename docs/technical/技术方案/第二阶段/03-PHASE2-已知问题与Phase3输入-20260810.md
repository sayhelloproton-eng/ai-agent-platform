# Phase 2｜已知问题与 Phase 3 输入（2026-08-10）

> 本文不是 Phase 2 blocker 清单，而是正式 Phase 3 设计输入。除非影响历史证据保存，不再要求在 Phase 2 分支继续逐项修复。

## P0：必须进入 Phase 3 领域设计

### 1. Browser Delivery 与 response lifecycle 耦合

现象：Browser message 已经 `HOST_DISPATCH_DELIVERED`，但 BHR 继续等待 ChatGPT response；后续合法 Action Allow 被判断为 `RESPONSE_INTERRUPTED_BY_USER`，导致原 Browser Work 反向 FAILED。

Phase 3 输入：Delivery terminal semantics；Execution / Continuation 分离。

### 2. Observation 有页面副作用

现象：Observation / followLatest 会主动滚动；长聊天页面增长后 viewport 被扩展反复拉动，位置越来越不稳定。

Phase 3 输入：Observation Plane 必须 read-only；scroll / reveal 成为显式能力或执行内部局部动作。

### 3. Approval waiting 与 execution lease 混用

现象：人工审批期间 Dispatch claim 不断过期 / reclaim，产生较高 claimEpoch 和不必要的 Journal 压力。

Phase 3 输入：正式 `WAITING_FOR_APPROVAL` / `READY_TO_EXECUTE`；业务等待和执行租约分离。

### 4. Controller Wake 生命周期过重

现象：Wake 会与 Controller generation、composer、Action confirmation、user-control 竞争。

Phase 3 输入：Wake 作为通知 / continuation delivery；BUSY defer，Delivery 后结束。

### 5. Browser Runtime 内部职责过载

Phase 3 输入：至少概念上拆为：

```text
Host Lifecycle Plane
Observation Plane
Execution Plane
Continuation Plane
```

## P1：平台公共领域必须统一解决

- 模块不能直接 import 其他领域内部实现；
- 同一能力需要支持 in-process / localhost / LAN / remote；
- 配置由 Runtime-owned Composition Root 注入；
- Flow 不得硬编码 IP、目录、执行文件、内部源码路径；
- 使用 `backend_ref / capability_ref / command_ref / provider_ref` 等逻辑标识；
- 公共合同必须版本化、可验证、有兼容策略；
- Opaque ref、Idempotency、Error / Result、Approval / Evidence 语义必须统一；
- 模块部署位置不能改变 Flow 协议。

## P1：Task 领域必须精炼

第三阶段需要重新定义而非简单扩字段：

- Task / Plan / Work / Dispatch 各自拥有的状态；
- Claim / Lease 的严格语义；
- Business Wait；
- Approval Wait；
- Delivery；
- Result；
- Continuation；
- Retry / Recovery；
- UNCERTAIN；
- Cancellation；
- Event cursor / replay。

要求：先写“需求目标与不可接受行为”，再冻结状态机。

## P2：Browser / Host Hardening

- stale Binding prune；
- heartbeat freshness 与 poll liveness 分离；
- Extension reload / content script recovery；
- pending review TTL / cleanup；
- Journal pressure / compaction；
- dynamic DOM contract；
- anchor-based scrolling；
- recorded DOM fixtures；
- restart / replay matrix。

## P2：Mobile / Inference Provider

手机模型 MVP 仍在独立验证，因此 Phase 3 只冻结 Provider 边界，不冻结具体模型结论：

- FAST / REASON role；
- Provider mapping 由 Runtime 配置；
- Tool Proposal 不是 Tool Execution；
- inference backend 不拥有 Task / Approval / Browser 权限；
- Flow 不携带设备 IP / model id；
- 未来 MLXHub、Mac local、cloud backend 可互换。

## 迁移原则

Phase 3 允许颠覆性设计和整个仓库重塑。

但是必须区分：

```text
保留真实语义
≠ 保留当前实现
```

可以删除当前 class、package、目录和旧内部 API；不应无意识删除已经被真实测试证明的重要安全语义，例如：

- Opaque refs；
- Claim token / Delivery receipt / Report token 分离；
- one-time Approval；
- no blind retry after uncertain side effect；
- target identity / binding；
- idempotency；
- Delivery evidence。
