# 智能体运行与协作领域｜当前设计原则与 v1 非目标

## 1. v1 核心原则

```text
真实业务优先
当前 Carrier 可落地优先
Owner 清晰优先
静态明确优于动态聪明
防御性校验优于相信模型
```

不为未来通用 Agent Platform 提前制造 Agent Runtime framework。

## 2. 角色模型

v1 固定三个复合角色：

```text
产品 = 运营 + 产品经理
总控 = 项目管理 + 研发
测试 = 测试 + 运维
```

## 3. Agent Package / Role / Worker

- `Agent Package`：版本化 Agent 定义，以 npm package 为载体。
- `roleRef`：用户部署后真实 Custom GPT 的 g-id。
- `workerRef`：具体 Custom GPT Conversation 的 c-id。
- `agentPackageRef != roleRef`。
- v1 不建立 Agent、Session、AgentRun business entity。
- 一个 Agent Package 在一个工作区只能有一个当前有效 Role。

## 4. Role 生命周期与注册

- Role 是长期部署配置，不跟随 Task 结束释放。
- 更换 GPT 采用 delete + recreate/register；v1 不提供 updateRole/replaceRole。
- Runtime Public API 只暴露 `listRegisteredRoles / getRegisteredRole`。
- register/delete 属于本地管理 CLI。
- 一个 Role 一个独立 Bearer/API key；Gateway 根据凭证反解 roleRef，不信任 GPT 自报身份。
- Key 可独立轮换，不改变 Role identity。

## 5. Agent Package 内容边界

- Agent manifest / GPT create metadata 放在 package.json 的 Agent 字段。
- fixed context 与 memory 语义分离。
- v1 不允许运行时自动改写永久 Memory；长期材料更新通过 Agent Package 版本升级。
- Custom GPT 创建/编辑是 Web-only，CLI 只生成材料、校验要求并给出 `ACTION_REQUIRED_WEB`。
- Actions OpenAPI 静态版本化随 Agent Package 发布，不做运行时 schema composer/capability catalog。

## 6. Action 安全与 Gateway

Action 选择使用三层约束：

1. Agent Package 裁剪可见 operation；
2. OpenAPI operationId/summary/description/schema/error 明确；
3. 下游领域 Policy / approval / runtime validation 做最终防线。

`agent-gateway` 是 Custom GPT Actions 唯一公网 ingress，负责认证、OpenAI transport 适配、请求路由、协议归一化和响应序列化；不拥有 Task、Effect、Model 判断或业务文件事实。

## 7. Task / Execution / Agent 的事实分工

- Task：workflow、Node、TaskRoleBinding、TaskDocument 的唯一业务真源。
- Agent：Role、Worker identity、Collaboration Message 的逻辑真源。
- Execution：真实本地/Browser Effect、物理文件 fetch/materialization、Delivery/Evidence。
- Agent 不复制 Task binding；Execution 不推进 Task 状态。

## 8. Worker 生命周期

- 产品 Worker 可以在 Task 创建前已经存在并参与需求形成。
- Task 获得人工执行授权后，先创建/绑定研发 Worker，再创建/绑定测试 Worker；两者齐备后才进入正式 Node work。
- 同一 Task 同一 role 始终复用同一 Worker。
- reopen 继续使用该 Task 原 Worker，不创建新人员。
- workerRef/c-id 的权威获取与核验仍由 Browser URL/页面现实完成；Action request 不被假定提供稳定 c-id。

## 9. Collaboration

Public collaboration 只有：

```text
askPeer(...)
replyPeer(...)
```

消息中心持久化逻辑问答；严格串行：下一问必须等上一 Reply 物理 `DELIVERED`。Browser 物理投递由 Execution 完成，Agent 根据结果更新逻辑 delivery state。

## 10. Browser 与 Carrier

Browser Extension 不属于 Agent Domain；它属于 Execution。Agent 只依赖 Browser 能力结果与 Worker identity evidence。

WAKE 只注入小型 identity/trigger envelope；大型动态 Task 内容优先通过 Task API / GPT Actions File Bridge，而不是 DOM 大段注入。

## 11. OpenAI Carrier 使用原则

- v1 使用 GPT Actions，不同时启用 Apps。
- GPT native Function Calling 是 Carrier 能力，不改变 Model Runtime 的工具调用架构。
- File Bridge 用于 Conversation 文件输入/输出，不新建 File Domain、Artifact Domain、File Service 或 OpenAI File DB。
- Web Search 用于公共互联网 research；Code Interpreter 用于受限分析/patch artifact；真实 repo/browser/platform Effect 仍由 Execution 执行。
- exact model id 不是 Role READY 条件；READY 依据实际 capability + auth + E2E behavior。

## 12. v1 明确非目标

- 通用 Agent/Session/AgentRun framework。
- 动态 Action Schema / Capability Catalog / Runtime tool discovery。
- Agent 主动监听 READY Node 并成为第二调度器。
- Agent 直接读写 Task DB 或 Execution Store。
- askPeer 直接调用 Browser Extension。
- 自动创建缺失 Worker 作为 askPeer 的常规职责。
- 自动写永久 Memory。
- OAuth、多租户、复杂 Role update workflow。
- MCP 重新进入当前主链。

## 13. 升级触发器

只有出现真实多 Carrier、多 Role 实例、多租户、可替换 Session runtime、动态 capability negotiation 等需求时，再扩展当前模型；不得为了潜在未来提前增加实体和服务。
