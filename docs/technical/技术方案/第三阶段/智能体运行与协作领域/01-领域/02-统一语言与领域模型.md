# 智能体运行与协作领域｜领域模型与事实所有权

> 本文是 v1 领域语义真源。实现不得自行增加 Agent / Session / AgentRun 等实体，也不得把 Task / Execution 状态吸入本领域。

---

# 1. 最小领域模型

## 1.1 Agent Package

**Agent Package 是 v1 的 Agent 实体定义。**

它是一个 npm 包，承载：

- 角色名称、描述；
- 对话开场白；
- Instructions；
- 固定 Context / Memory / Knowledge 文件；
- Custom GPT 推荐模型与功能配置；
- 该角色固定的 Custom GPT Action OpenAPI；
- Carrier setup CLI；
- Role register / show / validate / delete CLI；
- 版本信息；
- 部署领域要求的模块描述/requirements/provides/lifecycle primitives。

Agent Package 是长期、版本化定义，不是一个运行中的 Worker。

未来同一 Agent Package 可以通过不同 Carrier Adapter 导出到：

```text
Custom GPT
OpenCode
Codex
Claude Code
Future self-hosted runtime
```

v1 只实现 Custom GPT Carrier。

---

# 2. Role

## 2.1 定义

Role 是 Agent Package 在当前用户环境中创建并注册后的**固定 Carrier 角色实例**。

v1：

```text
roleRef
= 用户在 ChatGPT Web 创建 Custom GPT 后得到的真实 g-id
```

示例形式：

```text
g-xxxxxxxx-...
```

`roleRef` 不能在 npm 包发布时前置生成，因为它来自用户部署后实际创建的 Custom GPT。

## 2.2 Role 与 Agent Package 的关系

```text
Agent Package 1 ---- 1 Registered Role   （v1 / 单工作区）
```

v1 一个工作区中，一个 Agent Package 只允许一个当前有效 Role。

Role Registry 只保存部署实例事实；名称/描述等展示信息继续复用 Agent Package `package.json`，不复制成第二真源。

Role Registry 保存：

```text
agentPackageRef
registeredPackageVersion
roleRef
carrierType
carrierUrl
registeredAt
status
```

## 2.3 Role 生命周期

```text
Agent Package installed
→ 用户根据 CLI 创建 Custom GPT
→ 获得 g-id / URL
→ 本地 register-role
→ Role REGISTERED
→ 长期存在
```

Task 完成不会删除 Role。

更换真实 GPT 时，v1 **不做 update/replace API**：

```text
delete local registration
→ 用户在 Web 创建/准备新的 GPT
→ register-role 新 roleRef
```

# 3. Worker / Person

## 3.1 定义

Worker / Person 是当前 Role 下真正处理工作的具体人员实例。

v1：

```text
workerRef
= Custom GPT Conversation ID（c-id）
```

逻辑：

```text
roleRef
→ 固定角色 GPT

roleRef + workerRef
→ 可以定位该角色下具体 Conversation
```

## 3.2 不建立 Worker Registry

v1 不建立：

```text
全局 Worker Pool
Worker availability
busy / idle
health state
round-robin
reassign
steal
```

Worker 由 Browser Extension 在真实 ChatGPT Web 中创建/识别；正式 Task 绑定事实保存在 Task Domain。

## 3.3 Task 级绑定

一个 Task 应保存：

```text
roleRef → workerRef
```

这表示：

> 该 Task 中这个角色由这个具体人员/Conversation 承担。

Task 完成后，绑定作为 Task 历史事实保留；Task 归档，不重新开启。

Node 仍可以保存当前 run 实际执行的 `workerRef`。

因此：

```text
Task role binding
= Task 内稳定人员关系

Node.workerRef
= 当前 Node run 实际执行人员事实
```

# 4. reopen 与 Worker

reopen 的核心规则：

> **同一个 Task、同一个角色必须复用已绑定的原 Worker。**

`reopenNode` 可以清空目标 Node 当前 run 的 `workerRef` 并进入 `READY`；Task-level `TaskRoleBinding` 不随 run 清空。新的 run 在 `startNode` 时必须从 TaskRoleBinding 重新解析并写回**同一个 Task-bound workerRef**。

即：

```text
Task.roleBindings[requiredRoleRef].workerRef = worker-A   # 不变

reopenNode
→ Node.runNo + 1
→ Node.workerRef = null（run-level reset）
→ Node READY

Extension
→ 读取 Task role binding = worker-A
→ startNode(... worker-A ...)
→ Node.workerRef = worker-A
```

这样同时满足：

- Task Domain 每个 run 的 start 事务语义；
- 用户明确要求 reopen 必须原人继续；
- 不引入 worker reassignment。

---

# 5. Agent / Session / AgentRun 为什么 v1 不建立

当前真实映射已经足够：

```text
Agent Package
Role(g-id)
Worker(c-id)
```

没有独立生命周期需要：

```text
Agent
Session
AgentRun
```

因此 v1 禁止为术语完整性增加三层表与状态机。

升级触发器只有：

- 一个 Worker 未来确实拥有多个 Session；
- Carrier 不再把 Conversation 作为稳定工作上下文；
- 需要 Run 级审计而 Task/Execution facts 无法表达；
- 自建 Agent Runtime 产生独立运行生命周期。

# 6. Context 模型

## 6.1 Package fixed context

Agent Package 内长期资料：

```text
fixed-context.md
memory.md
knowledge/*
```

这些是静态长期资料。

## 6.2 Instructions

Instructions 是行为、职责、边界与工作规则；v1 直接存放在 `package.json` 的 Agent 配置字段中，不单独创建 `instructions.md`。

## 6.3 Conversation context

同一个 `roleRef + workerRef` 是同一个具体 Custom GPT Conversation，因此可以持续保留任务工作上下文。

v1 **不要求每次 Extension 唤醒后强制先调 `getNodeContext`**。

Worker Instructions 必须要求：

- 当前上下文清楚且足够：直接继续；
- Task 状态可能变化 / 信息不明确：主动查 Task Public API；
- 需要代码、环境、日志等真实事实：主动查 Execution Local Resource API；
- 需要上下游确认：`askPeer`；
- 不确定正式状态：不得仅凭旧聊天历史猜。

Conversation 是有效工作上下文，但领域正式事实仍由各 Owner API 校验。

## 6.4 永久 Memory

v1 不做 Agent 自动写永久记忆。

长期资料修改：

```text
修改 Agent Package
→ package version bump
→ CLI 提示
→ 用户在 Custom GPT Web 手工更新 / 重新上传 Knowledge
```

# 7. 三个角色职责

## 7.1 运营 + 产品经理

主要发生在 Task 创建之前：

- 用户需求沟通；
- 需求澄清；
- Requirement / 产品方案；
- 查询已注册角色；
- 用户确认后创建 Task；
- 创建时绑定产品自身 roleRef + workerRef，并填入研发/测试 roleRef；
- Task 执行期间继续作为可被研发/测试问询的产品 Worker。

## 7.2 总控 = 项目管理 + 研发

- 理解 Task/Node；
- 技术设计与研发；
- 调用本地资源与执行能力；
- 开发完成后 `completeNode`；
- 基于测试/业务反馈判断 wait / reopen；
- reopen 后由原 Worker 继续。

## 7.3 测试 + 运维

- 测试方案；
- 测试执行；
- Test Result；
- 运行状态 / 日志 / health 查询；
- 发布与运维验证；
- 需求不明确时 `askPeer(product)`；
- 研发问题不明确时 `askPeer(dev)`；
- 不直接修改 Task Workflow 规则。

# 8. Agent Collaboration

本领域唯一拥有：

```text
CollaborationThread
CollaborationMessage
Delivery state
```

v1 不做：

```text
Delegate
Handoff
Spawn
Team optimizer
A2A runtime
```

跨角色协作通过两个 Agent Action：

```text
askPeer
replyPeer
```

Thread 支持多轮，但严格一问一答：

```text
Q1 → A1 → Q2 → A2 → ...
```

上一问未收到回复前，禁止同 Thread 继续发问。

# 9. 与五领域的边界

## Task Domain

Agent Domain 只消费 Public API；不读 Task SQLite。

Task 保存：

```text
role bindings
workerRef
Node / runNo
Workflow
Task Documents
```

## Execution Domain

Agent 发出 Action Intent；Execution 完成：

```text
File / Git / Shell / CodeGraph
Browser mutation / observation
Delivery / Result / Receipt
Approval / Authorization
```

## Inference Domain

Agent 只表达需要的逻辑推理能力；Provider/Model/Retry/Health 不归本领域。

## Deployment Domain

Deployment 管模块安装/配置/启动/验证；Agent Package 自己不拥有整体 deployment plan/apply。

## Browser Extension

是重要 Driver/Adapter，不是领域事实 Owner。

# 10. Worker 是 Task-scoped Person

不同 Task **禁止复用**同一个 Custom GPT Conversation：

```text
Task A → Product-A / Dev-A / Test-A
Task B → Product-B / Dev-B / Test-B
```

原因：Conversation 保持上下文，跨 Task 复用会造成需求、实现、测试信息污染。

同一 Task 内则必须稳定复用：

```text
roleRef + taskId → one workerRef
```

包括 reopen。

产品 Worker 例外只在“创建时机”：它在 Task 前由用户主动打开新的产品 GPT Conversation 并完成需求沟通；该 Conversation 在 createTask 时成为正式 product worker。研发/测试 Worker 则在 Task human authorization 后，由 Execution Browser provisioning flow 真实 CREATE/识别 Conversation，Agent 校验 Worker identity，Task `bindTaskWorker` 固化 TaskRoleBinding。

---

# 11. Role deletion 不是生命周期状态

v1 Role Registry 只保存当前注册 Role。`role delete` 是 physical delete：

```text
query Task Public API for non-terminal usage
→ in use: ROLE_IN_USE
→ otherwise remove registry entry + secret
```

不建立 `DELETED` 状态/tombstone。

---

## 当前正式约束：TaskRoleBinding ownership

Agent 只定义并校验 Role、Worker/Conversation identity；**TaskRoleBinding 由 Task Domain 唯一持久化**。reopen 时 Agent 不重新分配人员；TaskRoleBinding 保持不变，Node run-level `workerRef` 可清空后由 Task `startNode` 自动解析同一 `workerRef`。
