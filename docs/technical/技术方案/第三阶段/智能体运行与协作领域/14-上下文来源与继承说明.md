Phase 2 是证据来源，不是 Phase 3 代码结构真源。

# 6. Deployment context 的最新优先规则｜本 Chat 后续覆盖

早期 Phase 3 / EF6 文档曾提出：模块只声明 requirements/lifecycle primitives，由 Platform Deployment Planner/Executor 负责具体 apply。

**本 Chat 后续用户已明确修正为：**

> 所有独立包必须遵守统一 Package Lifecycle Protocol；同时每个包自己完成与自身有关的账号创建引导、登录、配置、绑定、启动/停止、status/verify/doctor 等闭环；总 Deployment 只统一发现、编排并透传调用包自己的命令。

因此本 Agent Domain v0.2 将其作为 `CROSS-DOMAIN CHANGE` 提交 Deployment 总纲，而不能继续把早期 Planner-owned apply 当作当前答案。

最终统一 lifecycle descriptor、命令合同、package/bin 命名仍由 Deployment Domain 冻结。

# 7. Current OpenAI product facts 的作用

v1 Carrier 依赖 ChatGPT Web Custom GPT，因此以下是**外部产品约束**，不是平台自己发明的领域规则：

- GPT editor 提供 Instructions、Knowledge、recommended model、Capabilities、Actions 等配置；
- Knowledge 是上传文件，行为/工作流规则应写 Instructions；
- Actions 通过 OpenAPI JSON/YAML 描述 server/endpoints/parameters/operationIds；
- Action auth 支持 API Key（含 Bearer）等方式；
- Schema 可以粘贴/导入，用户需要在 GPT editor 中配置和测试；
- v1 创建/更新流程按 Web editor 人工操作设计，不依赖一个未纳入官方文档的 Custom GPT management API。

这些事实会随 OpenAI 产品变化，因此未来 Agent Package Carrier 适配升级前必须重新核对官方文档。

# 8. 旧结论与当前结论映射

| 早期/前置说法 | 当前正式结论 |
|---|---|
| Role 可是包内 `role:controller-dev` | v1 roleRef = 部署后真实 GPT g-id |
| Conversation≈Worker/Session，实体待定 | v1 只建 Worker/Person，不建 Session |
| Agent entity 是否需要待定 | Agent Package 就是 v1 Agent definition |
| Agent Domain 选择 worker | v1 实际 Worker creation/identity 由 Task-driven Extension完成；Agent Domain 管 Role/Carrier，Task 保存 binding |
| reopen 清 Node worker 后可重新选 | Task-level binding不变，必须原 Worker |
| 每轮 Agent Run 可能先组装 context | 不建 AgentRun；Conversation 保持上下文，按需查询 |
| Capability Catalog 候选 | v1 不做 |
| dynamic Schema 候选 | v1 每包 static OpenAPI |
| Agent Message/Delegate/Handoff 待定 | v1 只做 askPeer/replyPeer Message Center；不做 Delegate/Handoff framework |
| Collaboration 可能创建/恢复 Session | v1 消息绝不创建 Worker |
| registerRole 可视作 API | v1 local CLI，不是 runtime Public API |

# 10. 文档中的三种状态必须区分

## CONFIRMED

用户在本 Chat 已确认/认可或明确提出且未被后续推翻。

实现默认遵循。

## CROSS-DOMAIN CHANGE / NEED MASTER AUDIT

本领域需求已经确认，但改变其他领域 Public Contract，必须由总纲/Owner 审计后才能视为对方真源。

## IMPLEMENTATION RECOMMENDATION / OPEN

为了把业务落地而提出的工程形状，例如：

- （已裁决）Collaboration 下一问必须等待上一条 Reply 真实 `DELIVERED`；
- `WORKER_BIND` 的最终浏览器文案；
- `startNode` 与 Browser submit 的精确顺序；
- SQLite/JSON 的最终文件名；
- candidate npm package 名。

这些不能伪装成用户已经确认的业务语义。

# 11. Dynamic Task Context：Knowledge 与 File Bridge 分层

Custom GPT v1 上下文来源进一步固定为：

```text
Instructions              → 行为/硬规则
Knowledge                 → Role 长期静态参考
Conversation history      → 当前 Worker 连续上下文
Action JSON               → 小型结构化 Task/Node/identity/control
Action File Bridge        → TaskDocument / report / patch / bounded context pack
Execution/Model Public API→ 真实资源与受约束认知
```

Task 动态文档不进入永久 Knowledge，也不默认由 Browser DOM 注入。

Gateway 只做 Carrier transport；Task 仍是 TaskDocument 真源，Execution 仍是物理 fetch/materialization/effect Owner。
