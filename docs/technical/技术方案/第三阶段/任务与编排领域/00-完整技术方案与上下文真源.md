# 1. Domain｜领域：解决什么问题

任务与编排领域负责所有长期、确定、可恢复的“工作推进事实”。

它回答：

```text
当前有哪些 Task？
Task 是否允许开始？
当前执行到哪个 Node？
哪个角色应该执行当前 Node？
当前 Node 由哪个具体 Worker 承担？
Task 是运行、等待、失败、暂停还是完成？
后续 Node 何时可以进入 READY？
出现问题后应该继续、等待、失败还是 reopen 前序 Node？
大型任务链中哪个 Task 当前允许执行？
任务相关需求 / PRD / 技术方案 / 测试结果应该给当前 Worker 哪些上下文？
```

核心职责：

> **持久化工作事实 + 校验合法推进 + 提供稳定查询。**

它不负责“智能判断下一步应该做什么”，也不负责真实世界副作用。

# 3. Subdomain｜第一版子问题

第一版只拆 5 类业务问题，不为了 DDD 形式感继续拆细。

## 3.1 Task Lifecycle

负责 Task 创建、可执行性、开始、暂停 / 恢复、等待人工处理、技术失败、完成、终止。

## 3.2 Task Chain / TaskGroup

负责大型系统预先建立一组阶段 Task、顺序关系、`maxActiveTasks = 1` 的第一版约束、TaskGroup 人工 `READY → ACTIVE`、前序 Task 未完成时后序 Task 不可执行，以及当前 Task `WAITING / FAILED / PAUSED` 时停止继续释放后续 Task。

第一版不是通用 Task DAG。

## 3.3 Node Workflow

负责一个 Task 内的有序 Node、Node 角色要求、具体 Worker 绑定、输入 / 输出文档要求、自然向后推进和 `reopenNode` 受控回退。

第一版不是通用图工作流引擎。

## 3.4 Task Documents

负责 Requirement / PRD / Technical Design / Test Plan / Test Result / Release Result 等 Task-scoped Markdown；Node 明确声明 `inputDocuments / outputDocuments`；Worker 按 `taskId + nodeId` 获取该 Node 所需上下文；Git 管正文历史；SQLite 只保存当前文档索引 / 路径 / hash。

## 3.5 Message / Event / Audit

负责 WAITING / FAILED 等需要人关注的待处理消息、Task / Node 状态事件、审计与问题追踪。第一版不引入消息总线，由 SQLite 保存，扩展 / 前端轮询读取。

# 任务与编排领域｜领域模型与状态语义

> 本文是第一版业务语义真源。实现不得自行发明额外状态含义。

---

# 1. TaskGroup / Task Chain

## 1.1 定义

TaskGroup 是第一版“大型系统阶段任务链”的轻量容器。

典型场景：

```text
一个大型系统一次规划 10 个阶段 Task
→ 先全部创建
→ 但一次只允许一个 Task 实际进入工作
→ 当前 Task 成功后再释放下一 Task
```

第一版 `maxActiveTasks = 1`。这是组内约束，不是平台全局只能执行一个 Task。

## 1.2 状态

第一版 TaskGroup 至少：

```text
READY
ACTIVE
SUCCEEDED
```

`READY → ACTIVE` 必须来自一次明确的人工启动。

TaskGroup ACTIVE 后，Task Domain 只负责计算 / 校验哪些 Task 当前可执行。对于“一夜迭代”模式，人工授权发生在 TaskGroup 层；后续 Task 的实际启动可由扩展 / 自动化驱动，但仍必须调用正式 `startTask` 并通过 Task Domain 校验。

## 1.3 阻塞

若当前 Task 为 `WAITING / FAILED / PAUSED`，TaskGroup 停止继续释放后续 Task，直到人工处理。

---

# 2. Task

## 2.1 定义

Task 是一个可持久化、可启动、可暂停、可等待、可失败恢复、可完成或终止的工作目标。

Task 拥有：

```text
taskId
title
objective
status
version
planVersion
currentNodeId
TaskGroup membership（可选）
```

## 2.2 Task 状态

第一版：

```text
PENDING
READY
ACTIVE
WAITING
FAILED
PAUSED
SUCCEEDED
TERMINATED
```

### PENDING

Task 已存在，但尚未同时满足“执行授权 + 前置条件”。可存在 taskId、title / objective、Plan / Nodes、Requirement 等初始文档，也可以在创建时保存产品已有的 TaskRoleBinding；但不能开始，也不产生可执行 Node。独立 Task 通过 `authorizeTask` 记录 human authorization；TaskGroup 成员可由已人工授权且 ACTIVE 的 TaskGroup 满足授权门。

### READY

Task 已满足执行授权与前置条件，可以进入执行初始化。`startTask` 前 required TaskRoleBinding 必须补齐；授权本身不等于 Task 已 ACTIVE。

独立 Task：human authorization 由 `authorizeTask` 完成；进入 READY 后不再要求第二次重复人工批准，完成 required Worker provisioning 后即可调用 `startTask`。

属于已人工激活的 TaskGroup：组级人工授权可满足成员 Task 的授权门；后续符合前置条件的 Task 可以由扩展 / 自动化驱动 provisioning 并调用 `startTask`，但 Task Domain 仍是唯一合法性校验者。

### ACTIVE

Task 已真正开始，可以设置 `currentNodeId`、让当前 Node READY，并接受 `startNode / completeNode / waitNode / failNode`。

### WAITING

**业务级整 Task 停止。**

第一版不设计复杂“并行节点还能不能继续”的规则。

规则：

> **只要进入 WAITING，整个 Task 停。**

必须创建待处理 Message、记录 reason、让扩展 / 前端能发现，并等待人工处理。

典型原因：

```text
BUSINESS_CONFIRMATION
ACTION_APPROVAL_REQUIRED
EXECUTION_ALERT
```

### FAILED

表示技术 / 系统执行失败，例如 Execution Browser unavailable、本地服务失败、文件无法写入、Worker 执行异常。

`FAILED` **不是终态**。修复后可以通过受控 reopen / 重试机制继续。

### PAUSED

人工明确暂停 Task。

重要规则：

> **PAUSED 是 Task 级闸门，不要求逐个 Node 改为 PAUSED。**

例如：

```text
Task = PAUSED
Node = IN_PROGRESS
```

此时 Browser Extension 不继续驱动、Worker 不开始新动作、总控不继续推进 Task、写 API 必须拒绝非法推进。

恢复：`PAUSED → ACTIVE`，继续原 `currentNodeId` / 当前 run。

PAUSED 是协作式暂停，不是操作系统进程 kill。已经发出的外部动作可能自然结束，但其后续提交必须重新经过 Task 状态校验。

### SUCCEEDED

第一版完成条件：最后一个有效 Node `SUCCEEDED`，且 Task 当前不存在 `WAITING / FAILED / PAUSED`，然后 Task → SUCCEEDED，`currentNodeId = null`。

终态。

### TERMINATED

中文业务语义统一为“终止”，不使用 CANCELLED 作为主语义。

`Task → TERMINATED` 后不可 resume；后续若还要做，应创建新 Task。

# 3. Node

## 3.1 定义

Node 是 Task Workflow 中的**逻辑工作阶段，同时也是第一版最小可调度工作单元**。

第一版已经明确删除 WorkItem：

```text
Task
  ↓
Node
  ↓
具体 Worker
```

Node 不是人、Agent、Worker、浏览器页面或一次 Tool Execution。Node 代表当前 Task 的一个业务阶段，例如产品设计、研发 + 项管、测试 + 运维、上线验证。

## 3.2 不做并行 Node

第一版不存在并行 Node。即使现实中前端 / 后端可以并行，也统一归入当前复合角色“总控 = 项管 + 研发”的一个研发 Node。未来真实需要多 Worker / 多子工作后再抽 WorkItem / 并行 Node。

## 3.3 Node 状态

第一版：

```text
PENDING
READY
IN_PROGRESS
WAITING
FAILED
SUCCEEDED
TERMINATED
```

**没有 Node PAUSED。** Task PAUSED 控制整体执行。

- `PENDING`：尚未轮到该 Node。
- `READY`：满足条件，可以绑定 Worker 并开始。
- `IN_PROGRESS`：当前 run 已绑定 Worker 并实际处理，但未完成 / 等待 / 失败。它不是“LLM 正在输出 token”。
- `WAITING`：需要人工处理，Node / Task 均进入 WAITING 并创建 PendingMessage。
- `FAILED`：当前 run 技术执行失败，Task 同步 FAILED。
- `SUCCEEDED`：当前 run 正常完成并满足必需输出文档校验。
- `TERMINATED`：Task 终止时尚未完成的 Node 可终止；已 SUCCEEDED 历史不反向改写。

---

# 4. 业务结果“不通过”与技术 FAILED 分开

测试工作正常执行并得到“产品不通过”，不是测试执行失败。

正确理解：

```text
测试执行本身 = 成功
业务结果 = NOT_PASSED
```

后续总控根据正式测试结果决定进入 WAITING 并 reopen 研发。

Execution Browser runtime 根本无法运行、测试脚本未执行、环境损坏等才属于 Node FAILED。

---

# 5. Node runNo

取消 WorkItem 后，每个 Node 使用 `runNo` 表示第几次实际执行。

```text
DEV runNo = 1 → SUCCEEDED
测试不通过 → reopen DEV
DEV runNo = 2 → READY
```

旧 run 不覆盖，由 `node_execution_history` 保存。

---

# 6. Worker 绑定

Node 直接保存：

```text
requiredRoleRef
workerRef
```

`requiredRoleRef` 表示需要哪类 Role；`workerRef` 是 Agent Domain 实际选择的 Worker / Session opaque ref。

Task Domain 不创建 Worker、不维护 Worker Pool、不理解 Conversation URL；但 Task 唯一拥有 TaskRoleBinding，并据此解析 Node run 的 workerRef。

运行中 Node `workerRef` 不可修改。reopen 可清空 run-level workerRef，但 TaskRoleBinding 保留；新 run 默认复用原 Worker，不重新选人。

---

# 7. 为什么没有 Claim

第一版正式删除 Claim。

原来的：

```text
Node → WorkItem → Claim → Worker
```

收敛为：

```text
Node → workerRef
```

`startNode` 原子完成 Task ACTIVE / Node READY / expectedVersion / idempotency 校验，并写 workerRef、startedAt、Node → IN_PROGRESS。

只有未来出现多人抢占、Lease、重新分配、多 Worker 争抢时再设计 Claim。

---

# 8. reopenNode：第一版循环 / 回退机制

第一版不实现通用 Workflow 循环引擎。所有跨 Node 回退使用显式 `reopenNode`。

例：

```text
产品       SUCCEEDED
研发       SUCCEEDED
测试       WAITING
上线       PENDING
```

总控确认后 `reopen 研发`：

```text
研发：runNo + 1，status → READY，workerRef → null
测试：status → PENDING，workerRef → null
上线：PENDING
Task：status → ACTIVE，currentNodeId → 研发
```

Node Execution History、Task Documents、Task Events 全部保留。

原则：`reopen` 只指定回到哪个 Node；之后按正常顺序重新向后推进。不建立自动 Edge 循环。

---

# 9. Node 内部业务循环

产品讨论、方案审计、多轮修改由当前 Worker 在同一个 Node 内完成。Task Domain 不把每次讨论都建成 Node。

---

# 10. Task Document

Task 相关正文属于 Task，不属于 Role 固定 Context。

```text
Requirement
PRD
Technical Design
Test Plan
Test Result
Release Result
```

这些随 taskId 走，不永久写进角色固定 Prompt / Memory。

---

# 11. Node 输入 / 输出文档

Plan 中每个 Node 必须显式声明：

```text
inputDocuments
outputDocuments
```

Worker 不自行遍历目录猜上下文。Task Service 根据 `taskId + nodeId` 组合当前 Node 所需 Markdown 内容。

---

# 12. Node 完成条件

普通 Node 流转没有人工审批。

完成条件：

```text
当前 Worker 正常完成
+
Plan 声明的必需 outputDocuments 均存在
=
Node SUCCEEDED
```

缺输出返回 `NODE_OUTPUT_MISSING`。

人工介入只在 Task / TaskGroup 开始、业务明确需要确认、Action 需要权限、Browser / Execution 明显异常或风险时发生。

---

# 13. Message

第一版 Message 状态只需：

```text
PENDING
ACKNOWLEDGED
```

`acknowledgeMessage` 只表示人已经看过 / 处理待办，不自动推进 Task。后续必须显式 `resumeTask` 或 `reopenNode`。

---

# 14. Event

Event 用于审计、调试、管理后台、问题排查、验收证据；不是当前状态真源。

当前状态必须查询：

```text
tasks
nodes
task_groups
```

# 任务与编排领域｜关键流程与状态转换

---

# 1. 正常 Task 主流程

```text
Task PENDING
   ↓ human authorization（独立 Task；TaskGroup 成员可由已授权 TaskGroup 满足该门）
   ↓ 前置条件满足
Task READY
   ↓ provision / 补齐 required TaskRoleBinding
   ↓ startTask
Task ACTIVE
   ↓
Node-1 READY
   ↓ startNode（Task 自动解析 TaskRoleBinding）
Node-1 IN_PROGRESS
   ↓ completeNode
Node-1 SUCCEEDED
   ↓
Node-2 READY
   ↓
...
最后 Node SUCCEEDED
   ↓
Task SUCCEEDED
```

第一版不引入自动 Graph Engine。下一 Node 按 `sequenceNo + 1`。

---

# 2. createTask

`createTask` 一次完成 Task + planVersion + ordered Nodes + initialDocuments，不拆 `createTask / createPlan / attachPlan`。

**Superseded by ALIGN-071：** 新 Task 统一先进入 PENDING；human authorization 后才可 READY；TaskGroup 前置条件仍由 Task Owner 判定。

---

# 3. startTask

原子效果：

```text
校验 Task == READY
校验 expectedTaskVersion
校验 group eligibility（如有）
校验 required TaskRoleBinding 已补齐

Task READY → ACTIVE
Task.version + 1
Task.startedAt = now

第一个 Node PENDING → READY
Node.version + 1

Task.currentNodeId = firstNodeId

写 Event
写 idempotency record
COMMIT
```

不得出现 Task 已 ACTIVE 但 first Node 仍 PENDING。

---

# 4. startNode

**Superseded by ALIGN-006：** 调用前必须已有 TaskRoleBinding；`startNode` 由 Task 自动解析 requiredRoleRef 对应的 workerRef。

原子效果：

```text
校验 Task == ACTIVE
校验 Node == READY
校验 workerRef 尚未绑定
校验 expectedTaskVersion
校验 expectedNodeVersion
校验 idempotency

Node.workerRef = workerRef
Node.status = IN_PROGRESS
Node.startedAt = now
Node.version + 1

Task.version + 1
NODE_STARTED Event
COMMIT
```

第一版没有 CLAIMED 中间状态。

---

# 5. completeNode

前置：Task ACTIVE、Node IN_PROGRESS、actor / worker 与当前 workerRef 合法、expectedVersion 正确、必需 outputDocuments 已存在。

事务：

```text
保存当前 run 的 execution history
Node → SUCCEEDED
Node.completedAt = now
Node.version + 1

若有下一个 Node：
  next PENDING → READY
  next.version + 1
  Task.currentNodeId = nextNodeId

若无下一个 Node：
  Task → SUCCEEDED
  Task.currentNodeId = null
  Task.completedAt = now

Task.version + 1

NODE_COMPLETED
NODE_READY 或 TASK_SUCCEEDED
idempotency record
COMMIT
```

---

# 6. waitNode

用于业务确认、Action 权限、Browser / Execution 异常或无法安全继续。

请求包含 `waitType / reasonCode / message / relatedRef?`。

效果：

```text
Node → WAITING
Task → WAITING
创建 PendingMessage
写 NODE_WAITING / TASK_WAITING Event
```

整个 Task 停止。

---

# 7. resumeTask

用于 `PAUSED → ACTIVE` 或 `WAITING → ACTIVE`。

若 current Node 是 WAITING：`Node WAITING → IN_PROGRESS`，runNo 和 workerRef 不变。

如果只是 Task PAUSED，Node 状态无需变化。

FAILED 不走普通 resume，优先显式 reopen。

---

# 8. failNode

只用于技术执行失败：

```text
Node → FAILED
Task → FAILED
记录 errorCode / errorMessage / retryable
创建必要 Event / Message
```

不自动重试。修复后 reopen 当前 Node，开始新的 runNo。

---

# 9. pauseTask

```text
Task ACTIVE / WAITING / FAILED
→ PAUSED
```

不逐个修改 Node。

所有执行方下一次推进前必须检查 Task.status。Task PAUSED 时禁止 startNode / completeNode / 新业务推进，扩展停止自动驱动。

---

# 10. terminateTask

```text
Task → TERMINATED
```

未完成 Node 可 TERMINATED；已 SUCCEEDED Node 保留；不可 resume。

---

# 11. reopenNode

例：

```text
1 产品       SUCCEEDED
2 研发       SUCCEEDED
3 测试       WAITING
4 上线       PENDING
```

执行 `reopenNode(node-dev)`：

```text
校验 Task 当前允许 reopen
校验目标 Node 属于当前 Task
校验 expectedTaskVersion

目标 Node:
  runNo + 1
  status = READY
  workerRef = null
  startedAt = null
  completedAt = null
  result / error 清空
  version + 1

所有 sequenceNo > target 的后续 Node:
  status = PENDING
  workerRef = null
  startedAt = null
  completedAt = null
  当前 result / error 清空
  version + 1

Task:
  status = ACTIVE
  currentNodeId = target
  version + 1

旧 history / document / event 全保留
NODE_REOPENED Event
COMMIT
```

原则：reopen 点以前 Node 保持已完成；reopen Node READY 新 run；之后 Node PENDING 等待重新经过。

---

# 12. 为什么不做通用循环

若直接允许 TEST → DEV → TEST → DEV，会立即引入循环计数、退出条件、旧 Node 状态、多轮 Artifact、死循环、自动回边、恢复点等复杂度。

第一版：跨 Node 回退 = `reopenNode`；Node 内多轮业务讨论 = Worker 自己处理。

---

# 13. 测试不通过推荐流程

```text
研发 Node SUCCEEDED
        ↓
测试 Node IN_PROGRESS
        ↓
测试工作执行成功
        ↓
写 test-result.md
业务结果 = NOT_PASSED
        ↓
waitNode(BUSINESS_CONFIRMATION, TEST_NOT_PASSED)
        ↓
Task WAITING
        ↓
总控读取测试结果
        ↓
人工 / 总控确认
        ↓
acknowledgeMessage
        ↓
reopenNode(研发)
        ↓
研发 runNo + 1
        ↓
重新向后推进
```

`TEST_NOT_PASSED != Node FAILED`。

---

# 14. Action 权限 / Browser 异常

```text
Execution / Browser detects approval required
        ↓
waitNode(ACTION_APPROVAL_REQUIRED)
        ↓
Task / Node WAITING
        ↓
PendingMessage
        ↓
人工处理真正权限 / Approval
        ↓
acknowledgeMessage
        ↓
resumeTask
```

Task Domain 不拥有真正 Approval Grant，只保存“当前 Task 被什么原因阻塞”。

---

# 15. TaskGroup / 一夜迭代

```text
TaskGroup READY
    ↓ 人工一次明确启动
TaskGroup ACTIVE

Task-01 READY
    ↓ startTask
ACTIVE → ... → SUCCEEDED

Task-02:
前序满足 → READY
扩展 / 自动化可继续调用 startTask

若任一 Task:
WAITING / FAILED / PAUSED
→ 整条链不继续释放后续 Task
→ 等人工处理
```

Task Domain 只负责 eligibility / status / sequence / maxActiveTasks，不负责打开浏览器或启动 GPT Conversation。

## 6.1A authorizeTask

用途：记录独立 Task 的 human execution authorization，使 Task 在前置条件满足后具备进入 READY 的资格。已由人工启动的 TaskGroup 可以作为其成员 Task 的 authorization source，不要求用户逐 Task 重复点击批准。

请求：

```json
{
  "taskId": "task-001",
  "expectedTaskVersion": 1,
  "actorRef": "human:operator",
  "idempotencyKey": "idem:authorize-task-001"
}
```

语义：

- 只由 Task Domain 修改授权事实；不创建独立 Approval entity/table；
- 写入 `authorizedByRef / authorizedAt`（TaskGroup 成员若使用 group-level authorization，可由 Task Owner 依据 ACTIVE TaskGroup 判定授权已满足）；
- 若授权与 Task 前置条件均已满足，则 `PENDING → READY`；否则保持 `PENDING`，待前置条件满足后由 Task Owner 计算 READY；
- 同一幂等意图重复提交返回原结果；version conflict 必须重新读取后再决定；
- authorization 只允许 Task 进入执行初始化，**不等于**任何 Execution Effect Approval。

响应：

```json
{
  "taskId": "task-001",
  "status": "READY",
  "version": 2,
  "authorizedByRef": "human:operator",
  "authorizedAt": "2026-08-12T00:00:00.000Z"
}
```

## 6.1B bindTaskWorker

用途：把 Agent 已校验的 Worker identity 固化为 Task Owner 的稳定 `TaskRoleBinding`。真实 Conversation CREATE/RESTORE 由 Execution Browser 完成，Agent 只拥有/校验 Worker identity；两者都不能直接写 Task binding。

请求：

```json
{
  "taskId": "task-001",
  "roleRef": "role:controller-dev",
  "workerRef": "worker:conversation:bbb",
  "expectedTaskVersion": 2,
  "actorRef": "platform-host:worker-provisioning",
  "idempotencyKey": "idem:bind-task-001-controller-dev"
}
```

语义：

- `(taskId, roleRef)` one-time + idempotent；
- 空 binding 可写入；同 workerRef 重放返回原结果；
- 尝试覆盖为不同 workerRef 返回 `TASK_ROLE_BINDING_CONFLICT`；
- roleRef 必须已属于该 Task 的 required/declared roles，否则拒绝；
- terminal Task 默认拒绝修改；
- reopen 不删除 TaskRoleBinding。

响应：

```json
{
  "taskId": "task-001",
  "version": 3,
  "roleBinding": {
    "roleRef": "role:controller-dev",
    "workerRef": "worker:conversation:bbb"
  }
}
```

# 2. task_groups

```sql

  task_group_id       TEXT PRIMARY KEY,

  objective           TEXT,
```

| 字段 | 含义 |
|---|---|
| `task_group_id` | TaskGroup ID |

| `objective` | 总体目标 |
| `status` | READY / ACTIVE / SUCCEEDED |
| `max_active_tasks` | v1 = 1 |
| `version` | 乐观并发版本 |
| `created_by_ref` | 创建主体 opaque ref |
| `created_at` | 创建时间 |
| `updated_at` | 最近业务修改时间 |

# 3. tasks

```sql
CREATE TABLE tasks (
  task_id             TEXT PRIMARY KEY,
  task_group_id       TEXT,
  sequence_no         INTEGER,
  title               TEXT NOT NULL,
  objective           TEXT NOT NULL,
  status              TEXT NOT NULL,
  version             INTEGER NOT NULL DEFAULT 1,
  plan_version        INTEGER NOT NULL DEFAULT 1,
  current_node_id     TEXT,
  created_by_ref      TEXT NOT NULL,
  authorized_by_ref   TEXT,
  authorized_at       TEXT,
  created_at          TEXT NOT NULL,
  started_at          TEXT,
  completed_at        TEXT,
  updated_at          TEXT NOT NULL,
  FOREIGN KEY (task_group_id)
    REFERENCES task_groups(task_group_id)
);
```

| 字段 | 含义 |
|---|---|
| `task_id` | Task ID |
| `task_group_id` | 可选 TaskGroup |
| `sequence_no` | TaskGroup 中顺序 |
| `title` | 任务名称 |
| `objective` | 任务目标 |
| `status` | TaskStatus |
| `version` | Task 乐观并发版本 |
| `plan_version` | 当前 Plan version；v1 通常为 1 |
| `current_node_id` | 当前流程位置 |
| `created_by_ref` | 创建者 |

| `authorized_at` | 独立 Task execution authorization 时间；不是 Execution Effect Approval |
| `started_at` | 首次 ACTIVE |
| `completed_at` | SUCCEEDED / TERMINATED 时间 |
| `updated_at` | 最近修改 |

v1 不单独建 `plans` 表。

# 4. nodes

```sql
CREATE TABLE nodes (
  node_id               TEXT PRIMARY KEY,
  task_id               TEXT NOT NULL,
  sequence_no           INTEGER NOT NULL,
  title                 TEXT NOT NULL,
  objective             TEXT NOT NULL,
  status                TEXT NOT NULL,
  version               INTEGER NOT NULL DEFAULT 1,
  run_no                INTEGER NOT NULL DEFAULT 1,
  required_role_ref     TEXT NOT NULL,
  worker_ref            TEXT,
  input_documents_json  TEXT NOT NULL DEFAULT '[]',
  output_documents_json TEXT NOT NULL DEFAULT '[]',

  error_code            TEXT,

  error_retryable       INTEGER,
```

# 任务与编排领域｜Transaction / Version / Idempotency / Recovery

---

# 1. 总原则

第一版只坚持四条：

```text
1. SQLite 状态变化必须 transaction
2. Task / Node / Group 使用 expectedVersion 防旧写
3. 重要写操作使用 idempotencyKey + requestHash
4. Markdown + SQLite 不伪装成分布式事务，采用安全文件写 + 可恢复索引同步
```

---

# 2. Version

对象：

```text
Task.version
Node.version
TaskGroup.version
```

规则：只要对象业务状态被修改，version + 1。

调用方使用最后读到的 `expectedTaskVersion / expectedNodeVersion / expectedGroupVersion`。版本不匹配返回稳定冲突错误，不自动覆盖。

---

# 3. 为什么 Task 和 Node 都需要 version

例：

```text
总控读取：Task v10 / Node v4
扩展启动 Node：Task → v11 / Node → v5
旧总控继续提交：expectedTaskVersion=10 / expectedNodeVersion=4
```

必须失败，防止旧 GPT Conversation、旧 Browser page、重复 Action、延迟响应覆盖新状态。

---

# 4. startTask transaction

```text
检查 idempotency
校验 Task READY
校验 expectedTaskVersion
校验 TaskGroup eligibility（如有）

Task READY → ACTIVE
Task.version + 1
Task.startedAt = now

first Node PENDING → READY
Node.version + 1

Task.currentNodeId = firstNodeId

append Events
save idempotency response
COMMIT
```

---

# 5. startNode transaction

```text
检查 idempotency
校验 Task ACTIVE
校验 Node READY
校验 workerRef null
校验 expectedTaskVersion
校验 expectedNodeVersion

Node.workerRef = request.workerRef
Node.status = IN_PROGRESS
Node.startedAt = now
Node.version + 1

Task.version + 1

append NODE_STARTED
save idempotency response
COMMIT
```

可使用条件 UPDATE：

```sql
UPDATE nodes
SET
  status = 'IN_PROGRESS',
  worker_ref = ?,
  started_at = ?,
  version = version + 1
WHERE node_id = ?
  AND status = 'READY'
  AND version = ?;
```

要求 `changes == 1`。

---

# 6. completeNode transaction

先由 TaskDocumentService 校验 required outputDocuments 全部存在、hash / index 合法。

事务：

```text
check idempotency
validate Task ACTIVE
validate Node IN_PROGRESS
validate worker / actor
validate expected versions
snapshot current run history
Node → SUCCEEDED
completedAt = now
Node.version + 1

if next node:
    next → READY
    next.version + 1
    Task.currentNodeId = next
else:
    Task → SUCCEEDED
    Task.currentNodeId = null
    Task.completedAt = now

Task.version + 1
append events
save idempotency response
COMMIT
```

---

# 7. reopenNode transaction

```text
check idempotency
validate Task
validate target Node
validate expectedTaskVersion
需要时先保存将被重置的当前 run 历史

target Node:
  runNo + 1
  READY
  workerRef null
  result/error null
  startedAt/completedAt null
  version + 1

all later Nodes:
  PENDING
  workerRef null
  result/error null
  startedAt/completedAt null
  version + 1

Task:
  ACTIVE
  currentNodeId = target
  version + 1

append NODE_REOPENED
save idempotency response
COMMIT
```

不得删除 node_execution_history / task_documents / task_events。

---

# 8. Idempotency

保存：

```text
idempotencyKey
operation
requestHash
responseJson
```

重复规则：

```text
same key + same semantic request
→ return stored response

same key + different semantic request
→ IDEMPOTENCY_CONFLICT
```

---

# 9. requestHash

只包含影响业务语义的规范化字段。

例如 startNode：

```text
taskId
nodeId
workerRef
expectedTaskVersion
expectedNodeVersion
```

不加入 traceId / HTTP header / 传输 timestamp / 随机 request id。

---

# 10. 不使用 Lease / Lock Table

第一版没有 distributed lock / lease token / claim token / lock table。

依赖 SQLite transaction + version check + conditional UPDATE，满足当前单机第一版。

---

# 11. putTaskDocument：跨 SQLite + FileSystem

文件系统和 SQLite 不是一个 ACID transaction。第一版不引入两阶段提交 / 分布式事务。

推荐：

```text
1. 校验 task / node / documentType / expectedVersion
2. 计算安全目标路径
3. 写临时文件
4. fsync / close（按实现能力）
5. atomic rename 到正式 Markdown
6. 计算 contentHash
7. SQLite transaction:
   - upsert task_documents
   - Task.version + 1（按最终契约）
   - DOCUMENT_UPDATED Event
   - idempotency record
8. COMMIT
```

---

# 12. Reconciliation

若文件已写成功但 SQLite 更新失败，不为此引入复杂 transaction manager。

TaskDocumentService 提供内部 `reconcileDocumentIndex()`，按 file exists / content hash / taskId / documentType 修复索引。

---

# 13. Crash / Recovery 最低测试

必须至少覆盖：

```text
startTask transaction 中途失败 → 无半状态
startNode double submit → exactly one effective
completeNode double submit → one completion
reopenNode 中途失败 → 不出现部分 reset
same idempotency key same request → same response
same key different request → conflict
stale expectedVersion → zero side effect
document file written + DB failure → reconcile 可恢复
SQLite restart → 状态可读
WAL restart → integrity PASS
```

---

# 14. Blind Retry

Phase 2 已证明：不确定副作用不得盲目重试。

Task Domain 自己没有 Browser / Shell Delivery 语义，但 API 必须允许 Execution Domain 在结果不确定时将 Task 放入 WAITING，而不是自动重跑业务 Node。

# 任务与编排领域｜Service 与 npm 模块设计

---

# 1. 运行时原则

第一版：

> **3 个逻辑 Service，1 个领域业务 npm 包；模块化不等于多进程。**

Task Domain 可以被现有 Gateway / Runtime in-process 加载。未来若需要独立 HTTP service，可复用相同 Public Contract 和 Service 层。

---

# 2. 3 个逻辑 Service

```text
TaskCommandService
TaskQueryService
TaskDocumentService
```

由 `@ai-agent-platform/task-orchestration` 统一提供。

---

# 3. TaskCommandService

负责写业务动作：

```text
createTaskGroup
startTaskGroup
createTask
authorizeTask
bindTaskWorker
startTask
pauseTask
resumeTask
terminateTask
startNode
completeNode
waitNode
failNode
reopenNode
acknowledgeMessage
```

职责：读取当前状态、校验 expectedVersion、校验状态转换、检查 idempotency、开启 transaction、修改 Task / Node / Group、写 Message / Event、保存幂等响应并 commit。

不负责选择 Worker、模型推理、Browser 操作、Shell、判断测试结果业务好坏、决定用户是否应该批准。

---

# 4. TaskQueryService

只读：

```text
getTaskGroup
listTasks
getTask
getNodeContext
listPendingMessages
listTaskEvents
```

默认不修改业务状态。

`getNodeContext` 组合 Task + Node + inputDocuments + TaskDocumentService 读取的 Markdown。Worker 不直接访问 SQLite。

---

# 5. TaskDocumentService

Public：

```text
putTaskDocument
getTaskDocument
```

Internal：

```text
readDocumentsForNode
verifyRequiredOutputs
resolveDocumentPath
reconcileDocumentIndex
```

职责：safe path、Markdown read/write、atomic replace、content hash、document index、required output verification、reconciliation。

# 6. npm 包边界

第一版 3 个 npm 包：

```text
@ai-agent-platform/task-orchestration
@ai-agent-platform/task-store-sqlite
@ai-agent-platform/task-migration-runner
```

---

# 7. @ai-agent-platform/task-orchestration

领域业务包，拥有：

```text

Task / Node / TaskGroup 状态规则
Public Contracts
JSON Schemas（或其领域定义）
TaskCommandService
TaskQueryService
TaskDocumentService ports
Domain Errors
```

不写具体 SQLite SQL。

```text
src/
├── contracts/
├── domain/
├── services/
│   ├── task-command-service.ts
│   ├── task-query-service.ts
│   └── task-document-service.ts
├── ports/
└── index.ts
```

目录名是实现建议，不等于现在冻结目标仓库物理布局。

---

# 8. @ai-agent-platform/task-store-sqlite

任务领域 SQLite Adapter 包，拥有：

```text
SQLite connection lifecycle
transaction abstraction
TaskGroupRepository
TaskRepository
NodeRepository
NodeExecutionHistoryRepository
TaskDocumentRepository
TaskMessageRepository
TaskEventRepository
IdempotencyRepository
Task schema
Task migrations SQL
```

重要：Task / Node / Event / Idempotency 必须能够共享同一个 SQLite transaction。

---

# 9. Event Store 为什么不拆包

第一版 `TaskEventRepository` 明显仍属于 Task Domain。当前事件依赖 taskId / nodeId / taskVersion / nodeVersion，没有第二个领域真实共用。

因此 v1 不创建 `@ai-agent-platform/event-store`。

未来只有 Task / Agent / Execution / Deployment 等多个领域确实需要共同 append-only Event Journal 时，再抽公共包。

---

# 10. @ai-agent-platform/task-migration-runner

迁移执行包。

为什么带 `task-` 前缀：当前只有 Task Domain 一个真实消费者，不提前创建平台公共抽象。

职责：discover migrations、parse version / name、read schema_migrations、sort pending migrations、execute migration transaction、record applied migration。

它不拥有具体 Task SQL。

---

# 11. Migration 归属规则

原则：

> **谁拥有 schema，谁拥有 migration。**

所以 Task migration SQL 由 `task-store-sqlite` 维护；`task-migration-runner` 只负责执行。

未来多个领域真实复用后，再考虑抽 `@ai-agent-platform/migration-runner`。

---

# 12. Service / Package / Process 三层不能混

```text
Service = 逻辑业务能力
npm Package = 软件交付 / 模块边界
Process = 运行部署单元
```

第一版：3 logical services、3 npm packages、不要求 3 个 daemon。

当前优先：

```text
Gateway / Runtime process
    ↓
load task-orchestration
    ↓
task-store-sqlite
    ↓
SQLite / Markdown
```

---

# 13. Module 生命周期

具体模块部署行为必须遵循当前 Deployment Domain 的正式 Deployment Contract。

Task 侧至少需要机器可管理的生命周期能力，例如 describe / preflight / start / stop / status / verify / doctor；具体 install / configure / dependency planning 由 Deployment Domain 当前正式模型裁决，Task Domain 不自行建立第二套部署编排。

---

# 14. Provides

任务与编排领域对外提供：

```text
TaskGroup lifecycle
Task lifecycle
Node lifecycle
Node context
Task document access
Pending Message query / ack
Task Event query
```

---

# 15. Requires

业务层不直接依赖 Agent / Execution / Model / Deployment 内部实现，只接受 opaque refs。

基础运行依赖：Node.js runtime、filesystem、SQLite、Git repository workspace、clock、ID generator、hash function。

---

# 16. 明确禁止

```text
task-orchestration import Agent internal implementation
task-store-sqlite 读取其他领域数据库
Task Service 直接操作 Browser DOM
Task Service 直接调用模型
Task Service 直接执行 Shell
Task Migration Runner 拥有跨领域 migration SQL
```

# 任务与编排领域｜存储、Git 与 Task Document

---

# 1. 统一仓库模型

不区分“用户模式 / 开发者模式”两套架构。

统一：

> **目标 Git 仓库是平台部署与工作的根。**

当前实际源码仓库：

```text
/Users/agent/Desktop/ai-agent-platform
```

这是当前开发位置事实，不形成特殊领域语义。

平台可以迭代一个产品、多个产品、多个模块或平台自己；产品数量与 Task Domain 目录模型无关。

---

# 2. 根目录职责

目标仓库根主要承担：

```text
1. package.json / lockfile 声明平台 npm 部署依赖
2. 保存被平台迭代产生 / 修改的真实产品产物
```

平台自己的工作数据统一进入：

```text
.ai-agent-platform/**
```

原则：除必要的 npm manifest / lock 与真实产品产物，平台自身不应在目标根目录散落新的专有工作目录。

---

# 3. .ai-agent-platform

`.ai-agent-platform/` 是平台唯一专有工作目录命名空间。

Task Domain 的平台工作数据包括 Task Markdown、Task SQLite、Task logs、Task temp/cache、Task domain config（若属于平台运行配置）。具体子目录最终由实现 / Deployment Contract 固化，但必须位于该命名空间。

---

# 4. Git tracked 与 gitignored

`.ai-agent-platform` 不能整体忽略，因为里面既有正式 Markdown 工作产物，也有运行时数据库。

Git tracked：Requirement / PRD / Technical Design / Test Plan / Test Result / Release Result 等 Task Markdown。

Git ignored：SQLite db、WAL / SHM、lock、cache、tmp、默认 logs、可重建索引。

---

# 5. 数据职责

一句话：

> **Git / Markdown 管任务正文历史；SQLite 管机器状态与索引。**

SQLite 保存 taskId、TaskGroup、Task status/version、currentNodeId、nodeId、Node status/version/runNo、requiredRoleRef、workerRef、TaskDocument path/hash、Event、Message、Idempotency、Execution History metadata。

Markdown 保存 Requirement / PRD / Technical Design / Test Plan / Test Result / Release Result 等 Task-scoped 正文。

---

# 6. 为什么正文不进 SQLite

第一版正文天然适合 Markdown + Git diff + Git history + 人工审阅 + Agent 读取。

SQLite 只保存当前索引，不重复维护 DB TEXT copy + Markdown copy，避免正文双真源。

---

# 7. TaskDocument 逻辑模型

```text
taskId
documentType
sourceNodeId?
filePath
contentHash
updatedByRef
updatedAt
```

v1 同 taskId + documentType 一个当前文件；历史走 Git commit history。

---

# 8. documentType

第一版至少：

```text
REQUIREMENT
PRD
TECHNICAL_DESIGN
TEST_PLAN
TEST_RESULT
RELEASE_RESULT
```

Plan 使用逻辑类型，不写实际文件路径。

---

# 9. Node Context

Node 声明 inputDocuments / outputDocuments。Worker 调 `getNodeContext(taskId, nodeId)`；Task Service 查 Task / Node → 读取声明 → 查 task_documents → 安全读取 Markdown → 组合 response。

Worker 不自己扫描 `.ai-agent-platform`。

---

# 10. 写文档

Worker 调：

```text
putTaskDocument(taskId, nodeId, documentType, content)
```

不允许传绝对路径、`../` 等任意 target path。TaskDocumentService 自己映射安全相对路径。

---

# 11. Node 完成文档门禁

completeNode 前，对 Node.outputDocuments 中每种文档类型检查当前 TaskDocument 索引存在、实际文件存在、hash / index 合法。

否则返回 `NODE_OUTPUT_MISSING` 或 `DOCUMENT_INDEX_MISMATCH`。

---

# 12. Git 历史

第一版不建立 TaskDocumentVersion table / Artifact revision service / Versioned blob store。

未来只有 API 真正需要读取历史文档版本、跨 Task 对比、Knowledge retrieval 时再扩展。

---

# 13. .codegraph

第三方 CodeGraph 的 `.codegraph/codegraph.db` 属于代码知识图谱可重建索引，可以帮助研发 Agent 查询代码结构，但绝不能保存 taskId / Task status / Node status / Task Event / Task Document truth。

CodeGraph 不是 Task Domain 真源。

---

# 14. CodeGraph 未来归属

若后续采用，更适合归入智能体运行与协作领域 / 研发工具能力；若未来采用 MCP，也只能是 future / non-v1 adapter/tool 形态。Task Domain 不直接依赖。

---

# 15. 当前 ai-agent-platform 自举

当前 `/Users/agent/Desktop/ai-agent-platform` 既是现阶段源码所在 Git 仓库，也是未来 Task Domain 完成后可以拿来真实 dogfooding 的目标仓库。

Phase 3 正式技术方案仍写入当前源码目录正常的 `docs/technical/技术方案/第三阶段/**`；Task Runtime 运行中产生的 Task-scoped working documents / state 遵循 `.ai-agent-platform/**`。

# 任务与编排领域｜设计决策记录与明确非目标

> 用途：防止后续 Chat / 实现者把已经否决的设计重新带回来。

---

# 1. 设计方法

用户明确要求：第一版满足真实需求即可、不要过度设计、时间有限、避免 Phase 2 式反复返工。

任何新增实体 / 状态 / 服务 / 包都必须回答：

> 当前第一版哪个真实需求没有它就无法完成？

答不出来，则不加入。

---

# 2. 已确认：领域独立但载体无关

Task Domain 有自己的状态 / API / Service / Store，但只通过 opaque refs 对接 Agent / Execution。当前 Custom GPT / Conversation 只是 Agent Domain 的一种载体，Task Domain 不依赖 ChatGPT URL 格式。

---

# 3. 已确认：Role 与 Worker 分开

```text
Role = 资格 / 角色要求
Worker = 具体 Custom GPT Conversation / 执行实例；`Session` 仅是历史或外部运行时措辞，不建立 Agent Session business entity
```

Task Node 保存 `requiredRoleRef / workerRef`。Role 不是全局锁。

---

# 4. 已确认：Task Context 与 Role 固定 Context 分开

Role 固定 Context 是职责 / 方法 / 系统提示 / 工作规范；Task Context 是 Requirement / PRD / Technical Design / Test Plan / Test Result。Task 文档随 taskId 走，不写进 Role 长期 Memory。

---

# 5. 已删除：WorkItem

曾考虑 `Node → WorkItem → Claim`，已明确删除。

原因：串行 Node、单 Node 单具体 Worker、没有 Node 并行、没有 reassign、没有 worker queue。

未来触发条件：一个 Node 同时拆多个真实子工作、一个 Node 多 Worker 并行、独立工作队列、复杂 retry/lease。

---

# 6. 已删除：Claim

第一版没有 Claim entity / table / state / API。`startNode` 原子绑定 workerRef。

未来出现抢占 / Lease / 重新分配 / 多 Worker 争抢再设计。

---

# 7. 已删除：并行 Node

第一版 Workflow 是有序串行 Node。现实前端 / 后端并行仍归“研发 + 项管”一个 Node。未来真实需要多 Worker 并行再升级。

---

# 8. 已删除：通用循环引擎

不做 A → B → C → A 静态回边 / 自动无限循环。替代机制是 `reopenNode`；Node 内业务多轮讨论由 Worker 自己处理。

---

# 9. 已确认：reopen

reopen 前序 Node：target runNo + 1、target READY、target workerRef null；later Nodes PENDING / workerRef null；history preserved；documents preserved；Task ACTIVE；currentNodeId = target。

这是第一版流程回退唯一正式机制。

---

# 10. 已确认：PAUSED 只在 Task 层

不逐个 Node IN_PROGRESS → PAUSED。Task PAUSED 是全局协作闸门，Node 保持当前状态。

---

# 11. 已确认：WAITING 是整 Task 停

任何 WAITING 都使 Node WAITING + Task WAITING + Message required。

---

# 12. 已确认：FAILED 可恢复

FAILED != TERMINATED。技术失败修复后可以 reopen。

---

# 13. 已确认：终止

统一中文“终止”，技术 enum `TERMINATED`，不使用 CANCELLED 作为主语义。终止不可恢复。

---

# 14. 已确认：普通 Node 没有审批

Worker 完成 + required output docs 存在 → SUCCEEDED → next READY。

人工介入只在 Task / TaskGroup start、业务明确确认、Action permission、Browser / Execution abnormal / risk。

---

# 15. 已确认：Markdown + Git

Task 文档正文 = Markdown / Git history；SQLite = 状态 / 索引 / path / hash。不建立 DB 正文副本。

---

# 16. 已确认：平台专有工作目录

平台自己的 Task working documents / state / logs / cache 等统一收敛在 `.ai-agent-platform/**`。目标仓库可以迭代一个或多个产品，与 Task Domain 方案无关。

---

# 17. 已确认：CodeGraph 不是业务存储

`.codegraph/codegraph.db` 是可重建代码索引，不是 Task DB。

---

# 18. 已确认：SQLite

第一版 SQLite + sqlite3@6.x + raw SQL + WAL。不使用 PostgreSQL / Redis / ORM / Kysely / Drizzle / Prisma。

原因：老 Mac、Node 20、少 daemon、低运维成本、当前表数量小。

---

# 19. 已确认：不用 XState / Temporal / DBOS

当前状态机足够简单。未来出现复杂 DAG / durable distributed workflow / multi-host scheduler 再评估。

---

# 20. 已确认：Event Store 不独立

TaskEventRepository 暂时属于 `@ai-agent-platform/task-store-sqlite`。未来多个领域真实共享 append-only journal 后再抽。

---

# 21. 已确认：Migration 包带 task 前缀

当前 `@ai-agent-platform/task-migration-runner`，不是 `@ai-agent-platform/migration-runner`。没有第二个真实消费者，不提前抽公共包。

---

# 22. 当前 3 npm 包

```text
@ai-agent-platform/task-orchestration
@ai-agent-platform/task-store-sqlite
@ai-agent-platform/task-migration-runner
```

---

# 23. 当前 3 Service

```text
TaskCommandService
TaskQueryService
TaskDocumentService
```

一个领域业务 npm 包承载。

---

# 24. 仍留给后续实现细化

以下不是重新讨论领域模型的问题：最终 HTTP path、具体 class / function 文件名、完整 Error Code 枚举、日志格式、具体 config key 名、SQLite driver wrapper 细节、Migration filename convention、测试文件目录、具体 `.ai-agent-platform` 子目录名。

只要不改变本文语义，可在实现时决定并回写文档。

---

# 25. 升级触发器

| 真实需求 | 再考虑 |
|---|---|
| Node 多 Worker 并行 | WorkItem / parallel node |
| Worker 抢占 / Lease | Claim |
| 动态图 / 条件边 | DAG / Edge Engine |
| 自动复杂回环 | Loop Engine |
| 多机调度 | Queue / Scheduler / PostgreSQL |
| 多领域 Event Journal | 公共 Event Store |
| 多领域 migration 共用 | 公共 migration-runner |
| 文档跨 Task 检索 / embedding | 知识与检索领域 |
| API 读取历史文档版本 | Document version service |

没有触发器，不提前实现。

# 任务与编排领域｜技术选型调研与取舍

> 本文记录“为什么选当前方案”，避免后续在没有新需求的情况下重复横向选型。

---

# 1. 本机硬约束

当前真实开发环境：

```text
MacBook Pro 2017 Intel
8GB RAM
macOS Ventura 13.7.8
Node 20.20.1
npm 10.8.2
```

因此第一版技术选型优先：

```text
少常驻进程
少外部基础设施
无需 Docker
无需 Redis
无需独立数据库 Server
Node 20 可直接运行
TypeScript 主栈
```

---

# 2. SQLite：选择

选择原因：

```text
单机第一版足够
无独立 Server
事务满足 Task/Node 强一致
适合 repo-local state
低内存 / 低运维
可直接备份 / 诊断
```

第一版：

```text
SQLite + WAL + foreign_keys
```

---

# 3. PostgreSQL：不选第一版

PostgreSQL 对复杂关系、并发和未来多机很好，但当前会增加：数据库服务安装、启动、账号 / 端口 / 数据目录管理、额外 daemon 和部署复杂度。

当前没有多机 Task scheduler / 高并发需求，所以不进入 v1。

未来触发：

```text
多进程高并发
多机调度
SQLite 写并发成为真实瓶颈
跨实例共享 Task truth
```

再评估。

---

# 4. sqlite3@6.x：选择

目标是保持 Node 20 基线，不为了 driver 升级整个 Runtime。

实现前必须在当前 Intel Mac 做真实安装 Spike：open DB / transaction / WAL / restart PASS 后冻结。

---

# 5. better-sqlite3：当前不选

讨论时最新版 Node 要求与当前 Node 20 基线不匹配；锁旧版虽然可能可用，但会主动制造版本债。

没有性能证据要求它，因此第一版不选。

---

# 6. ORM / Query Builder：不选第一版

评估过 Kysely / Drizzle 等方向。

当前只有约 8 张业务表，SQL 简单、事务语义重要。

选择：

```text
Repository Ports
+
raw SQL implementation
```

不是让业务 Service 到处散 SQL。

未来真实出现几十张表 / 复杂查询 / SQL 重复维护成本后再评估。

---

# 7. XState：不选第一版

XState 适合状态机表达，但当前 v1 已收敛为简单状态 + 显式领域动作：

```text
start
complete
wait
fail
pause
resume
reopen
terminate
```

直接 TypeScript `assertTransitionAllowed()` 更透明。

未来复杂 DAG / 并行 / statechart 需求真实出现再评估。

---

# 8. DBOS：不选第一版

DBOS TypeScript 的 durable execution / Postgres workflow 思路有参考价值，但当前：

```text
Task 是业务状态真源
Workflow 是数据定义的有序 Node
Agent / Extension 外部驱动
本机要求极轻
```

引入 DBOS 会增加运行模型重叠，v1 不需要。

---

# 9. Temporal：不选第一版

Temporal 对 durable workflow 非常成熟，但需要独立 Runtime / Service 体系，当前单机第一版明显过重。

保留其 Workflow vs Activity 的领域边界启发，不复用其运行基础设施。

---

# 10. BullMQ / Redis：不选

当前没有独立异步 Worker Queue 真实需求；BullMQ 会引入 Redis。

Node 由扩展 / Agent 明确驱动，不需要先建立队列。

---

# 11. pg-boss / Graphile Worker：不选当前版本

Postgres-backed queue 思路有价值，但仍要求 PostgreSQL，并且调研时最新 Node 要求与当前 Node 20 基线不友好。

当前没有队列需求，因此不为它改变基础架构。

---

# 12. Trigger.dev / Vercel Workflow：参考，不嵌入

它们对 Run / Attempt / Wait / Durable Workflow 有参考价值，但主要偏 code-defined workflow / 平台运行时。

本项目 v1 的 Plan 是 Task-owned data-defined ordered Nodes，且大量推进由 Agent / Extension 通过 Public API 驱动，因此只借鉴概念，不嵌入。

---

# 13. Hatchet 等独立工作流服务：不选

会引入额外服务 / 非 TypeScript 主 Runtime / 运维复杂度，当前无必要。

---

# 14. Ajv：选择

公共 Contract 使用 JSON Schema，Ajv 做运行时输入输出验证。

用于：

```text
CreateTaskRequest
StartNodeRequest
CompleteNodeRequest
WaitNodeRequest
ReopenNodeRequest
Error Envelope
Event payload basic shape
```

Schema 是公共契约的一部分，不让 TypeScript 类型成为唯一运行时保障。

---

# 15. 原生 Node HTTP / 现有 Gateway：继续使用

当前仓库已有 Gateway / Runtime HTTP 运行形态。

第一版 Task Domain 不为了 HTTP 再加 Express / Fastify。

Task Domain 先是稳定 Service + Contract；HTTP 是 Adapter。

---

# 16. Git / Markdown：选择

Requirement / PRD / 技术方案 / 测试结果天然需要：

```text
人可读
AI 可读
Git diff
Git history
仓库统一管理
```

所以正文使用 Markdown，数据库只管索引和运行事实。

---

# 17. CodeGraph：可选研发工具，不是 Task 存储

若未来安装 CodeGraph，可用于研发 Agent 做代码结构 / 调用图查询。

其 `.codegraph` 数据是可重建索引，不属于 Task Domain 业务真源。

---

# 18. 当前冻结技术组合

```text
Node 20
TypeScript
npm / workspaces
SQLite
sqlite3@6.x
raw SQL
JSON Schema + Ajv
现有 Node HTTP / Gateway adapter
Markdown + Git
node:test（沿用仓库测试基线）
```

没有新真实需求，不重新横向选型。

# 任务与编排领域｜上下文继承与跨领域边界

> 本文保存本轮讨论中对后续 Agent / Execution 领域非常关键、但不应被误写进 Task Domain 内部实现的上下文。

---

# 1. Phase 2 是证据，不是 Phase 3 依赖

Phase 2 已证明 Task / Controller / Browser / Local / Approval / Delivery 能真实串联。

Phase 3 可以重写实现，但不能丢掉已验证的重要语义：

```text
opaque refs
idempotency 绑定请求语义
Business Wait != Execution side-effect / recovery state（`Execution Lease` 仅为 Phase2 historical term）
Delivery 是不可逆事实边界
Human Approval 是协议事件
OBSERVE != MUTATE
未知副作用不得盲目重试
Evidence / Result 可追踪
Execution Browser 不拥有 Task Workflow（`Browser Host` 为 Phase2 historical naming）
```

本 Task v1 已把其中属于任务领域的部分保留为：

```text
opaque role/worker/actor refs
expectedVersion
idempotencyKey + requestHash
WAITING
Event / Message
明确的 Task / Node 当前状态真源
```

真实 Delivery / Effect Approval / Evidence / UNKNOWN recovery 等继续由执行领域拥有；`Execution Lease` 不属于 Phase3 v1。

---

# 2. 当前 Custom GPT 载体观察

当前实际使用中，一个 Custom GPT 基础 `g-...` 可以被 Agent Domain 视作某种 Role / Worker Definition 外部载体；其多个 `/c/<conversationId>` Conversation 可以被 Agent Domain 视作具体 Worker / Conversation 外部载体（`Session` 不是 Agent business entity）。

例如逻辑关系：

```text
Custom GPT definition
→ Role / WorkerDefinition external carrier

Conversation
→ concrete Worker / Conversation external carrier（Session = external wording only）
```

**这不是 Task Domain Contract。**

Task Domain 只看到：

```text
requiredRoleRef
workerRef
```

未来 Custom GPT 被自建 Agent Runtime 替换，Task API 不变。

---

# 3. 三个第一版复合角色

当前业务验证使用：

```text
1. 运营 + 产品经理
2. 总控 = 项目管理 + 研发
3. 测试 + 运维
```

这些角色的职责和固定 Context 归智能体运行与协作领域。

Task Node 只引用 `requiredRoleRef`。

---

# 4. 用户批准需求后的 Task 创建

目标业务流程：

```text
运营 / 产品与用户讨论需求
→ 用户最终批准
→ 创建 taskId
→ 将批准后的需求保存为 Requirement Markdown
→ 创建该 Task 的有序 Plan Nodes
→ Task 进入 READY / PENDING（取决于 TaskGroup 前置）
```

Requirement 不写入产品经理的永久 Memory。

---

# 5. Execution Task Driver / Browser path 在 Task 主链中的角色

Execution-owned Task Driver / Browser path 可以：

```text
轮询 listTasks
显示 canStart / blockedReason
人工批准独立 Task（调用 `authorizeTask`）
在已授权 TaskGroup 中继续驱动 eligible Task
读取 TaskRoleBinding；若 required binding 缺失，则由 Execution Browser CREATE/识别 Conversation，Agent 校验 Worker identity，Task 调用 bindTaskWorker 固化 binding
required bindings 齐全后调用 startTask
Execution Browser RESTORE / WAKE 对应 Worker Conversation
调用 startNode；Task 自动从 TaskRoleBinding 解析 workerRef
轮询 pending messages
```

但是 Execution Task Driver / Browser path 不拥有：

```text
Task eligibility 规则
Task 状态机
Node 状态机
reopen 语义
```

这些必须由 Task Domain 返回和校验。

---

# 6. 总控在 Task 主链中的角色

总控 / 项管基于正式反馈做智能判断，例如：

```text
测试不通过
→ 是否 reopen 研发？

业务确认完成
→ 是否 resume？

技术错误修好
→ 是否 reopen 当前 Node？
```

总控负责“决定”。

Task Domain 负责：

```text
这个动作是否合法
当前版本是否匹配
如何原子修改状态
如何保留历史
```

---

# 7. 执行领域边界

当 Browser / Local 等 Execution capability 出现（MCP 仅为 future/non-v1 adapter 例）：

```text
Action permission
页面异常
真实副作用不确定
Execution error
```

执行领域负责真实判断与 Evidence / Delivery / Receipt。

Task Domain 接受的结果只应是：

```text
waitNode
failNode
resumeTask
completeNode
```

等明确业务动作或引用。

Task Domain 不读取 DOM 来决定状态。

---

# 8. TaskGroup 与产品数量无关

平台可以迭代一个产品或多个产品。

TaskGroup 是“任务链”概念，不是“Product”实体。

第一版 Task Domain 不建立 Product Domain / Product table，也不假设一个 Git 仓库只能对应一个产品。

---

# 9. 当前源码位置

现阶段源码位置：

```text
/Users/agent/Desktop/ai-agent-platform
```

Phase 3 正式领域文档落在该仓库 `docs/technical/技术方案/第三阶段/**`。

平台运行时 Task working data 使用统一 `.ai-agent-platform/**` 语义。

---

# 10. 接手规则

后续 Chat / Agent 接手任务与编排领域时：

```text
先读 README
再读 09-设计决策记录与明确非目标
再读 API / DDL / Transaction 文档
```

除非出现文档中列出的真实升级触发器，否则不要重新提出 WorkItem / Claim / DAG / Redis / Temporal 等第一版已否决设计。

```text
任务与编排领域
= 持久工作事实 + 合法推进 + 可恢复编排 + Task-scoped document context
```

## Bounded Context

```text
Task Orchestration Context
```
