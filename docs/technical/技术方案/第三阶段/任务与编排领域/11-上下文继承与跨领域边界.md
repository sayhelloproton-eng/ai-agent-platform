> 本文保存本轮讨论中对后续 Agent / Execution 领域非常关键、但不应被误写进 Task Domain 内部实现的上下文。

---

# 1. Phase 2 是证据，不是 Phase 3 依赖

Phase 2 已证明 Task / Controller / Browser / Local / Approval / Delivery 能真实串联。

Phase 3 可以重写实现，但不能丢掉已验证的重要语义：

```text
opaque refs
idempotency 绑定请求语义
Business Wait != Execution Lease
Delivery 是不可逆事实边界
Human Approval 是协议事件
OBSERVE != MUTATE
未知副作用不得盲目重试
Evidence / Result 可追踪
Browser Host 不拥有 Task Workflow
```

本 Task v1 已把其中属于任务领域的部分保留为：

```text
opaque role/worker/actor refs
expectedVersion
idempotencyKey + requestHash
WAITING
Event / Message
明确的 Task / Node 当前状态真源
```

Delivery / Approval / Execution Lease 等继续由执行领域拥有。

---

# 2. 当前 Custom GPT 载体观察

当前实际使用中，一个 Custom GPT 基础 `g-...` 可以被 Agent Domain 视作某种 Role / Worker Definition 外部载体；其多个 `/c/<conversationId>` Conversation 可以被 Agent Domain 视作具体 Worker Instance / Session 外部载体。

例如逻辑关系：

```text
Custom GPT definition
→ Role / WorkerDefinition external carrier

Conversation
→ concrete WorkerInstance / Session external carrier
```

**这不是 Task Domain Contract。**

Task Domain 只看到：

```text
requiredRoleRef
workerRef
```

未来 Custom GPT 被自建 Agent Runtime 替换，Task API 不变。

# 3. 三个第一版复合角色

当前业务验证使用：

```text
1. 运营 + 产品经理
2. 总控 = 项目管理 + 研发
3. 测试 + 运维
```

这些角色的职责和固定 Context 归智能体运行与协作领域。

Task Node 只引用 `requiredRoleRef`。

---

# 4. 用户批准需求后的 Task 创建

目标业务流程：

```text
运营 / 产品与用户讨论需求
→ 用户最终批准
→ 创建 taskId
→ 将批准后的需求保存为 Requirement Markdown
→ 创建该 Task 的有序 Plan Nodes
→ Task 进入 READY / PENDING（取决于 TaskGroup 前置）
```

Requirement 不写入产品经理的永久 Memory。

---

# 5. 扩展在 Task 主链中的角色

Browser Extension 可以：

```text
轮询 listTasks
显示 canStart / blockedReason
人工点击执行独立 Task
在已授权 TaskGroup 中继续驱动 eligible Task
调用 Agent Domain 获得 / 选择具体 Worker
打开 / 驱动对应 Worker 页面
调用 startNode 绑定 workerRef
轮询 pending messages
```

但是扩展不拥有：

```text
Task eligibility 规则
Task 状态机
Node 状态机
reopen 语义
```

这些必须由 Task Domain 返回和校验。

---

# 6. 总控在 Task 主链中的角色

总控 / 项管基于正式反馈做智能判断，例如：

```text
测试不通过
→ 是否 reopen 研发？

业务确认完成
→ 是否 resume？

技术错误修好
→ 是否 reopen 当前 Node？
```

总控负责“决定”。

Task Domain 负责：

```text
这个动作是否合法
当前版本是否匹配
如何原子修改状态
如何保留历史
```

---

# 7. 执行领域边界

当 Browser / Local / MCP 等出现：

```text
Action permission
页面异常
真实副作用不确定
Execution error
```

执行领域负责真实判断与 Evidence / Delivery / Receipt。

Task Domain 接受的结果只应是：

```text
waitNode
failNode
resumeTask
completeNode
```

等明确业务动作或引用。

Task Domain 不读取 DOM 来决定状态。

---

# 8. TaskGroup 与产品数量无关

平台可以迭代一个产品或多个产品。

TaskGroup 是“任务链”概念，不是“Product”实体。

第一版 Task Domain 不建立 Product Domain / Product table，也不假设一个 Git 仓库只能对应一个产品。
