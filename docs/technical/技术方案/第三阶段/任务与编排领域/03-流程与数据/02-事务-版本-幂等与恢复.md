# 任务与编排领域｜Transaction / Version / Idempotency / Recovery

---

# 1. 总原则

第一版只坚持四条：

```text
1. SQLite 状态变化必须 transaction
2. Task / Node / Group 使用 expectedVersion 防旧写
3. 重要写操作使用 idempotencyKey + requestHash
4. Markdown + SQLite 不伪装成分布式事务，采用安全文件写 + 可恢复索引同步
```

---

# 2. Version

对象：

```text
Task.version
Node.version
TaskGroup.version
```

规则：只要对象业务状态被修改，version + 1。

调用方使用最后读到的 `expectedTaskVersion / expectedNodeVersion / expectedGroupVersion`。版本不匹配返回稳定冲突错误，不自动覆盖。

---

# 3. 为什么 Task 和 Node 都需要 version

例：

```text
总控读取：Task v10 / Node v4
扩展启动 Node：Task → v11 / Node → v5
旧总控继续提交：expectedTaskVersion=10 / expectedNodeVersion=4
```

必须失败，防止旧 GPT Conversation、旧 Browser page、重复 Action、延迟响应覆盖新状态。

---

# 4. startTask transaction

```text
检查 idempotency
校验 Task READY
校验 expectedTaskVersion
校验 TaskGroup eligibility（如有）

Task READY → ACTIVE
Task.version + 1
Task.startedAt = now

first Node PENDING → READY
Node.version + 1

Task.currentNodeId = firstNodeId

append Events
save idempotency response
COMMIT
```

---

# 5. startNode transaction

```text
检查 idempotency
校验 Task ACTIVE
校验 Node READY
校验 workerRef null
校验 expectedTaskVersion
校验 expectedNodeVersion

Node.workerRef = request.workerRef
Node.status = IN_PROGRESS
Node.startedAt = now
Node.version + 1

Task.version + 1

append NODE_STARTED
save idempotency response
COMMIT
```

可使用条件 UPDATE：

```sql
UPDATE nodes
SET
  status = 'IN_PROGRESS',
  worker_ref = ?,
  started_at = ?,
  version = version + 1
WHERE node_id = ?
  AND status = 'READY'
  AND version = ?;
```

要求 `changes == 1`。

---

# 6. completeNode transaction

先由 TaskDocumentService 校验 required outputDocuments 全部存在、hash / index 合法。

事务：

```text
check idempotency
validate Task ACTIVE
validate Node IN_PROGRESS
validate worker / actor
validate expected versions
snapshot current run history
Node → SUCCEEDED
completedAt = now
Node.version + 1

if next node:
    next → READY
    next.version + 1
    Task.currentNodeId = next
else:
    Task → SUCCEEDED
    Task.currentNodeId = null
    Task.completedAt = now

Task.version + 1
append events
save idempotency response
COMMIT
```

---

# 7. reopenNode transaction

```text
check idempotency
validate Task
validate target Node
validate expectedTaskVersion
需要时先保存将被重置的当前 run 历史

target Node:
  runNo + 1
  READY
  workerRef null
  result/error null
  startedAt/completedAt null
  version + 1

all later Nodes:
  PENDING
  workerRef null
  result/error null
  startedAt/completedAt null
  version + 1

Task:
  ACTIVE
  currentNodeId = target
  version + 1

append NODE_REOPENED
save idempotency response
COMMIT
```

不得删除 node_execution_history / task_documents / task_events。

---

# 8. Idempotency

保存：

```text
idempotencyKey
operation
requestHash
responseJson
```

重复规则：

```text
same key + same semantic request
→ return stored response

same key + different semantic request
→ IDEMPOTENCY_CONFLICT
```

---

# 9. requestHash

只包含影响业务语义的规范化字段。

例如 startNode：

```text
taskId
nodeId
workerRef
expectedTaskVersion
expectedNodeVersion
```

不加入 traceId / HTTP header / 传输 timestamp / 随机 request id。

---

# 10. 不使用 Lease / Lock Table

第一版没有 distributed lock / lease token / claim token / lock table。

依赖 SQLite transaction + version check + conditional UPDATE，满足当前单机第一版。

---

# 11. putTaskDocument：跨 SQLite + FileSystem

文件系统和 SQLite 不是一个 ACID transaction。第一版不引入两阶段提交 / 分布式事务。

推荐：

```text
1. 校验 task / node / documentType / expectedVersion
2. 计算安全目标路径
3. 写临时文件
4. fsync / close（按实现能力）
5. atomic rename 到正式 Markdown
6. 计算 contentHash
7. SQLite transaction:
   - upsert task_documents
   - Task.version + 1（按最终契约）
   - DOCUMENT_UPDATED Event
   - idempotency record
8. COMMIT
```

---

# 12. Reconciliation

若文件已写成功但 SQLite 更新失败，不为此引入复杂 transaction manager。

TaskDocumentService 提供内部 `reconcileDocumentIndex()`，按 file exists / content hash / taskId / documentType 修复索引。

---

# 13. Crash / Recovery 最低测试

必须至少覆盖：

```text
startTask transaction 中途失败 → 无半状态
startNode double submit → exactly one effective
completeNode double submit → one completion
reopenNode 中途失败 → 不出现部分 reset
same idempotency key same request → same response
same key different request → conflict
stale expectedVersion → zero side effect
document file written + DB failure → reconcile 可恢复
SQLite restart → 状态可读
WAL restart → integrity PASS
```

---

# 14. Blind Retry

不确定副作用不得盲目重试。

Task Domain 自己没有 Browser / Shell Delivery 语义，但 API 必须允许 Execution Domain 在结果不确定时将 Task 放入 WAITING，而不是自动重跑业务 Node。

---

## 当前正式约束：绑定、恢复与重试

- `bindTaskWorker` 与 `startNode` 都属于 Task transaction；`startNode` 在事务内解析稳定 TaskRoleBinding。
- version conflict 不允许直接重放旧 payload；必须重新读取当前 Task/Node/binding 后重新计算意图。
- Task 不复制 `UNKNOWN_SIDE_EFFECT`。Execution 返回 UNKNOWN 时，Task 只进入自身 WAITING/未决语义，并等待 reality verification 结果。
- restart/reopen 恢复 Task 持久事实；不得依赖 platform-host/browser transient cache。
