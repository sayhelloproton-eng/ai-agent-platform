## 二、Phase 2 最重要的真实经验

不要把以下问题继续当成零散 Browser bug：

- Journal capacity → polling starvation；
- Approval waiting → claim/reclaim；
- false user_reviewing；
- send readiness；
- Wake during generation；
- Action Allow → RESPONSE_INTERRUPTED_BY_USER；
- Observation 自动滚动；
- 长聊天页面 scroll 漂移；
- Delivery 已成功但后续 response 把 Browser Work 反向判 FAILED。

共同根因是：

> Browser Host 逐步越过 Executor 边界，开始同时拥有 Observation、Workflow waiting、Human interaction、Response lifecycle、Continuation，造成状态组合爆炸。

冻结经验：

```text
OBSERVE != MUTATE
DELIVERY 是不可逆事实边界
Business Wait != Execution Lease
Human Approval 是协议事件
CONTROLLER_WAKE 是通知，不是 response workflow
Browser Host 不拥有 Task Workflow
动态页面位置使用 semantic state / anchor，不用绝对 scrollTop
真实 Browser 是 Acceptance，不是主要状态机 Debugger
```

## 四、Phase 3 的总体目标

一句话：

> 把 Phase 2 已验证的五类能力，从“能串起来的一套实现”升级成“通过稳定协议连接、部署无关、可替换、可独立测试和部署的一组 Agent Platform 模块”。

重点目标：

1. **公共领域 / Platform Commons 优先**：定义所有模块共同使用的 Ref、Contract Envelope、Result/Error、Capability Descriptor、Module Manifest、Approval/Evidence 基础语义、Provider Config、Port/Adapter 规范。
2. **Task Domain 优先**：重塑 waiting / lease / execution / delivery / continuation / recovery 状态语义。先讲清需求和不变量，再设计状态机。
3. **Execution Flow Runtime**：建立 Runtime-owned Composition Root；所有外部依赖通过 config + Adapter/Provider 注入。
4. **整个平台独立部署**：同一模块未来可 in-process、localhost、LAN、remote 部署而不修改 Flow 协议。
5. **Browser Lifecycle vNext**：拆分 Host Lifecycle / Observation / Execution / Continuation；Observation read-only，Delivery terminal。
6. **Inference Provider**：手机/本地/云模型通过 `backend_ref` 配置替换，Flow 不硬编码 IP / model mapping。
7. **Deterministic Verification**：fake clock、state-machine simulation、race matrix、replay/crash test，真实 Browser 回归最终验收角色。

## 五、强制架构基线

模块内部：

```text
只依赖自己的 public ports/contracts
不直接 import 其他模块内部实现
```

外部依赖：

```text
Runtime-owned config
→ Composition Root
→ Adapter / Provider
```

Flow 只允许逻辑引用：

```text
backend_ref
capability_ref
command_ref
provider_ref
module_ref
```

禁止在 Flow 写：

- IP；
- 本机目录；
- executable path；
- 其他模块源码路径。

本地同进程实现只能是一种 Adapter，不是强耦合前提。

跨模块使用稳定版本化 API / protocol；部署位置变化不改 Flow。

## 六、Controller / Task / Flow / Runtime 初始边界假设

先审计并允许推翻：

```text
Controller = 决策 / 计划语义 / 下一步选择
Task       = Durable Coordination / Plan progress / Work / Event
Flow       = 有界、声明式 Execution Contract
Runtime    = Config / Composition / Provider / Bounded Execution
Capability = 一个领域能力执行者
```

特别注意区分：

```text
Plan != Execution Flow
Task Orchestration != Runtime Execution
```
