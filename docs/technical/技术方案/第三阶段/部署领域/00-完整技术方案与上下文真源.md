# Deployment Domain｜完整技术方案与上下文真源

## 0. 冻结声明

本文冻结 Phase 3 v1/P0 Deployment Domain。目标不是建设通用云平台、Kubernetes 控制面或插件市场，而是为当前单仓库、TypeScript-first、repo-local 的 AI Agent Platform 提供稳定的**模块治理 + 确定性部署 + 真实验证 + 升级管理**能力。

所有设计遵循最小充分原则：当前真实调用链、稳定性、升级治理和验收不需要的实体、服务、数据库和调度系统，不进入 v1。

---

# 1. 领域职责

Deployment Domain 负责：

- 定义平台统一 Module Contract；
- 维护标准 Module Template；
- 通过 Deployment Conformance 形成长期一致性门禁；
- 统一管理内部 Module 与 External Resource Module；
- 汇总 Provides / Requires / Requirements / Config Slots；
- 构建实例级依赖图；
- 生成不可变 Deployment Plan；
- 执行 install/configure/upgrade/repair 的确定性 apply；
- 调用 Module 自身公开 lifecycle / verify / doctor primitives；
- 记录 installed version 与按版本保留的 verification history；
- 生成当前真实部署 Manifest；
- 生成实例级 `INSTALL.generated.md`；
- 为 AI 提供结构化、可验证、低智能依赖的部署入口；
- 通过 `module-skill` 辅助创建、升级和迁移 Module，但不让 AI 绕过 Contract/Conformance。

Deployment Domain 不负责：

- Task 工作流与状态推进；
- Agent Role / Worker / Conversation / Collaboration；
- Execution 的 real-world effect policy、Action Approval 与执行结果；
- Model 的 FAST/REASON/AUTO 推理语义；
- 各领域自己的业务健康判定；
- 为方便部署而重新划分其他领域 Service/Process 边界。

---

# 2. 五包冻结架构

```text
Deployment Domain

├── module-contract
│   └── Module/Requirements/Provides/Requires/Config/Lifecycle/Result/Error/Version Contracts
│
├── module-template
│   └── 各 Module Kind 的标准工程起点 + templateVersion
│
├── deployment-conformance
│   └── Static Contract / Package / Behavior 三层 Gate
│
├── platform-cli
│   └── preflight / plan / apply / start / stop / status / verify / doctor / manifest
│
└── module-skill
    └── AI 创建/升级/模板迁移/Conformance 修复/External Adapter 创建
```

- 五个都是 npm Package。
- Deployment Domain 不新增后台 daemon。
- `platform-cli` 是唯一部署 CLI 应用。
- `module-skill` 是 AI 开发辅助，不是部署控制面。

---

# 3. Module 统一治理模型

## 3.1 Module

Module 是平台统一治理单元。包括：

- 内部 library package；
- service package；
- CLI/migration package；
- Browser Extension；
- Agent Package；
- External Resource Module。

所有正式 Module 都必须：

```text
遵守 module-contract
→ 对齐 module-template
→ 通过 deployment-conformance
→ 被 platform-cli 纳入统一计划/状态/验证/升级管理
```

## 3.2 Module Package

Module Package 是承载 Module 规范与实现的 npm package。

内部资源通常 Module 本身就是 npm package。

外部资源本身可能不是 npm package，因此由一个 Module Adapter / Module Package 负责：

```text
External Resource
        ↑
Module Adapter npm package
        ↑
module-contract / conformance / platform-cli
```

## 3.3 Deployment Unit

Deployment Unit 是拥有真实部署/运行生命周期的 Module。

因此：

```text
Module ≠ Deployment Unit
npm Package ≠ Service
Service ≠ Process（逻辑 Service 不必独立进程）
```

Library 仍接受版本、依赖、Conformance、升级治理，但不伪造 `start/stop`。

---

# 4. External Resource Module 是硬规则

所有平台依赖的外部资源必须进入 Module Graph。禁止“某个模块偷偷带一个外部依赖，只在 README 里写一下”。

典型 External Resource Module：

- Model API Provider；
- Microsoft Dev Tunnel；
- Chrome Runtime；
- ChatGPT Web / Custom GPT Carrier；
- 其他未来真实进入平台运行链的外部程序、API 或载体。

其生命周期只声明真实支持项。例如远端 API 不拥有 start/stop；Dev Tunnel 可以 install/start/stop；Chrome 是否可自动 install 取决于适配能力。

需要登录、授权、购买、创建 GPT、加载 Extension 等人工步骤时，统一返回 `ACTION_REQUIRED`。

## 4.1 Bootstrap 边界

Platform CLI 自身要运行必须先有最小 bootstrap 环境（OS/filesystem/Node/npm 或未来等价发行方式）。这是不可消除的启动根。

一旦 `platform-cli` 可执行，平台依赖的这些外部运行环境也应通过 External Resource Module 纳入持续的 status/verify/doctor/upgrade 管理；bootstrap 不构成长期旁路。

---

# 5. Module Contract 最小内容

`module-contract` v1 只冻结实现必需内容：

```ts
interface ModuleDescriptor {
  contract: "module";
  contractVersion: "1.0.0";
  moduleRef: string;
  packageName: string;
  moduleVersion: string;
  kind: ModuleKind;

  templateVersion: string;
  platformCompatibility: string;

  provides: ModuleProvide[];
  requires: ModuleRequire[];
  requirements: ModuleRequirement[];
  configSlots: ConfigSlot[];

  lifecycle: LifecycleSupport;
  verification: VerificationContract;
  effects: DeploymentEffect[];
}
```

`moduleVersion` 必须由 package/adaptor 的版本真源自动提供，不允许人工维护第二套版本。

External Resource Module 还要区分：

- Module Adapter 自身版本；
- 当前 observed external resource version（若资源有可识别版本）。

外部资源没有传统版本时不伪造版本号，以 resource identity/configuration + verification reality 为准。

---

# 6. Provides / Requires

Provides / Requires 表达逻辑 Contract，不表达物理地址：

```ts
interface ModuleProvide {
  contractRef: string;
  version: string;
}

interface ModuleRequire {
  contractRef: string;
  versionRange: string;
  optional?: boolean;
}
```

禁止将以下内容写入逻辑依赖：

- IP；
- localhost port；
- phone address；
- Chrome tabId；
- ChatGPT conversation id。

这些属于实例配置或运行事实。

Platform CLI 只在**本次目标 Module Set / 平台已知 Module Set**里解析依赖；v1 不做 npm Marketplace、全网 Plugin Discovery 或动态 Provider Registry Service。

---

# 7. Requirements 与 Config Slots

Module Requirement 必须机器可读、只读、零副作用，用于描述：

- Runtime/OS/version；
- executable；
- port；
- filesystem；
- network；
- external resource；
- human prerequisite；
- contract dependency。

Config Slot v1 类型仅需：

```text
string | number | boolean | url | path | enum | secretRef
```

Module 声明“需要什么配置”，Platform CLI 负责实例级收集与材料化。

Secret 原值不进入 Descriptor、日志和 Manifest。

---

# 8. Lifecycle 与部署动作

Module Contract 可以声明支持：

```text
describe
preflight
status
verify
doctor
start
stop
restart
migrate
```

`start/stop/restart/migrate` 只在真实支持时声明。

平台级部署动作：

```text
install
configure
upgrade
repair
```

由 `platform plan` 生成实例级 Deployment Plan，再由 `platform apply` 统一执行。Module 只提供其真实 lifecycle primitive、requirements、verification hints 与可能 effects，不自己规划整个实例的部署拓扑。

---

# 9. Platform CLI v1

冻结命令：

```bash
platform preflight [module]
platform plan --intent <install|configure|upgrade|repair> [...]
platform apply <planRef>

platform start [module]
platform stop [module]
platform status [module]
platform verify [module]
platform doctor [module]
platform manifest [module]
```

可增加易用 alias，但不改变主合同。

不冻结：Marketplace、publish、复杂 export、远端 Fleet 管理。

---

# 10. Deployment Plan

Plan 是不可变计划文件，不是 Workflow Entity：

```ts
interface DeploymentPlan {
  planRef: string;
  intent: "install" | "configure" | "upgrade" | "repair";
  modules: ResolvedModule[];
  steps: DeploymentStep[];
  effects: DeploymentEffect[];
  humanActions: HumanAction[];
  verification: VerificationStep[];
  createdAt: string;
}
```

价值：**用户/AI 确认的计划与最终 apply 的计划必须是同一份。**

Plan 保存于：

```text
.ai-agent-platform/deployment/plans/<planRef>.json
```

---

# 11. Apply 与 ACTION_REQUIRED

每个 Step 都以“先观察当前 reality，再决定动作”为原则：

```text
check reality
→ 已满足：SKIP
→ 可执行：EXECUTE
→ 需要用户：ACTION_REQUIRED
→ 不可继续：FAILED
```

`ACTION_REQUIRED` 发生后立即 STOP。用户完成后再次执行相同 `planRef`，Platform CLI 重检现场并跳过已经满足的步骤。

这提供安全 resume，但不建设 Workflow Engine、Job、Lease、Worker 或持久化 Scheduler。

同一工作区 v1 禁止并发 `apply`，使用简单的 repo-local exclusive lock 即可。

---

# 12. Verify / Doctor / Manifest

Module 的业务 READY 定义由 Module Owner 领域提供。

Deployment：

- 调用 `verify`；
- 保存按版本/资源身份区分的 Verification Record；
- 汇总平台依赖关系与运行状态；
- 不复制 Model/Execution/Agent/Task 的业务验证逻辑。

`doctor` 默认只诊断，不偷偷修改现场；修复需要重新生成 `repair` Plan。

`manifest` 动态生成当前部署视图，不是人工维护第二真源。

---

# 13. Platform READY

平台级 READY 必须同时满足：

1. Required Modules 存在且目标版本正确；
2. Config Slots 完整；
3. Required Provides/Requires 已解析；
4. Required External Resource Modules 当前可用；
5. 需要运行的 Deployment Units 当前 READY；
6. 当前版本/当前资源身份拥有有效 Verification PASS；
7. Cross-module verify PASS；
8. Blocking `ACTION_REQUIRED` 为 0。

平台级公开状态：

```text
READY | DEGRADED | ACTION_REQUIRED | NOT_READY
```

任何持久化 `state.json` 都不能制造假 READY。

---

# 14. 版本与升级

v1 管理：

- module/package version；
- module contract version；
- template version；
- platform compatibility；
- Provides/Requires contract version compatibility；
- External Resource observed version（若可获取）。

Upgrade 是 v1 正式能力：

```text
current
→ target
→ compatibility
→ conformance metadata
→ dependency graph
→ upgrade plan
→ confirmation
→ apply
→ migrate if needed
→ restart if needed
→ verify
```

失败后 STOP + doctor。v1 不做事务式自动 rollback；回退通过新的 Deployment Plan 完成。

---

# 15. Template / Conformance / Skill

`module-template` 使用 Module Kind Profile：

```text
library
service
cli
browser-extension
agent-package
external-resource
```

只生成该 Kind 真正需要的结构。

`deployment-conformance` 只保留三层：

1. Static Contract Gate；
2. Package Gate；
3. Behavior Gate。

`module-skill` 支持：

- create module；
- update descriptor/contract；
- template migration；
- conformance integration/repair；
- external resource adapter generation；
- upgrade compatibility assistance。

Skill 不能绕过 Contract/Conformance，也不能直接修改生产 Deployment State。

---

# 16. Deployment 状态文件

```text
.ai-agent-platform/deployment/
├── state.json
├── plans/
├── verification/
├── generated/
│   └── INSTALL.md
└── logs/
```

Deployment v1 不使用 SQLite。

真源层级：

- npm internal package version：root package.json/lockfile；
- Module Descriptor：package/adaptor 自描述；
- current runtime reality：Module `status`/`verify`；
- deployment actions/history：Deployment files；
- `state.json`：索引和已执行事实，不是当前在线状态真源。

---

# 17. 跨领域映射

Deployment 统一治理 Task / Agent / Execution / Model 的所有正式 Module，以及这些 Module 依赖的外部资源。

Deployment 不重新定义各领域内部包名、业务 Contract 或 READY 语义。

**[RESOLVED by ALIGN-022～030/223/230] Application Composition Root 已冻结：**

> `@ai-agent-platform/platform-host` 是独立 npm package 的 Local Platform Host / Application Composition Root，只 in-process 装配 Task Runtime、Agent Runtime 等独立 package，并负责 dependency injection、local transport、startup/shutdown 与轻量 health aggregation。

Deployment 将其作为普通受治理 Module/Deployment Unit；不擅自创造 `task-service / agent-service` 等新 daemon。Execution Runtime、Model Runtime、Agent Gateway 仍保持独立 Process/Deployment Unit。

---

# 18. 工程基线

新仓库 TypeScript-first，Node 20.20.1 基线。

- Public Contract 强类型；
- 外部/边界数据 `unknown` + runtime validation；
- TS 运行使用 `tsx` / `node --import=tsx`；
- `tsc --noEmit` 是独立类型门；
- structured JSON + stable error/status；
- 不依赖 AI 猜自然语言输出。

---

# 19. v1 明确非目标

不建设：

- Deployment backend service；
- Deployment SQLite；
- Workflow Engine / Scheduler / Lease / Worker；
- Kubernetes/Docker orchestration；
- Marketplace/Plugin Registry Service；
- 动态 Provider Plugin Framework；
- Secret Vault Service；
- 自动事务式 Rollback；
- Fleet/remote multi-host management；
- 复杂 rollout/canary；
- 模块业务测试的重复实现。

达到当前平台真实需求与稳定性后停止。
