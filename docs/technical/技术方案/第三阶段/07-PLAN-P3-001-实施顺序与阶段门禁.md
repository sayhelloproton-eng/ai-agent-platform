# PLAN-P3-001｜Phase 3 实施顺序与阶段门禁

> 时间优先：先建立可独立部署的平台骨架，不追求一次性完成所有 Hardening 和产品功能。

## Stage 0｜Rebaseline

目标：宣布 Phase 3 Repository Reset。

输出：

- Phase 2 evidence freeze；
- 当前 package / dependency graph 审计；
- Public semantics inventory；
- 明确哪些旧规则暂时停用。

停止条件：新架构不再被旧目录 / Registry / Feishu 同步规则绑架。

## Stage 1｜公共领域 P0

先设计后实现：

- Ref taxonomy；
- Contract envelope；
- Result / Error；
- Capability descriptor；
- Module manifest；
- Provider config；
- Port / Adapter 规则；
- Compatibility policy。

Gate：至少两个 toy modules 可通过相同 Port 使用 in-process / HTTP Adapter。

## Stage 2｜Task Domain P0

先用 state-machine / simulator 冻结：

- waiting；
- lease；
- execution；
- delivery；
- continuation；
- recovery；
- idempotency。

Gate：fake-clock race matrix 全部确定性 PASS，不接真实 Browser。

## Stage 3｜Execution Flow Runtime P0

- Composition Root；
- provider mapping；
- module discovery；
- bounded Flow execution；
- in-process / localhost adapter interchangeability。

Gate：同一 Flow 在两种部署组合下运行，Flow 文件不变。

## Stage 4｜领域 Adapter 迁移 P1

顺序建议：

```text
Local Control
→ Inference Provider
→ Controller Adapter
→ Browser Host vNext
```

Browser 最后迁移，因为它是动态环境，不应再次成为基础架构 debugger。

## Stage 5｜真实串行验收 P1

只做少量真实 E2E：

```text
Goal
→ Controller
→ Task vNext
→ Runtime
→ Local / Browser
→ Approval
→ Result / Delivery
→ Continuation
→ Complete
```

若失败，先定位到 contract / simulator / adapter test，再决定是否重新真实执行。

## 明确暂缓

Phase 3 主线暂不做：

- K8s / 服务网格；
- HA；
- 多租户；
- 完整 RBAC；
- 完整管理后台；
- 大规模并发；
- 完整飞书 / 文档同步治理；
- 大量新 Browser capability。

## 阶段成功定义

Phase 3 完成时应能证明：

> **平台模块在哪里运行、由哪个 Provider 实现，不再是 Flow 和业务领域代码的硬编码前提。**
