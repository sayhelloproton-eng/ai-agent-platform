# 01｜领域边界与依赖约定

> 状态：FROZEN  
> 目标：确定五个正式领域如何拥有状态、暴露能力、建立依赖，以及 Application / Adapter 如何跨领域组合。

---

# 1. 第一原则：状态必须有唯一 Owner

每一项业务事实必须明确唯一 Owner。

```text
Task State
→ 任务与编排领域

Role / Worker / Conversation Identity
→ 智能体运行与协作领域

Execution Delivery
→ 执行领域

Provider Health
→ 模型与推理领域

Installed Module Version
→ 部署领域
```

其他领域：

```text
MAY 保存 Ref
MAY 保存事件投影
MAY 保存只读 Snapshot
MAY 建立缓存 / Read Model
```

但：

```text
MUST NOT 修改另一个领域拥有的事实
MUST NOT 把副本当作第二事实真源
MUST NOT 根据另一个领域的内部实现推导平台公共语义
```

---

# 2. Public / Internal 边界

每个领域必须明确：

```text
Public
Internal
```

`Public` 至少可能包含：

```text
Public API
Public Port
Public Contract
Public Event Schema
Public Query
Public Types
```

`Internal` 包含：

```text
内部实体
内部状态机
Repository
ORM Model
数据库 Schema
内部 Service
内部 Adapter
内部 Helper
未公开 Event
内部错误
```

规则：

> 跨领域依赖只能指向 Public。

禁止：

```text
Domain A → Domain B internal/**
Domain A → Domain B private storage
Domain A → Domain B ORM model
Domain A → Domain B implementation class
```

---

# 3. Provides / Requires 是跨域依赖真源

每个正式领域必须维护：

```text
Provides
Requires
```

示例：

```text
任务与编排

Provides:
- Task Command / Query
- TaskDocument
- TaskRoleBinding
- Task Event

Requires:
- Agent Role / Worker identity facts
- Execution Result / Evidence Ref
- Model inference（仅在 Task Owner 真实需要认知判断时）
```

要求：

1. `Provides` 必须指向真实 Public Contract / API / Event；
2. `Requires` 必须指明 Provider；
3. `Requires` 不得写成模糊的“需要 Task 数据”“需要 Agent 状态”；
4. 如果无法说清 Provider 和 Contract，说明边界尚未完成；
5. 跨域集成测试必须以 Provides / Requires 对齐为基础。

---

# 4. 允许的依赖形式

## 4.1 同步 Public API

适合：

```text
查询当前状态
提交明确命令
需要立即得到领域级接受 / 拒绝
```

例如：

```text
Agent Application
→ Task Public API
→ getCurrentWork(...)
```

## 4.2 异步领域事件

适合发布已经发生的事实：

```text
TASK_COMPLETED
EXECUTION_DELIVERED
AGENT_HANDOFF_COMPLETED
```

Event 不是“偷偷调用另一个领域”的替代品。

## 4.3 Public Port

当 Domain 需要能力但不应该依赖具体 Provider 实现时：

```text
Agent Domain
→ Inference Port
→ 模型与推理领域实现
```

## 4.4 Application Orchestration

允许 Application 层组合多个领域：

```text
Management Backend
Controller Application
Gateway Application
```

但 Application：

```text
MUST NOT 拥有领域状态机
MUST NOT 绕过领域 API 直接写数据库
MUST NOT 把跨域补偿逻辑偷偷变成业务事实 Owner
```

---

# 5. 禁止共享数据库作为集成接口

禁止：

```text
Task DB ← Agent 直接 SELECT
Execution DB ← Task 直接 UPDATE
Inference Table ← Management Backend 直接写
```

即使当前技术上部署在：

```text
同一个 Node 进程
同一个 SQLite
同一个 PostgreSQL
同一个 monorepo
```

逻辑所有权仍然必须独立。

若某个过渡部署形态物理共用同一数据库文件，仍必须保持 table / repository / API owner 的逻辑隔离；物理同库绝不等于共享业务所有权。

---

# 6. 跨域引用规则

跨域引用：

```text
MUST 使用公开 Ref / ID
MUST 把 Ref 当作 opaque value
MUST NOT 解析另一个领域 Ref 的内部结构获得业务含义
```

例如消费者可以保存：

```text
taskId / nodeId
roleRef / workerRef
executionRef / evidenceRef
inferenceRef / modelRef
moduleRef
```

但禁止：

```text
split(executionRef, ":")[2]
→ 推导 Provider / 状态 / 类型
```

需要业务含义时必须使用 Owner 的 Public API / Contract。

---

# 7. 三个核心事实层必须明确分开

Phase 3 P0 设计必须始终区分：

```text
Task State
Agent State
Execution State
```

例如：

```text
Task Node = IN_PROGRESS
```

不能推出：

```text
Agent 一定仍在运行
```

同样：

```text
Execution = DELIVERED
```

不能由 Task 自行改写成：

```text
Execution = SUCCEEDED
```

Owner 只接收另一个领域正式提供的 Result / Event。

---

# 8. 领域依赖不是调用方向的简单箭头

业务协作可能形成：

```text
Task
→ Agent
→ Execution
→ Result
→ Task
```

这不是代码循环依赖的许可。

代码 / Package 依赖应该通过：

```text
Public Contract
Port
Adapter
Event
Application Layer
```

避免：

```text
task-package imports agent-internal
agent-package imports execution-internal
execution-package imports task-internal
```

业务闭环允许，代码级 internal 循环禁止。

---

# 9. Application / UI / BFF 的边界

前台和后台可以按用户用例聚合多个领域。

例如任务详情页读取：

```text
Task
Agent Worker / Collaboration
Execution
Owner-specific Approval（如该用例存在）
```

允许：

```text
Management BFF
→ Task Query API
→ Agent Query API
→ Execution Query API
```

如果读性能需要，可以建立：

```text
Management Read Model
```

Read Model：

```text
MAY 消费多个领域 Event
MAY 做反范式聚合
MAY 为页面优化结构
MUST 是可重建的
MUST NOT 成为写入事实真源
```

所有写操作必须回到真实领域 Owner。

---

# 10. Adapter 边界

以下应默认视为 Adapter / Context，而不是顶级领域：

```text
Browser
Local
MCP（future / non-v1 adapter only）
A2A
AG-UI
Remote Host
CLI
ChatGPT
```

例如：

```text
执行领域
├── Browser Adapter
├── Local Adapter
└── MCP Adapter（future / non-v1 example）

智能体运行与协作领域
└── A2A Adapter

Presentation / Application
└── AG-UI Adapter
```

Adapter 可以拥有连接态、协议态、缓存等技术状态，但不能擅自拥有上层领域业务事实。

---

# 11. 依赖准入表

| 依赖 | 允许 |
|---|---|
| Domain → 自己的 Internal | ALLOW |
| Domain → 其他 Domain Public Contract | ALLOW |
| Domain → 其他 Domain Public Port | ALLOW |
| Domain → 已批准 Shared Kernel | ALLOW |
| Application → 多 Domain Public API | ALLOW |
| BFF → 多 Domain Query API | ALLOW |
| Read Model ← 多 Domain Event | ALLOW |
| Domain → 其他 Domain internal/** | DENY |
| Domain → 其他 Domain private DB | DENY |
| UI → 直接写 Domain DB | DENY |
| Adapter → 修改非本领域业务事实 | DENY |

---

# 12. 新领域 / 新模块检查

新增正式领域前必须证明：

```text
有独立业务语义
有独立状态
有独立生命周期
有真实 Service / Module / API
有多个消费者或稳定边界
无法自然归属现有领域
```

否则优先作为：

```text
Subdomain
Bounded Context
Module
Service
Adapter
Infrastructure
Protocol
```

存在。

当前不自动升级为顶级领域的概念包括：

```text
Approval
Memory
Gateway
Capability Registry
Provider Registry
Observability
Evaluation
Browser
Local
MCP（future / non-v1 adapter only）
A2A
AG-UI
```

---

# 13. 领域设计完成条件

一个领域的第一版设计不能只写概念图。

至少要能回答：

```text
1. 我拥有哪些事实？
2. 我明确不拥有什么？
3. 我的真实 Module / Service 是什么？
4. 我 Provides 什么？
5. 我 Requires 什么？
6. Public / Internal 边界在哪？
7. 其他领域通过什么 Contract 使用我？
8. 我依赖其他领域的什么公开能力？
9. 哪些 Adapter 属于我？
10. 是否仍存在明确的待确认跨域问题？若存在，其 owner、fallback 与验证条件是什么？
```

---

## 当前正式约束：五领域最终依赖原则

五领域保持 Task / Agent / Execution / Model / Deployment，不新增第六业务领域。`platform-host` 是独立 npm package 的 Application Composition Root，不是领域。跨域只能经 Public Contract/Public API；禁止共享 DB、内部 Adapter/Repository、深路径 import。实现 package 依赖图必须可形成 DAG；领域 package 不得反向依赖 platform-host。

# 8. Carrier transport 与领域 Ownership 分离

Custom GPT 当前拥有 GPT Actions/File Bridge，并不改变五领域事实所有权：

```text
Agent Gateway → OpenAI protocol normalization
Task          → TaskDocument
Agent         → Role/Worker/Collaboration
Execution     → physical fetch/effect/evidence/Browser
Model         → inference
Deployment    → Carrier/Public-ingress Module governance
```

因此不得新增 File/Artifact Domain，也不得让 Gateway/Browser 因 transport convenience 成为业务内容真源。
