# 06｜测试与验收约定

> 状态：FROZEN  
> 目标：统一“哪一层测试证明什么”，避免再次出现低层测试全绿却真实链路不成立。

---

# 1. 测试层级

平台统一：

```text
Unit
Domain
Contract
Integration
E2E
Real Environment Acceptance
Conformance
```

它们不是互相替代关系。

---

# 2. Unit Test

证明：

```text
单函数
单类
单算法
单 Adapter helper
```

在隔离条件下正确。

Unit Test：

```text
MAY 大量 Mock
```

但不能证明：

```text
真实 Contract 对齐
真实数据库
真实网络
真实设备
真实权限
真实副作用
```

---

# 3. Domain Test

证明某领域内部：

```text
状态机
业务不变量
生命周期
并发
幂等
错误边界
```

例如：

```text
Task version conflict
Execution retry rules
Agent handoff invariants
Inference fallback rules
Deployment version records
```

Domain Test SHOULD 尽量不依赖其他领域。

---

# 4. Contract Test

证明：

```text
Provider 实现符合 Public Contract
Consumer 使用符合 Requires Contract
Schema 可验证
错误与版本语义匹配
```

至少包括：

```text
Provider Contract Test
Consumer Contract Test
```

Public Contract 变更：

```text
MUST 更新 Contract Test
```

如果只改 TypeScript 类型但没有运行时 Contract / Schema 校验：

> 不能视为完整 Contract Test。

---

# 5. Integration Test

证明多个真实组件按照公开接口正确协作。

例如：

```text
Task Service + Agent Adapter
Agent Runtime + Inference Gateway
Execution Runtime + Browser Adapter
Deployment CLI + Module Runtime
```

Integration Test 应尽量使用真实：

```text
storage
serializer
schema validator
adapter boundary
```

除非外部系统成本过高。

---

# 6. E2E

证明一个完整平台用例从入口到结果成立。

E2E 关注：

```text
跨领域 Contract
状态推进
错误传播
恢复
结果回写
```

但如果 E2E 仍然把真实设备 / 外部系统全部 Mock：

```text
它不能替代 Real Acceptance
```

---

# 7. Real Environment Acceptance

当能力依赖：

```text
浏览器
真实权限
本机 Shell
手机模型
局域网
外部 Provider
真实用户批准
真实部署环境
```

必须有真实环境验收。

它证明的是：

> 架构在真实约束下仍成立。

不是追求大规模覆盖。

Real Acceptance 应选择少量高价值链路。

---

# 8. Conformance Test

Conformance 证明模块持续符合平台约定。

未来可检查：

```text
Public / Internal
Package metadata
Contract Schema
Version
Module deployment protocol
Dependency direction
Required docs
```

Conformance：

```text
不证明业务正确
```

只证明：

> 结构和公共规则符合平台基线。

---

# 9. 测试证明边界

| 测试 | 主要证明 | 不能替代 |
|---|---|---|
| Unit | 实现单元正确 | Contract / Integration |
| Domain | 领域规则正确 | 跨域对齐 |
| Contract | 公共接口兼容 | 真实组件链路 |
| Integration | 组件协作 | 完整用户用例 |
| E2E | 平台链路 | 真实设备 / 权限 |
| Real Acceptance | 真实环境成立 | 全量回归 |
| Conformance | 平台规范符合 | 业务正确 |

---

# 10. Public Contract 变更最低 Gate

任何 Public Contract 变更至少：

```text
Schema / Type 更新
Provider Contract Test
受影响 Consumer Contract Test
Compatibility Review
```

如果影响两个以上领域：

```text
再增加 Integration Test
```

如果涉及真实副作用：

```text
根据风险决定 Real Acceptance
```

---

# 11. 副作用测试

对于：

```text
Browser submit
Shell write
File write
External API mutation
Deployment install
```

必须覆盖：

```text
成功前
成功后
超时
重复请求
结果丢失
Delivery 已发生但 Result 未回
网络断开
幂等重放
```

重点不是只测：

```text
happy path
```

而是证明：

```text
不会在不确定状态下重复造成副作用
```

---

# 12. 幂等测试

所有声明幂等的写操作至少验证：

```text
同 key + 同请求
→ 不重复创建业务事实

同 key + 不同请求
→ 拒绝

首次请求成功但响应丢失
→ 重放仍可得到同一业务事实

并发重复请求
→ 不产生双写
```

---

# 13. 并发与版本测试

声明 `expectedVersion` 的 API：

```text
MUST 有冲突测试
```

验证：

```text
旧版本拒绝
正确版本推进
重复命令行为明确
```

---

# 14. Fixture

Fixture：

```text
MUST 表达真实业务前置条件
MUST 避免为了让模型 / 代码通过而隐藏关键字段
```

如果一个确定性前置条件可以由结构化数据判断：

```text
不要把是否满足前置条件交给模型猜
```

这条直接适用于 Agent / Inference 测试设计。

---

# 15. Mock 边界

Mock 适合：

```text
昂贵外部依赖
不可控错误注入
Unit / Domain isolate
```

不适合证明：

```text
真实 Contract
真实 Adapter
真实权限
真实序列化
真实网络
真实 Tool / Browser 行为
```

当 Mock 的对象就是被验收能力本身：

```text
该测试不能作为最终验收证据
```

---

# 16. Flaky Test

Flaky Test：

```text
MUST 被视为失败
```

不能长期：

```text
失败就 rerun 到绿
```

允许有限 Retry 只用于：

```text
明确的环境暂态
```

并且必须记录 Retry 次数和原因。

---

# 17. Stop Condition

每轮验收应明确停止条件。

例如：

```text
任一关键 Contract 失败
→ STOP

出现未知副作用状态
→ STOP

版本冲突
→ 重新读取，不盲目推进

真实环境出现不可解释偏差
→ STOP 并定位
```

测试框架不应为了“跑完整套”而在关键错误后继续制造污染。

---

# 18. 测试数据与生产数据

测试：

```text
MUST 不依赖生产隐私数据
MUST 可重复
MUST 可清理
```

真实验收如果必须使用真实账户 / 环境：

```text
应使用最小权限
应明确产生的副作用
应具备清理策略
```

---

# 19. Phase 3 的测试策略


因此 Phase 3 不需要重复用 E2E 证明“Task → Agent → Execution 能不能跑”。

Phase 3 应把更多测试资源放到：

```text
领域内部不变量
Public Contract
新 Multi-Agent 能力
Execution 统一语义
Inference Router
独立 Module / Package Conformance
跨域升级兼容
```

只有新增或改变真实链路语义时，才增加对应 E2E / Real Acceptance。

---

# 20. 发布前最低原则

任何声称：

```text
READY
COMPLETE
PRODUCTION READY
```

必须明确是哪一层证据。

禁止：

```text
Unit 通过
→ 宣称 Production Ready
```

发布说明必须区分：

```text
Implemented
Contract Verified
Integrated
E2E Verified
Real Environment Verified
Production Hardened
```

---

## 当前正式约束：统一 Gate

统一测试层级：Unit / Domain Integration / Contract / Module Conformance / Cross-domain E2E / Fault Injection / Performance-Stability。Conformance PASS 不等于业务 PASS；Browser/Carrier/Effect 等关键链要求真实环境。测试 PASS 必须有机器可验证 evidence；触及 owner/contract/state/effect/approval/recovery 的修改必须跑受影响跨域回归。

# 9. Carrier-specific Conformance 不替代 Cross-domain E2E

对于 Custom GPT Carrier，Contract/Conformance 至少覆盖：

```text
File Bridge runtime shape
45s/100k/TLS/443
explicit consequential flag
no custom headers
auth
relay MIME/size/header/error semantics
```

而 Always Allow、Multi-Action Turn、Conversation file search、Code Interpreter artifact round-trip 必须在真实 ChatGPT Preview/E2E 中给出 `VERIFIED/PENDING_SPIKE/REJECTED_OR_UNSUPPORTED`，不能靠 mock 升级成平台保证。
