# 02｜公共契约与数据约定

> 状态：FROZEN  
> 目标：统一跨领域机器交互的基础表达，不统一各领域业务模型。

---

# 1. 适用范围

本约定适用于：

```text
跨领域 Public Contract
Public API Request / Response
Public Event
跨进程 / 跨设备消息
持久化的公共 Receipt / Result
对外公开 JSON Schema
```

领域内部私有模型可以采用不同结构，只要不泄露为跨域依赖。

---

# 2. JSON 与字段命名

默认机器契约：

```text
JSON UTF-8
```

字段命名：

```text
lowerCamelCase
```

例如：

```json
{
  "contract": "execution.public",
  "contractVersion": "1.0.0",
  "correlationId": "corr-...",
  "executionRef": "execution:..."
}
```

禁止在同一公共 Contract 中混用：

```text
task_id
taskId
TaskId
```

---

# 3. ID 与 Ref

## 3.1 ID

领域内部实体 ID：

```text
由领域 Owner 生成
MUST 全局或领域范围内满足其声明的唯一性
MUST 被消费者视为 opaque string
```

v0.1 不强制所有领域使用同一种 UUID / ULID / prefix 算法。

原因：

> ID 生成算法属于实现选择；跨域真正需要统一的是“不解析、不重写、原样传递”。

## 3.2 Ref

跨领域引用统一使用语义字段：

```text
taskId
nodeId
roleRef
workerRef
collaborationMessageRef
executionRef
evidenceRef
inferenceRef
modelRef
providerRef
moduleRef
approvalRef（仅由拥有该审批语义的领域定义）
```

规则：

```text
MUST 为非空字符串
MUST 由 Owner 生成
MUST 原样传递
MUST NOT 被消费者解析内部结构
MUST NOT 被消费者重写
```

领域可以让：

```text
ID == Ref
```

也可以不同。

这属于领域自己的实现决定。

---

# 4. contract 与 contractVersion

所有跨领域 Public Contract：

```text
MUST 分离 contract 名称与 contractVersion
MUST 声明 SemVer contractVersion
```

格式：

```text
contract = 稳定合同名称
contractVersion = Semantic Versioning / MAJOR.MINOR.PATCH
```

例如：

```json
{
  "contract": "task.command",
  "contractVersion": "1.0.0"
}
```

禁止把 `task.v1 / module.v1 / execution.v1` 这类“名称 + 主版本”字符串继续塞进 `contractVersion` 冒充 SemVer。

语义详见：

`04-版本与兼容性约定.md`

---

# 5. 时间

跨域 Timestamp：

```text
MUST 使用 RFC 3339 / ISO 8601
SHOULD 标准化为 UTC
```

推荐：

```text
2026-08-10T11:04:05.123Z
```

统一字段命名优先使用：

```text
createdAt
updatedAt
occurredAt
startedAt
completedAt
expiresAt
```

禁止仅使用：

```text
"2026-08-10 19:04"
```

这类没有时区语义的跨域时间。

内部可以使用 epoch，但 Public Contract 应输出标准时间字符串，除非某个协议明确规定其他格式。

---

# 6. correlationId 与 causationId

## 6.1 correlationId

用于把一次业务目标 / Task / 链路中的多个跨域动作关联起来。

跨域异步操作：

```text
SHOULD 携带 correlationId
```

如果上游已经提供：

```text
MUST 原样继承
```

下游不得重新生成新的 correlationId 替换上游值。

## 6.2 causationId

用于表示：

> 当前命令 / 事件是由哪个具体命令 / 事件直接导致。

存在事件链或异步恢复时：

```text
SHOULD 使用 causationId
```

不要求所有简单同步 API 都强制携带。

---

# 7. idempotencyKey

所有可能被重放、重试或网络重复提交的跨域写操作：

```text
MUST 定义幂等语义
```

若操作通过显式 key 幂等：

```text
使用 idempotencyKey
```

要求：

```text
同一 idempotencyKey + 同一请求语义
→ 返回同一业务结果或同一已接受事实

同一 idempotencyKey + 不同请求语义
→ MUST 拒绝
```

禁止：

```text
只比较 key，不绑定请求指纹 / 请求语义
```

领域应明确：

```text
幂等窗口
幂等作用域
请求指纹
已完成请求的重复响应行为
```

---

# 8. Version / Expected Version

拥有可并发更新状态的领域，应对 Public Write Contract 明确并发控制。

推荐模式：

```text
resourceVersion
expectedVersion
```

例如：

```json
{
  "taskRef": "task:...",
  "expectedVersion": 12
}
```

如果调用方提交过期版本：

```text
MUST 明确冲突
MUST NOT 静默覆盖
```

具体错误码由领域拥有。

---

# 9. Optional 与 Nullable

公共 Contract 必须区分：

```text
字段不存在
字段存在且值为 null
```

规则：

```text
optional
= 信息未提供 / 不适用 / 版本中未出现

nullable
= 字段存在，但业务语义允许明确为空
```

不得因为实现方便让所有字段都：

```text
optional + nullable
```

领域 Schema 必须明确。

---

# 10. Enum

跨域业务 Enum 由领域 Owner 定义。

平台只规定：

```text
MUST 使用稳定字符串值
MUST NOT 依赖序号
MUST NOT 在不做兼容分析的情况下改变既有值语义
```

例如应使用：

```text
"IN_PROGRESS"
```

而不是：

```text
2
```

新增 Enum 值是否兼容，必须根据消费者行为判断，不能机械视为“只加值就兼容”。

---

# 11. Error Envelope

公共失败响应至少必须能够表达：

```text
code
message
category
retryable
correlationId
details（可选）
```

建议结构：

```json
{
  "error": {
    "code": "EXECUTION_DELIVERY_UNCERTAIN",
    "message": "Delivery state cannot be proven.",
    "category": "CONFLICT",
    "retryable": false,
    "correlationId": "corr-...",
    "details": {}
  }
}
```

规则：

```text
code
→ 稳定机器语义，由领域 Owner 定义

message
→ 面向人类，不作为程序分支依据

category
→ 粗粒度公共分类

retryable
→ 当前失败是否允许按领域规则自动重试
```

注意：

> `retryable=true` 不代表调用方必须重试。

尤其涉及真实副作用时，仍必须遵守执行领域的 side-effect certainty。

建议公共 category 首批保持粗粒度：

```text
INVALID_REQUEST
NOT_FOUND
CONFLICT
UNAUTHORIZED
FORBIDDEN
UNAVAILABLE
TIMEOUT
INTERNAL
```

如果领域需要更细语义，用业务 `code` 表达，不无限扩张公共 category。

---

# 12. Result

不强制所有领域共享一个巨大 `Result<T>` 类型。

规则是：

```text
成功结果由领域 Public Contract 定义
失败使用稳定 Error Contract
```

领域若使用 Result Envelope：

```text
MUST 避免同时出现互相矛盾的：
success=true + error
success=false + data
```

跨域持久执行结果应优先使用：

```text
resultRef
receiptRef
```

把大对象或领域内部证据通过 Owner Query API 获取，而不是在所有链路中复制。

---

# 13. Event Envelope

公共领域事件至少包含：

```text
contract
contractVersion
eventId
eventType
occurredAt
producer
correlationId
subjectRef
payload
```

推荐：

```json
{
  "contract": "execution.event",
  "contractVersion": "1.0.0",
  "eventId": "evt-...",
  "eventType": "EXECUTION_DELIVERED",
  "occurredAt": "2026-08-10T11:04:05.123Z",
  "producer": "execution",
  "correlationId": "corr-...",
  "causationId": "cmd-...",
  "subjectRef": "execution:...",
  "payload": {}
}
```

`causationId`：

```text
可选，但在异步链路中 SHOULD 提供
```

---

# 14. JSON Schema

跨领域稳定 Contract：

```text
SHOULD 有机器可读 Schema
```

Phase 3 默认：

```text
JSON Schema Draft 2020-12
```

理由：

- 当前 Node / TypeScript 生态支持成熟；
- 可与 Ajv 2020 系列校验；
- 适合 Contract Test / Conformance。

Schema 必须：

```text
明确 required
明确 additionalProperties 策略
明确 enum
明确 format
明确 version
```

当前规则：

```text
公共边界默认 additionalProperties: false
```

但如果某协议明确需要扩展字段：

```text
必须定义 extension 容器或兼容策略
```

禁止依赖“随便多传字段消费者就忽略”作为版本策略。

---

# 15. 敏感数据

Public Contract：

```text
MUST NOT 默认暴露 Secret
MUST NOT 在 Event 中传播凭据
MUST NOT 把 Token / Password 放进 Error details
```

需要 Secret 的领域：

```text
保存 secretRef / credentialRef
```

而不是跨域复制 Secret 本体。

日志、Trace、Event、Receipt 均应遵循同样原则。

---

# 16. 公共类型抽取门槛

以下即使多个领域“长得一样”，也不能自动抽成 Shared Type：

```text
Status
Role
Result
Error Code
Provider
Capability
Versioned Entity
```

只有当：

```text
语义完全一致
真实消费者 >= 2
Owner 明确
变更节奏一致
```

才考虑提取。

> 结构相似不等于同一语义。

---

## 当前正式约束：公共数据合同

统一区分 contract 名称、SemVer contractVersion、packageVersion、业务实体 optimistic version、template/platform compatibility。Public boundary 采用 `unknown → runtime validation → typed DTO`；Ref owner 唯一且跨域 opaque；业务 Ref 与 path/URL/tabId/pid 等 physical/transient locator 分离。错误 envelope 统一外壳但保留领域 errorCode/retryable/correlationId。

# 12. Carrier DTO 可以不同于 Internal Domain DTO

OpenAI-specific 字段：

```text
openaiFileIdRefs
openaiFileResponse
x-openai-isConsequential
```

只存在于 Custom GPT OpenAPI/Gateway adapter boundary。

同理，GPT Actions 不支持的自定义 request headers 不能被写成平台 Domain Contract 必填项；`idempotencyKey/correlationId/expectedVersion/...` 在 GPT-facing API 中使用 body/path/query 表达，再由 Gateway 转换为内部合同。

规则：

```text
external carrier input = unknown
→ runtime validation/normalization
→ typed canonical DTO
→ owner Public Contract
```

OpenAI file id、temporary download URL、relay URL 都是 physical/external locator，不得升级为跨领域 stable Ref。
