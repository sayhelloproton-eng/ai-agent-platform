# 04｜版本与兼容性约定

> 状态：FROZEN  
> 目标：让五个领域、独立 npm package、跨域 Contract 和 Adapter 可以独立演进而不靠同步“大爆炸升级”。

---

# 1. 公共 Contract 使用语义化版本

公共 Contract：

```text
MAJOR.MINOR.PATCH
```

含义：

```text
MAJOR
= 存在 Breaking Change

MINOR
= 向后兼容的新能力

PATCH
= 不改变既有语义的修复 / 澄清
```

例如：

```text
1.0.0
1.1.0
1.1.1
2.0.0
```

---

# 2. Contract Version 与 Package Version 分开

必须区分：

```text
Package Version
Contract Version
Schema Version
Runtime / Module Version
```

一个 package 可以发布：

```text
package 3.4.2
```

仍然提供：

```text
contract 1.2.0
```

禁止用 npm package version 隐式替代所有 Contract Version。

---

# 3. 什么是 Breaking Change

以下默认视为 Breaking：

```text
删除 Public 字段
把 optional 改 required
修改字段语义
修改字段类型
重命名 Public 字段
删除 API
改变 API 的副作用
改变幂等语义
改变并发语义
改变 Error Code 语义
改变 retryable 的真实含义
改变 Event 的事实含义
改变 Ref 可用范围
改变已有 Enum 值语义
把同步成功改成可能产生不可识别异步状态
```

新增 Enum 值：

```text
不自动视为兼容
```

如果消费者使用 exhaustive switch，新值可能是 Breaking。

必须按真实消费者判断。

---

# 4. 通常可以视为兼容的变更

在 Schema 和消费者约定允许的前提下：

```text
新增可选字段
新增独立 API
新增独立 Event Type
新增不会改变已有结果的新查询能力
改进 human-readable message
修正文档
```

但如果消费者明确：

```text
additionalProperties: false
```

则向同一对象直接新增字段可能导致校验失败。

因此“新增字段”是否兼容必须和 Schema 策略共同判断。

---

# 5. 默认 Schema 演进策略

为了避免隐式扩展：

```text
公共对象默认 additionalProperties: false
```

若预计对象会频繁扩展：

优先：

```text
明确升级 MINOR Contract
```

或设计：

```text
extensions: {}
metadata: {}
```

这类明确扩展点。

不要依赖消费者“碰巧忽略未知字段”。

---

# 6. Producer / Consumer 兼容矩阵

每个 Public Contract 发布时至少应知道：

```text
Producer Version
Consumer Version
Supported Range
```

领域设计阶段不要求建设自动矩阵系统，但必须记录真实消费者。

如果一个 Public Contract 没人知道谁在消费：

> 它还不具备安全演进条件。

---

# 7. Deprecated

废弃流程：

```text
标记 Deprecated
→ 给替代方案
→ 保持兼容窗口
→ 迁移消费者
→ 验证无消费者
→ 下一 MAJOR 删除
```

禁止：

```text
今天标 Deprecated
明天删除
```

除非当前 Contract 明确仍处于未对外使用的实验阶段。

---

# 8. Version Negotiation

跨设备 / 跨进程协议如需要协商版本：

```text
Producer SHOULD 声明 supportedContractVersions
Consumer SHOULD 明确自己要求的版本
```

若没有共同版本：

```text
必须明确失败
```

不能自动“猜一个差不多能用”的 Schema。

---

# 9. Event Version

Event 本身必须能确定其 Contract Version。

推荐：

```text
contractVersion
```

不要依赖：

```text
eventType = EXECUTION_DELIVERED_V2
```

把版本硬编码进事件名。

Event Type 描述业务事实，Version 描述 Schema / Contract 版本。

---

# 10. Persisted Data Migration

Public Contract Version 变化不等于数据库必须同步变化。

领域内部可以：

```text
旧 DB Model
→ Adapter / Mapper
→ 新 Public Contract
```

数据库 Migration 属于领域内部实现。

只有当持久化格式本身被其他独立组件共享时，才需要作为公共版本管理对象。

---

# 11. Adapter Compatibility

Browser / Local / MCP（future / non-v1）/ A2A / Model Provider Adapter：

```text
必须明确自己实现的 Public Contract Version
```

Adapter 版本升级不能静默改变领域语义。

例如：

```text
Browser Adapter 2.0
```

可以改变浏览器实现，但如果：

```text
Delivery
Receipt
Side-effect certainty
```

语义变化，就必须对应 Execution Contract 版本变化。

---

# 12. Runtime Compatibility

部署领域必须能够最终回答：

```text
当前安装版本
当前运行版本
提供的 Contract Version
兼容的平台版本范围
```

第一版不强制所有模块立即实现完整版本协商。

先保证：

```text
版本事实可表达
不靠文件名猜版本
```

---

# 13. Breaking Change 流程

Breaking Change：

```text
提出变更
→ 枚举 Producer / Consumer
→ Impact Analysis
→ 确定迁移方案
→ MAJOR Version
→ 双版本 / 迁移窗口（如需要）
→ Contract Test
→ Integration Test
→ 删除旧版本
```

详见：

`07-约定变更机制.md`

---

# 14. 内部实现版本

Internal API：

```text
MAY 快速演进
```

只要不改变 Public Contract。

这是领域独立迭代的重要自由。

因此：

> 不要把内部 class / DB model / helper 暴露成 Public，只为了少写 Mapper。

Mapper 的成本远低于跨域耦合后的长期升级成本。

---

# 15. 从 v0.x 到 v1.0

平台各领域约定自身：

```text
v0.x
```

允许在五领域设计过程中受控修正。

当完成：

```text
五个领域第一版设计
五域 Provides / Requires 接口矩阵
至少一轮 Contract Review
部署 Module 形态校准
```

再评估：

```text
平台各领域约定 v1.0
```

v1.0 后 Breaking Change 必须更加严格。

---

## 当前正式约束：变更控制

兼容字段新增可在同 major 演进；破坏性语义变更升级 major，并走 Contract Change。任何领域不得单方面改变公共语义。字段或接口被新 Contract Version 取代时，必须显式声明 `deprecated`、替代目标、兼容窗口和移除条件，不允许静默替换。
