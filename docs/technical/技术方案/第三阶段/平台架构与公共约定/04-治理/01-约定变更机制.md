# 07｜约定变更机制

> 状态：FROZEN  
> 目标：允许平台约定随着五领域真实实现与验证结果演进，但禁止任何领域单方面改变全平台共同语义。

---

# 1. 什么时候不需要平台变更

如果变化只影响一个领域内部：

```text
内部状态
内部类
Repository
数据库 Schema
内部 Adapter
内部错误
内部算法
```

并且：

```text
不改变 Public Contract
不改变其他领域依赖
```

则：

> 领域自己决定。

无需升级平台各领域约定。

---

# 2. 什么时候属于 Public Contract Change

以下变化至少属于领域 Public Contract Change：

```text
Public API
Public Event
Public Schema
Public Error
Public Ref
幂等语义
并发语义
副作用语义
版本兼容规则
```

要求：

```text
Provider / Consumer Impact Analysis
Version Decision
Contract Test
```

---

# 3. 什么时候属于 Platform Convention Change

如果变化影响：

```text
两个及以上正式领域的共同交互规则
```

或改变：

```text
ID / Ref 公共规则
Event Envelope
Error Envelope
Version 规则
Public / Internal
Dependency Rule
Package Rule
Testing Gate
```

则属于：

> **Platform Convention Change**

必须修改本目录对应文档。

---

# 4. 最小变更流程

不建立复杂治理系统。

统一四步：

```text
1. 提出真实问题
2. 列出影响
3. 决定变更与版本
4. 更新约定 + 受影响 Contract / Test
```

必须先回答：

```text
当前规则为什么不够？
来自哪个真实领域需求？
是否只是单领域问题？
影响哪些领域？
是否 Breaking？
是否有更小的局部解决方案？
```

---

# 5. 变更提案最小格式

可以在 PR / Issue / ADR / 设计文档中使用：

```text
标题
问题
触发领域
当前约定
建议变更
影响领域
兼容性
迁移
测试
版本
```

不强制新建独立 Governance 系统。

---

# 6. 优先局部，谨慎上升平台规则

公共约定必须来自真实重复需求。

如果只有：

```text
Task 需要一个特殊字段
```

默认：

```text
Task 自己定义
```

直到：

```text
Agent / Execution 也出现相同语义
```

才评估是否抽到平台。

原则：

> **不要把“可能复用”当作“已经公共”。**

---

# 7. Breaking Change

Breaking Platform Convention：

```text
必须做 Impact Analysis
必须更新版本
必须更新所有受影响 Consumer
必须有迁移顺序
必须有 Contract / Integration 证明
```

如果暂时无法同步升级：

```text
允许双版本兼容窗口
```

禁止：

```text
直接修改 v1 语义，让旧消费者运行时再发现问题
```

---

# 8. 领域不得单方面修改公共语义

禁止：

```text
Task 因实现方便重新定义 correlationId
Agent 因 SDK 方便改变 Event Envelope
Execution 因 Adapter 方便改变 Ref 解析规则
Inference 因 Provider 限制改变公共 Error 语义
Deployment 因 CLI 方便改变所有 Contract Version 表达
```

如果确实需要：

```text
必须提升为 Platform Convention Change
```

---

# 9. 紧急 Hotfix

如果线上 / 真实验收出现：

```text
安全问题
数据损坏
重复副作用
不可恢复兼容错误
```

允许先做最小 Hotfix。

但：

```text
Hotfix MUST 不扩大变更范围
MUST 在同一修复周期补齐 Contract / Convention 记录
MUST 明确临时行为是否成为长期语义
```

Hotfix 不是绕过治理的永久入口。

---

# 10. 约定版本

公共约定通过 Git 和 Contract Version 独立演进。文档自身不额外维护与业务 Contract 重复的版本体系；真正影响消费者兼容性的变化必须体现在对应 Contract Version 中。

当机器可消费的公共 Convention Schema 或 Contract 发生 Breaking Change 时，必须升级对应 major version，并明确 Producer / Consumer 兼容窗口。纯文档解释性修订不单独制造版本号。

---

# 11. 约定和 ADR

以下适合 ADR：

```text
为什么采用五领域
为什么 Approval 不独立
为什么 Execution 统一 Browser / Local，以及 MCP 仅保留 future / non-v1 adapter slot
为什么 Memory 不独立
为什么采用特定消息总线
为什么选择重大技术边界
```

以下更适合本目录：

```text
Event Envelope 字段
Ref 规则
Version 规则
Public / Internal
Contract Test Gate
Package dependency rule
```

ADR 解释重要决策原因。

平台各领域约定规定当前必须遵守的规则。

---

# 12. 变更完成条件

Platform Convention Change 完成至少满足：

```text
[ ] 文档已更新
[ ] 影响领域已列出
[ ] Compatibility 已判断
[ ] Public Contract 已更新
[ ] Producer Test 已更新
[ ] Consumer Test 已更新
[ ] 必要 Integration 已验证
[ ] Breaking 时迁移方案已存在
```

缺一项不能声称完成。

---

# 13. 五领域协同变更工作方式

公共约定与领域 Contract 采用证据驱动的闭环：

```text
领域实现 / 测试 / 外部能力变化产生证据
        ↓
定位受影响的 Public Contract 与 Producer / Consumer
        ↓
执行 Impact Analysis 与 Compatibility 判断
        ↓
必要时提交 Contract Change
        ↓
同步 Provider / Consumer Contract 与测试
        ↓
执行跨领域 Integration / E2E 验证
        ↓
满足发布门禁后生效
```

领域不得因为自身实现便利直接改变公共语义；公共约定也不得脱离真实领域需求预设复杂能力。

---

## 当前正式约束：文档与实现治理

五领域的公共语义变更必须以 Contract Change 管理，并可追踪到 domain / document / section / change type / reason / affected producer-consumer。实现阶段只有真实代码、测试、E2E、故障注入或外部能力变化等证据可以触发 Contract Change；不得因为实现便利而无证据扩大公共语义。
