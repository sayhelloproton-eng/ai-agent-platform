# 01 · 领域职责边界与非目标

## 1. [FROZEN] Model Domain 的唯一业务价值

Model Domain 不是“大模型接入平台”，而是给其他领域提供一层**稳定、可替换、受规范约束的认知算力**。

其输出必须能被调用领域作为“判断输入”依赖，但不能越权成为业务事实或执行授权。

## 2. 领域所有权矩阵

| 事项 | 所有领域 | Model Domain 角色 |
|---|---|---|
| Task/Node/Run 状态 | Task | 仅接收调用方传来的 opaque context |
| Role/Worker/Conversation | Agent | 不拥有、不维护 |
| Collaboration | Agent | 可被请求做判断，但不创建消息事实 |
| File/Git/Shell/Browser effect | Execution | 只给 judgment/proposal，不执行 |
| Scope / Policy | Execution/调用领域 | 不覆盖 hard rules |
| Human/Effect Approval | 所属业务领域 | 可返回 `ESCALATE`，不创建审批 |
| 模型角色映射 | Model + Deployment config | Model 定义能力要求；Deployment 写配置 |
| Provider credentials/base URL | Deployment | 运行时只消费，不向上层暴露 |
| Reasoning Spec | Model | 领域真源 |
| 推理日志 | Model | 落盘到平台统一日志根 |

## 3. [FROZEN] Context 所有权

调用方必须自己准备所需业务上下文。

Model Runtime 接受“已经组装好的认知输入”，不反向读取其他领域数据库。

理由：

1. 防止 Model Domain 偷偷变成第二个 Controller；
2. 防止同一问题因为隐藏上下文变化而不可复现；
3. 让 Reasoning Spec 输入可以完整测试；
4. 让权限边界保持在数据拥有领域。

## 4. [FROZEN] 判断不是授权

对所有调用领域都成立：

```text
Model Judgment
≠ Business Decision
≠ Effect Approval
≠ Execution Authorization
```

模型结果必须回到调用领域的确定性规则中。

## 5. [FROZEN] v1 非目标

v1 不实现：

- 自主 Agent runtime；
- 长链 planning；
- Tool Calling runtime；
- tool registry；
- provider marketplace；
- model marketplace；
- 多租户模型资源池；
- 持久化推理任务中心；
- Prompt 运营平台；
- 模型训练/微调；
- Embedding/RAG/Knowledge Retrieval；
- 长 CoT 保存；
- 自动从互联网发现模型；
- 根据价格动态套利/多云路由。

这些都不是当前第一版稳定闭环的必要条件。

## 6. [FROZEN] 旧 MVP 治理

旧 SOL-MOB-001、历史脚本、实验包只可提供：

```text
已验证模型能力
真实 latency
错误/故障经验
输入输出稳定性证据
可复用实现候选
```

不能决定：

```text
领域边界
包数量
Public Contract
Reasoning Spec 语义
状态模型
服务拓扑
```

复用必须在领域冻结后做 `REUSE / REFACTOR / REWRITE / DROP` 审计。
