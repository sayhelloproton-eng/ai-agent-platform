# 13 · 测试验收：M1 ~ M4

## 1. [FROZEN] M1 — Contract Gate

纯自动化测试，必须覆盖：

- `model-contracts` 类型编译；
- Reasoning Spec 定义合法；
- input/output runtime schema；
- unknown→typed boundary；
- FAST/REASON/AUTO mode rules；
- Capability Proposal 只能选候选能力；
- one proposal per inference；
- bounded repair；
- error normalization；
- RuntimeStatus schema。

**停止门**：M1 不通过，禁止接真实模型。

## 2. [FROZEN] M2 — Model Capability Gate

对部署配置的真实 API 模型执行。

FAST：

- text；
- no-thinking 行为；
- structured output；
- Vision（若声明）；
- context/output limit sanity；
- latency baseline。

REASON：

- text；
- thinking/reasoning；
- structured output；
- Vision（若声明）；
- latency baseline。

**停止门**：声明能力与实测不一致，role 标记 UNAVAILABLE。

## 3. [FROZEN] M3 — Reasoning Spec Scenario Regression

每个进入生产控制路径的 Spec 都必须有固定 Case，而不是只测普通聊天。

第一批建议场景族：

```text
execution.command-risk
execution.evidence-conflict
execution.unknown-recovery
browser.page-state
browser.progress-gap
system.health-assessment
capability.proposal
```

每组至少有：

- 正例；
- 否例；
- 边界；
- 低置信/ESCALATE；
- invalid output defense。

指标优先：

- route correctness；
- schema validity；
- decision correctness；
- false-allow / false-deny 的关键风险。

## 4. [FROZEN] M4 — Stability / Performance Gate

必须按真实单 Lane 连续跑，而不是单个 benchmark：

```text
FAST
FAST
FAST + image
FAST
REASON
FAST
...
```

记录：

- sustained success rate；
- schema pass rate；
- routing pass rate；
- queue latency；
- inference latency；
- total latency；
- timeout/error distribution；
- FAST/REASON role switching 稳定性。

## 5. [FROZEN] 替换模型的验收规则

任何 FAST/REASON 模型替换都必须重新跑：

```text
M2 + 受影响 Reasoning Specs 的 M3 + 关键 M4
```

不能只因为 API schema 相同就认为等价。

## 6. [DEFERRED] Deployment verify/doctor

M2/M4 的具体 CLI 编排留给最终 Deployment Domain；本领域只冻结测试语义与 PASS 标准。

---

## 当前正式约束：测试门

M1 增加 runtime validation/contract provider tests；M2/M3 继续以真实 Capability Profile + ReasoningSpec 场景验收；M4 保持真实需求相关 latency/queue/stability/sustained gate，不追求无业务依据 QPS。跨域关键 Contract 变化必须跑受影响 E2E。
