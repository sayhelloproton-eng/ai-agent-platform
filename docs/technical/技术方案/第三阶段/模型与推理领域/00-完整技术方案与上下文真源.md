# 00 · Model & Reasoning Domain 完整技术方案与上下文真源

## 0. 文档目的

本文件是 Phase 3 Model & Reasoning Domain v1/P0 的第一技术真源。它不以旧手机模型 MVP 的代码组织为起点，而是依据已冻结的 Task / Agent / Execution 边界与平台真实需求独立设计。

实现者只读本文件，应能够回答：

- Model Domain 为什么存在、拥有什么、不拥有什么；
- 其他领域到底如何依赖这层算力；
- FAST / REASON / AUTO 是什么；
- thinking / no-thinking / Vision / structured output 如何成为稳定性约束；
- 为什么模型 API 不需要原生 Tool Calling；
- 小模型如何通过 Reasoning Spec、结构化 Proposal 与有限循环稳定工作；
- 2 包 / 1 服务 / 6 模块如何落地；
- Runtime 如何串行调度、校验、路由、记录日志和暴露健康；
- 模型替换、远端 API、本地 API 如何在不改变领域合同的前提下工作；
- v1 明确不做什么，以及何时必须停止继续设计。

---

## 1. [FROZEN] 领域 Charter

### 1.1 定义

**Model & Reasoning Domain 是平台的认知计算层。**

它接收调用领域已经形成的上下文、证据和问题，将这些输入交给满足能力要求的 API 模型，以受控推理强度完成一次认知计算，校验输出并返回调用方可以可靠消费的结构化结果。

它提供的是“可依赖算力”，而不是“一个 LLM HTTP wrapper”。

### 1.2 核心句

> **模型不是自由 Agent，而是受协议约束的认知函数。**

> **Small-model-first：平台正确性不得依赖模型开放式自主智能。**

关键推理必须依靠：

```text
Reasoning Spec
+ typed input
+ bounded context
+ constrained output
+ runtime validation
+ bounded FAST→REASON escalation
+ bounded capability proposal rounds
```

### 1.3 正式职责

Model Domain owns：

- 模型 API 接入与 Provider 适配；
- FAST / REASON / AUTO 逻辑算力角色与物理模型映射；
- 单一 inference lane 的资源协调；
- 版本化 Reasoning Spec；
- 确定性 Prompt 渲染；
- 结构化推理输出解析与 runtime validation；
- 模型能力画像与调用前能力校验；
- 推理超时、有限 retry / repair；
- Runtime health；
- 推理日志与稳定性可观测；
- 模型能力合格标准和 M1~M4 验收定义。

### 1.4 明确不拥有

Model Domain does **not** own：

- Task 状态、Node 进度、Plan、Task 完成判定；
- Agent Role、Worker、Conversation、Collaboration；
- File / Git / Shell / Browser 等真实执行；
- Scope / Policy 的最终业务裁决；
- Effect Approval 或其他业务审批；
- 浏览器页面状态真源；
- Deployment 安装、凭证管理、Provider endpoint 配置生命周期。

模型可以给出判断，但判断不能直接改变其他领域事实。

## 2. [FROZEN] 与其他领域的关系

```text
Task & Orchestration
→ 决定“现在该推进什么业务事实”

Agent Runtime & Collaboration
→ 决定“谁在做、谁和谁协作、上下文归谁”

Model & Reasoning
→ 提供“这件事如何判断”的受控认知算力

Execution
→ 把 Intent 变成真实 Effect + Evidence

Deployment
→ 最终负责安装、配置、启动、verify/doctor
```

### 2.1 Execution → Model

Execution 可请求：

- command / mutation risk judgment；
- evidence conflict judgment；
- UNKNOWN recovery 的认知判断；
- Browser screenshot / page-state Vision judgment；
- System Observer 的稳定性判断。

但 Execution 仍保留 hard rules、Scope、Policy、Approval 与最终执行权。

```text
Model: decision=ALLOW
Execution hard scope: DENY
→ 最终 DENY
```

### 2.2 Agent → Model

Agent 可在未来或 P0 需要时请求：

- 分类；
- 抽取；
- 结构化判断；
- 深推理。

Model 不读取 Agent Registry，不拥有 Role/Worker。

### 2.3 Task → Model

v1 原则上 Task Domain 不需要直接依赖 Model Runtime。Task 管理确定性工作流事实，不应把 Task 状态机决策委托给模型。

### 2.4 Deployment → Model

Deployment 最终负责配置：

```text
FAST → configured API model
REASON → configured API model
provider wire settings / base URL / credentialRef / model id
```

Model Domain 定义“一个配置模型要满足什么能力才算合格”；Deployment 负责把它装好、验证好。

## 3. [FROZEN] v1 包 / 服务 / 模块

```text
Model & Reasoning Domain v1

├── model-contracts
│   └── TypeScript npm library；不部署
│
└── model-runtime
    └── 唯一平台 Runtime Service
```

v1 不新增：

```text
model-router-service
model-provider-service
model-health-service
model-vision-service
model-scheduler-service
prompt-service
tool-service
model-registry-service
evaluation-service
```

## 4. [FROZEN] 对外暴露逻辑算力，而不是具体模型

上层只认：

```text
FAST
REASON
AUTO
```

不认：

```text
某个 Qwen model id
MLXHub
手机 IP
LAN URL
某个云厂商 endpoint
OpenAI-compatible 参数细节
```

### FAST

逻辑目标：

- 高频；
- 低延迟；
- no-thinking；
- 结构化控制输出稳定；
- 在 Spec 需要时支持 Vision。

### REASON

逻辑目标：

- 低频；
- thinking / reasoning；
- 用于证据冲突、复杂不确定性、FAST 无法可靠判断；
- 在 Spec 需要时支持 Vision。

### AUTO

AUTO 不是第三模型；它表示 Runtime 可以按照当前 Reasoning Spec 的静态规则进行有限 FAST→REASON 选择/升级。

**FAST 不可用时不能偷偷切 REASON；REASON 不可用时不能偷偷降 FAST。只有 AUTO + Spec 明确允许时才可升级。**

---

## 5. [FROZEN] Vision 是输入模态，不是第三种模型角色

```text
FAST + image
REASON + image
```

调用方表达的是“这次推理包含 image”，不是“调用 Vision Service”。

Provider Adapter 将统一 image ContextPart 转成具体 API 格式；如果目标模型不支持 image：

```text
CAPABILITY_UNSUPPORTED
```

禁止丢弃图片后继续文本推理。

---

## 6. [FROZEN] API Provider Adapter 必须通用

本领域不固化 MLXHub 或手机资源。

模型可能由：

```text
本机 API
手机 API
LAN Server
云 API
企业内部 API
```

提供。

Provider Adapter 只负责：

- 将统一 InferenceRequest 转换为具体模型 API 请求；
- 处理 provider wire protocol；
- 将 provider response/error 标准化；
- 转换 text/image payload；
- 隐藏 base URL、credential、model id 与 provider-specific 参数。

这些具体配置属于 Deployment/Provider 配置，不是跨领域业务合同。

v1 只有一个通用 API Provider Adapter 位置；不建设 Provider Plugin Framework。

---

## 7. [FROZEN] Model Capability Profile

具体模型能否承担 FAST / REASON，不能只看 API 是否返回 200。

每个配置模型必须声明并能被验证至少这些能力：

```text
reasoning mode:
  thinking
  no-thinking

input modality:
  text
  image

structured output:
  native
  prompted
  unsupported

limits:
  context window
  max output tokens
```

以及部署验证得到的稳定性事实，例如典型 latency / schema 合法性。

### 7.1 FAST 资格

至少：

```text
no-thinking
text
structured output 可用
```

若某 FAST Spec 需要 image，则还必须支持 image。

### 7.2 REASON 资格

至少：

```text
thinking
text
structured output 可用
```

若某 REASON Spec 需要 image，则还必须支持 image。

### 7.3 structured output

允许：

```text
native
prompted + strict runtime validation + bounded repair
```

`unsupported` 不能承担平台控制型推理。

## 8. [FROZEN] Small-model-first 与 Reasoning Spec

小模型不是靠长开放 Prompt 自由发挥，而是通过静态版本化 Spec 工作。

典型 Spec：

```text
execution.command-risk.v1
browser.page-state.v1
browser.progress-gap.v1
execution.unknown-recovery.v1
system.health-assessment.v1
capability.proposal.v1
```

每个 Spec 固定：

```text
specRef / version
purpose
allowed modes
required modalities
static instruction
input schema
output schema
decision vocabulary
optional capability proposal allowlist contract
context/output limits
AUTO routing rules
bounded repair rules
```

调用方优先使用：

```ts
infer({
  specRef: "execution.command-risk.v1",
  payload: { ...typed data... },
  mode: "fast"
})
```

而不是把任意自由 Prompt 作为跨领域公共合同。

### 8.1 Prompt Renderer

Runtime：

```text
validate payload
→ resolve static Spec
→ deterministic render
→ provider request
→ raw output
→ parse
→ validate output schema
→ typed InferenceResult
```

Reasoning Spec v1 用 TypeScript 静态定义、Git 版本化；不建设 Prompt Service / Prompt DB。

---

## 9. [FROZEN] 模型 API 不依赖原生 Tool Calling

v1 公共合同没有：

```text
tools
tool_choice
tool_calls
function calling
```

如果推理需要提出下一步真实能力，模型输出：

```text
Capability Proposal
```

而不是 Tool Call。

### 9.1 Capability Proposal 原则

模型只能从调用方显式给出的有限候选能力集合中选择。

模型最多提出：

```text
capability id
strongly-typed arguments
reasonCode / short rationale
confidence
```

禁止：

- 发明未知能力；
- 使用未给出的 capability；
- 携带 secret；
- 直接执行；
- 绕过 Scope/Policy/Approval。

### 9.2 真正执行链

```text
Model Result
→ Proposal schema validation
→ caller-side allowlist validation
→ Execution Scope
→ Execution Policy
→ Effect Approval（如需要）
→ Execution real effect
```

**模型输出永远不是执行授权。**

### 9.3 Result 回灌

Execution Result 若需再次交给模型，必须使用结构化、裁剪后的 Result Envelope；禁止把杂乱 stdout、整个 DOM、超大日志原样回灌。

### 9.4 有限轮次

单次 inference 最多产生一个 Proposal。

是否再调用模型由调用领域决定，并设置有限 `maxRounds`。v1 不允许开放式自主 Tool Loop。

---

## 10. [FROZEN] 模型输入输出规范

平台控制型推理必须结构化。

模型输出不能是：

```text
“我觉得大概可以，你最好再看看……”
```

而应是当前 Spec 定义的有限结果，例如：

```json
{
  "decision": "ESCALATE",
  "confidence": 0.61,
  "reasonCode": "EVIDENCE_CONFLICT",
  "rationale": "目标分支与任务预期不一致"
}
```

Model Runtime 不要求也不持久化长 Chain-of-Thought。平台依赖：

```text
decision
confidence
reasonCode
short rationale
```

而不是内部思维过程。

---

## 11. [FROZEN] Context 所有权

调用领域负责组装输入 Context。

Model Runtime 不：

- 读取 Task SQLite；
- 读取 Agent Registry；
- 读取 Execution Record 数据库；
- 自己决定补哪些业务上下文；
- 偷偷摘要/截断改变语义。

Context 超过 Spec / Model 限制：

```text
CONTEXT_TOO_LARGE
```

调用领域决定是否重新裁剪或改变问题。

---

## 12. [FROZEN] 单一 inference lane

v1 无论模型 API 在手机、本机还是云端，都保持：

```text
one Model Runtime
→ one inference lane
→ one active inference at a time
```

这是平台稳定性策略，不只是手机硬件限制。

### 12.1 优先级

只保留：

```text
business
background
```

- Task / Agent / Execution 正常业务推理：`business`
- Browser System Observer 等后台稳定性判断：`background`

尚未开始的 background 必须让 business；已经开始的 inference v1 不做复杂抢占。

### 12.2 队列不持久化

```text
queue / active inference → memory
history → structured disk logs
```

Runtime 重启时排队/运行中的推理失败，由调用方重新提交；推理没有现实副作用，因此不复制 Execution 的 UNKNOWN_SIDE_EFFECT 恢复模型。

---

## 13. [FROZEN] FAST / REASON / AUTO 路由

### FAST

```text
requested FAST
→ validate FAST role capability
→ FAST only
→ unavailable => MODEL_UNAVAILABLE
```

### REASON

```text
requested REASON
→ validate REASON role capability
→ REASON only
→ unavailable => MODEL_UNAVAILABLE
```

### AUTO

```text
resolve Reasoning Spec routing policy
→ usually FAST
→ only on allowed trigger
   low-confidence / explicit-escalate / evidence-conflict
→ REASON
```

Runtime 执行 Spec 的路由规则，但不发明业务规则。

---

## 14. [FROZEN] 请求生命周期

```text
1. Inference API 接收 request
2. runtime validate envelope
3. resolve Reasoning Spec
4. validate typed payload
5. determine requested/allowed reasoning mode
6. validate model capability profile
7. enqueue business/background
8. Resource Coordinator 获取单 Lane
9. prepare configured role/model
10. Provider Adapter 发起 API inference
11. receive raw output
12. Output Validator parse + schema validate
13. bounded repair（最多一次，如 Spec 允许）
14. AUTO 可按 Spec 有界升级到 REASON
15. 返回 typed InferenceResult
16. 记录结构化推理日志
```

没有业务数据库状态机，没有自主工具循环。

---

## 15. [FROZEN] Timeout / Cancel / Retry / Repair

### Timeout

必须区分：

```text
QUEUE_TIMEOUT
INFERENCE_TIMEOUT
```

前者说明算力繁忙，后者说明本次 provider/model 推理太慢或异常。

### Cancel

- 排队中：直接取消；
- 已运行：Provider 支持 cancel 时尽力 cancel；不支持时调用方停止等待，迟到结果丢弃。

没有 `UNKNOWN_SIDE_EFFECT`，因为 inference 本身不产生真实世界副作用。

### Retry

只有能确认请求尚未真正开始的瞬时 transport failure，最多一次 retry。

### Repair

结构化输出不合法时，如 Spec 允许，最多一次 bounded repair；仍不合法则 `INVALID_OUTPUT`。

禁止无限：

```text
retry
repair
FAST→REASON→FAST
self-loop
```

## 16. [FROZEN] Runtime Health

Public status 最小语义：

```text
Runtime:
  READY | DEGRADED | UNAVAILABLE

Lane:
  IDLE | BUSY

FAST:
  READY | UNAVAILABLE

REASON:
  READY | UNAVAILABLE
```

附最小运行事实：

```text
activeInferenceRef?
activeRole?
businessQueueDepth
backgroundQueueDepth
lastSuccessAt?
lastFailureAt?
lastErrorCode?
```

Health 必须表达真实可依赖状态，不允许仅因为“历史上 API 曾经 200”就显示 READY。

深度模型能力验证属于 Deployment verify/doctor；Runtime health 保持轻量。

## 18. [FROZEN] Public Contract

v1 对外核心 API 只需要：

```text
infer(request)
getRuntimeStatus()
```

不做：

```text
Inference Job API
Scheduler API
Model Registry API
Prompt CRUD API
Tool API
```

`infer()` 使用统一 Envelope + `specRef + typed payload`。

所有跨进程/HTTP 边界数据：

```text
unknown
→ runtime schema validate
→ typed TypeScript object
```

## 20. [FROZEN] 模型能力验证

一个配置角色不是“填上 model id”就算 READY。

FAST 至少验证：

```text
Text PASS
no-thinking 语义符合配置
structured output PASS
latency baseline 可接受
Vision PASS（若声明）
```

REASON 至少验证：

```text
Text PASS
thinking/reasoning 行为符合配置
structured output PASS
Vision PASS（若声明）
```

若声明能力但验证失败：

```text
role = UNAVAILABLE
```

具体 verify/doctor 命令由 Deployment 最终设计，能力合格标准由 Model Domain 定义。

## 21. [FROZEN] 测试 Gate

### M1 — Contract Gate

验证：

- Reasoning Spec TS 类型；
- input/output schema；
- runtime validation；
- Proposal allowlist；
- bounded repair；
- FAST/REASON/AUTO routing。

### M2 — Capability Gate

对真实配置模型验证：

- FAST text/no-thinking/structured/Vision（如声明）；
- REASON text/thinking/structured/Vision（如声明）。

### M3 — Scenario Regression Gate

跑真实平台控制场景：

```text
ALLOW / DENY / ESCALATE
Scope conflict
Evidence conflict
Capability Proposal
UNKNOWN recovery judgment
Browser screenshot page-state
Progress Gap
System health assessment
```

每个 Reasoning Spec 应有固定回归集。

### M4 — Stability / Performance Gate

按真实单 Lane 串行负载：

```text
FAST → FAST → Vision → FAST → REASON → ...
```

评估：

```text
成功率
schema 合法率
route 正确率
latency
queue latency
timeout
角色切换
持续稳定性
```

## 24. [FROZEN] 防过度设计停止规则

> **满足需求和稳定性就停止。**

如果某设计不能回答以下至少一项，就不进入 v1：

```text
它是否是当前跨领域真实调用链所必需？
它是否解决已经确认的稳定性风险？
它是否是部署验证所必需？
它是否是验收 Gate 所必需？
```

全部为“否”时：删除或延后。

---

## 25. 最终工程锚点

> **Model Runtime 不替其他领域做决定，它只可靠地完成受规范约束的认知计算。**

> **FAST / REASON 是逻辑算力角色；API Provider 是实现通道；Model Capability Profile 决定具体模型是否有资格承担逻辑角色。**

> **Reasoning Spec 才是小模型稳定性的核心合同。**

> **模型提出 Capability Proposal，Execution 才拥有真实 Effect。**
