# 02 · 总体架构、包、服务与运行拓扑

## 1. [FROZEN] 2 包 / 1 服务

```text
packages/
  model-contracts/
  model-runtime/
```

`model-contracts`：纯 TS library。

`model-runtime`：唯一模型与推理后端服务。

## 2. [FROZEN] 六个内部模块

```text
model-runtime
├── Inference API
│   ├── Reasoning Spec Resolver
│   └── Prompt Renderer
├── Resource Coordinator
├── Reasoning Router
├── API Provider Adapter
├── Output Validator
└── Health & Observability
```

这些是源码模块，不是六个服务。

## 3. 运行拓扑

```text
Agent --------------------┐
Execution ----------------┼──→ Model Runtime Service
Browser System Observer --┘            │
                                       │ API
                              ┌────────┴────────┐
                              ▼                 ▼
                         FAST model        REASON model
                         configured API     configured API
```

FAST/REASON 可以指向：

- 同一 Provider 的两个模型；
- 同一个模型的两种明确 reasoning mode；
- 完全不同远端 API；
- 本地/手机/局域网 API。

领域合同不改变。

## 4. [FROZEN] 为什么不拆 Provider 包

v1 当前只需要一个统一 API Adapter 位置。拆独立 Provider 包会引入：

- plugin lifecycle；
- provider registry；
- provider compatibility matrix；
- 更多发布单元。

在没有第二类真实 Provider 实现需求前都没有价值。

## 5. [FROZEN] 为什么单 Lane 即使远端 API 也保留

单 Lane 是第一版稳定性选择：

- 行为可复现；
- FAST/REASON 不互相抢调度；
- background 易于让路；
- 日志顺序清楚；
- 小模型的并发不确定性不会扩散；
- 不需要复杂 queue/scheduler。

未来只有真实吞吐瓶颈被 M4 证明后才允许扩并发。

---

## 当前正式约束：部署依赖

`model-runtime` 保持独立 Service/Process/Deployment Unit。FAST/REASON 是 Model 逻辑角色，不是 Deployment Provides。物理 Provider 必须作为 Deployment External Resource Module，通过 `moduleRef`/逻辑 `model.provider.api` 解析；Model Runtime 不私藏旁路 endpoint 作为跨域真源。
