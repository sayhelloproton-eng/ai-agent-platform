# 02｜运行时与模型选型

> 核心问题：为什么最终是 MLXHub LAN Server，以及为什么 FAST/REASON 都选 Qwen3.5-4B？

## 1. 设备与 Runtime 基线

| 项 | 当前冻结 |
|---|---|
| 设备 | iPhone 17 Pro |
| 运行方式 | MLXHub LAN Server，可信局域网实验环境 |
| FAST | `sayhelloproton/Qwen3.5-4B-MLX-4bit-no-think` |
| REASON | `mlx-community/Qwen3.5-4B-MLX-4bit` |
| 同时运行模型 | 不并发；按请求切换 / 串行 |
| 推理并发 | `max_inference_concurrency = 1` |
| 资源锁 | `runtime_model_lock` / provider-global serial lane |

局域网 IP、端口和“当前安装了几个模型槽位”都是实验部署事实，不是公共合同。

## 2. 为什么 MLXHub 成为最终 Runtime

真机已经实际验证：

```text
GET  /health
GET  /v1/status
GET  /v1/models
POST /v1/chat/completions
```

以及：

- Text；
- Streaming；
- 多轮；
- `image_url` inline Base64；
- HTTP image URL；
- 模型 ID 显式选择；
- FAST → REASON → FAST 切换；
- OpenAI-compatible 客户端接入。

这让 MLXHub 满足了“**平台 Provider**”而不仅是“本地聊天 App”的最低条件。

## 3. FAST 模型

### 3.1 来源

```text
base checkpoint:
mlx-community/Qwen3.5-4B-MLX-4bit

FAST artifact:
sayhelloproton/Qwen3.5-4B-MLX-4bit-no-think
```

FAST 只调整 Chat Template 以默认抑制 Thinking，模型权重不变。

### 3.2 为什么要 no-think

平台的大多数高频工作不是开放式长推理，而是：

- 读 Task/Node/Evidence；
- 分类状态；
- 做结构化候选判断；
- 识别截图；
- 判断是否需要 Approval；
- 选择 allow-listed script/capability；
- 验收结构化执行结果。

让这些请求默认进入长 Thinking 会浪费大量同步延迟，并使 JSON 输出更难稳定。

### 3.3 当前定位

**FROZEN**：

```text
FAST = default / high-frequency path
```

它不是低智能“路由器”，而是承担平台日常绝大多数受约束理解与判断。

## 4. REASON 模型

### 4.1 为什么不能靠一个模型 ID 动态开关 Thinking

实测以下请求参数不能可靠改变原始 Qwen3.5 的 Thinking 行为：

```text
enable_thinking
chat_template_kwargs.enable_thinking
additionalContext
additional_context
chat_template_args
reasoning_effort
```

对原始 Qwen 模型的官方能力探针中，多个“关闭 Thinking”的变体仍然显示 `<think>`，典型单次耗时约 45~79 秒。

因此当前实现不是：

```text
same model id + thinking=true/false
```

而是：

```text
FAST model id   != REASON model id
```

### 4.2 当前定位

**FROZEN**：

```text
REASON = explicit low-frequency escalation path
```

适用：

- evidence conflict；
- state contradiction；
- unknown side effect；
- high-risk ambiguity；
- complex causal diagnosis；
- 多个安全候选都说得通、FAST 不应猜测时。

## 5. Gemma 为什么退出主线

Gemma 曾经有三层角色：早期冷启动候选、模型能力对照、Tool/Agent 对照。后来退出主线的原因是组合性的：

1. 不同 Gemma 资产/Runtime 兼容性不稳定；
2. 一些可用版本是 text-only，不能替代 FAST 的 Vision 职责；
3. Qwen no-think 已满足高频 FAST；原始 Qwen 又能复用为 REASON；
4. 两个模型槽位更适合保留同一家族的 FAST/REASON，而不是继续维持一个缺乏明确职责的对照模型。

Gemma 的历史实验仍保留，因为它证明了“模型资产格式 / Serving Runtime 兼容性”必须实测，不能只看模型卡。

## 6. Privacy AI 与 MLXHub 的关系

Privacy AI 属于比较性验证，不是当前正式 Provider。它证明：即使都宣称 OpenAI-compatible，不同 iPhone App 的 `/status`、模型命名、Gateway 语义、模型暴露方式也可能差异明显。

长期平台抽象因此必须是：

```text
logical role / required capability
        ↓
Inference Backend / Provider Adapter
        ↓
physical endpoint + model mapping
```

而不是把 App 特有 API 泄漏到 Flow 或 Agent。
