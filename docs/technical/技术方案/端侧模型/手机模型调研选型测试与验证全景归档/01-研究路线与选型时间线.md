# 01｜研究路线与选型时间线

> 核心问题：手机模型路线是怎样从“端侧节点构想”演化为当前 MLXHub + Qwen FAST/REASON 的？

## 2. 最早构想中哪些东西保留了

早期方案虽然把 Gemma 4 E4B、Qwen3.5-9B、LoRA、端侧 RAG 等都列为候选，但几条架构原则后来被多次真实实验验证：

- 手机模型不是 Controller；
- 模型输出是 Observation / Classification / Candidate / Proposal；
- Tool / Browser / File / Task / Approval 的真值和执行权不在手机模型；
- 一个 Runtime 可以服务多个逻辑角色，但 Prompt、History、Task Context、Output Contract 必须隔离；
- 角色不能靠用户 Prompt 自行升权；
- 模型品牌和物理设备不能写进上层业务合同。

这些原则从 Proposal 演化成后来的 Provider / Execution Flow Runtime 边界。

## 3. 被淘汰或降级的路线

### 3.1 自建 iPhone Model Host

**SUPERSEDED**。

讨论过 fork Off Grid、llama.rn / React Native、自写 HTTP Server 等方式。最终放弃的核心原因不是“技术上绝对做不到”，而是当时开发环境与维护成本不匹配：老 Mac、iOS 工具链、自建 Native Runtime/HTTP 服务都会把手机模型研究变成新的产品开发项目。

因此路线收敛为：先使用现成可安装 App，验证“设备上的模型服务是否真的能成为平台 Provider”。

### 3.2 Lekh AI

**HISTORICAL CANDIDATE**。

它一度是“现成 App”路线的优先测试对象，但没有形成后来 MLXHub 那样完整、持续的 LAN API / Vision / 模型切换 / 长上下文 / Tool Proposal / Runtime Integration 证据链，因此没有进入最终冻结基线。

### 3.3 Privacy AI

**HISTORICAL COMPARATOR**。

做过 API / model list / context 等比较性测试。其 Gateway 行为和 MLXHub 不完全一致，例如 `/v1/status` 并不是相同的 JSON Runtime Contract。最终没有成为正式 Runtime。

### 3.4 Gemma

**HISTORICAL COMPARATOR / SUPERSEDED MAINLINE**。

Gemma 4 E4B 在早期被设想为冷启动模型和 Qwen 对照；测试中还遇到不同 MLX / llama.cpp 资产和兼容性问题。后来 `DreamFoundries/gemma-4-E4B-it-4bit` 作为 text-only 对照进入过模型槽位，但随着 Qwen no-think + original-thinking 双模型路线稳定，Gemma 退出正式主线。

### 3.5 Qwen3.5-9B + LoRA

**HISTORICAL TARGET DESIGN**。

早期把 9B + LoRA 视作“最终执行模型候选”，但后续 4B Qwen 已通过大量结构化判断、Vision、Tool Proposal 和平台场景 gate，因此没有理由把 LoRA/9B 训练继续作为当前前置。

## 4. 最终选型形成的关键转折

真正决定当前路线的不是单一 benchmark，而是多项证据同时成立：

```text
MLXHub LAN Server
+ OpenAI-compatible chat API
+ Base64 / HTTP image Vision
+ Qwen3.5-4B no-think 的稳定结构化输出
+ 原始 Qwen3.5-4B 的 Thinking 路径
+ 模型切换可验证
+ Tool Proposal 可用
+ Runtime 能串行管理两类模型
+ Execution Flow 能把模型降级为受约束 inference node
```

因此最终选择的是“**可替换 Provider + 明确角色 + Runtime 控制**”，而不是“某个手机模型成为智能体本身”。
