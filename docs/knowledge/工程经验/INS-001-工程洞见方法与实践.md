# INS-001 工程洞见方法与实践

## 1. 文档定位

工程经验不能只记录“发生了什么”，也不能从一次事件直接生成全局定律。

本文把已有证据支持的具体工程事件，归纳为可以在后续任务中使用的：

- 工程判断；
- 工程模式；
- 工程反模式；
- 工程启发式；
- 工程检查清单；
- 洞见演进规则。

本文是面向人类和飞书的综合阅读视图。成熟度、生命周期、Occurrence、关系和来源以
[`Engineering Insight Registry`](../../technical/元数据/engineering-insights/)
为唯一主记录。

## 2. 工程判断

### 2.1 外部调用者表达意图，受信任边界掌握内部控制权

外部调用方只提交业务意图和必要参数。身份、权限、路由、执行者、任务生命周期和内部协议字段，应由受信任服务端根据认证上下文和端点语义生成。

适用于 LLM Tool Calling、第三方 Agent、Webhook、浏览器扩展和公共 API 到内部工作流。

对应洞见：`EI-INTENT_ADAPTER_001`。

### 2.2 最终完成必须由真实用户路径证明

内部组件、相似接口、预览环境和局部测试只能证明对应层级。正式完成需要覆盖用户实际经过的入口、认证、路由、协议和关键响应语义。

对应洞见：`EI-REAL_PATH_001`。

### 2.3 权限不是一个开关

网络可达、身份认证、能力授权、用户意图确认和运行时策略保护不同风险，由不同主体控制。放开其中一层，不能替代其他层。

对应洞见：`EI-LAYERED_AUTH_001`。

### 2.4 探索方案先匹配当前目标

MVP 和技术预研首先需要证明核心假设。选型应优先控制组件数量、远端状态、配置漂移、首次可运行时间、可观察性和回滚成本。

对应洞见：`EI-PHASE_FIT_EXIT_001`。

### 2.5 复审强度由风险增量决定

已有可信基线后，应根据实际差异、信任边界、可逆性和既有证据有效性选择复审深度，而不是每次从零重复全量审计。

对应洞见：`EI-RISK_REVIEW_001`，当前成熟度为 `candidate`。

## 3. 工程模式

### 3.1 Intent Adapter Pattern

```text
外部调用方
   │ 业务意图 + 必要参数
   ▼
受信任适配层
   ├── 身份注入
   ├── 能力白名单
   ├── 参数校验
   ├── 协议补全
   └── 内部对象构造
   ▼
内部执行系统
```

该模式缩小外部契约，避免概率性调用方进入内部控制面，并让外部适配测试与内部契约测试分离。

### 3.2 Real-Path Verification Pattern

```text
单元测试
  → 内部集成测试
  → 外部适配测试
  → 正式用户入口验证
  → 自动回归
```

每一层证明不同事实。最终验收必须使用正式入口、真实认证、真实请求形态和关键响应断言。

### 3.3 Layered Authorization Model

```text
Network Access
    ↓
Identity Authentication
    ↓
Capability Authorization
    ↓
User Intent Confirmation
    ↓
Runtime Policy Enforcement
```

每层需要独立定义控制主体、输入、拒绝结果和验证方法。

### 3.4 Phase-Fit Experiment Pattern

```text
当前目标
  → 高风险假设
  → 最小探针
  → 成功证据
  → 时间 / 成本预算
  → 退出条件
  → 替代路线
```

它用于探索性工作，不替代正式生产架构设计。

## 4. 工程反模式

### 4.1 外部调用者拥有内部控制字段

外部模型或第三方请求指定身份、权限、执行者、路由和生命周期，服务端只做透传。

替代：Intent Adapter。

### 4.2 相似路径通过等于真实路径通过

内部通用接口、预览环境或局部测试通过，被描述为正式用户入口通过。

替代：Real-Path Verification。

### 4.3 单一权限开关

把公网访问、身份认证、能力授权、用户批准和运行时策略混成同一件事。

替代：Layered Authorization Model。

### 4.4 用长期完整性替代阶段可行性

核心假设未验证前建设大量外围治理，方案优先追求未来完整性而不是当前目标。

替代：Phase-Fit Experiment Pattern。

### 4.5 无退出条件的补丁循环

没有最大投入、失败阈值、替代路线和回滚方式，仅因已经投入而继续投入。

### 4.6 每次变更都从零审计

忽略已有可信基线和实际变化，使审计成本与风险不匹配。

替代：Risk-Proportional Review。

### 4.7 每个问题都形成长期经验

一次拼写错误、未查明故障或低影响操作也生成全局规则，导致经验库膨胀。

替代：先 Screening，允许 `reject` 和 `needs_evidence`。

### 4.8 一次事件直接成为定律

使用“永远”“所有场景”“只能”，但没有 Precondition 和 Exclusion。

## 5. 工程启发式

- **高风险假设优先**：优先验证“不确定性 × 失败影响”最高的外部假设。
- **当前阶段优先**：MVP 先优化核心假设首次通过时间，生产阶段再评估长期治理。
- **外围修复触发路线复评**：连续修复集中在目标能力之外时，应重新比较替代路线。
- **真实入口决定最终证据等级**：代码完成、组件测试、内部链路和正式用户路径是不同证据等级。
- **证据有效性可以复用**：复审前识别上次可信基线后实际改变了什么。
- **没有索引，不声明唯一**：无法访问完整 Registry 时，查重只能标记为 `unverified`。
- **单一事件成熟度通常不高于 provisional**：缺少验证时保留为 `candidate`。
- **恢复不等于根因证明**：重启后恢复或重试成功只能证明相关性。

## 6. 工程检查清单

### 6.1 外部智能调用接口

- 外部调用方是否能指定身份、权限、执行者或路由？
- 哪些字段可以由服务端生成？
- 是否存在能力白名单？
- 参数错误是否在进入内部执行层前被拒绝？
- 是否分别测试外部适配和内部任务契约？

### 6.2 真实用户路径验收

- 自动验收和正式用户是否经过同一入口？
- 方法、认证、请求体和序列化是否一致？
- 是否断言服务端生成标识和关键业务字段？
- 适配层损坏后，当前测试是否仍可能通过？
- 最终证据保存在哪里？

### 6.3 权限分层

- 网络访问由谁控制？
- 身份认证使用什么凭据？
- 能力授权在哪一层判断？
- 用户是否确认本次具体意图？
- 运行时是否执行独立策略检查？
- 各层拒绝是否可以区分和观察？

### 6.4 探索性技术选型

- 当前核心假设是什么？
- 最小探针是什么？
- 成功证据是什么？
- 最大时间和成本预算是多少？
- 哪些条件触发停止？
- 替代路线是什么？

### 6.5 风险分级复审

- 上次可信基线是什么？
- 此后精确修改了什么？
- 是否跨越认证、权限、数据或运行边界？
- 哪些旧证据仍有效？
- 需要差异审查、相关集成测试，还是完整端到端复审？

### 6.6 经验沉淀

- 事件是否已解决或具有明确证据？
- 根因是事实、推断还是未知？
- 是否改变了工程决策？
- 是否能形成防复发动作？
- 是否可能跨场景复用？
- 处置应为 `proceed_full`、`needs_evidence` 还是 `reject`？

## 7. 洞见演进与应用

### 7.1 任务前

根据目标、阶段和风险，从 Registry 检索少量相关洞见，转换为：

- Preflight Checklist；
- Decision Gate；
- Test Requirement；
- Exit Condition；
- Review Constraint。

### 7.2 任务中

检查已知反模式，记录关键假设并保存证据；边界不适用时，不强行套用旧规则。

### 7.3 任务后

```text
已解决事件
  → Screening
  → Full Distillation
  → Registry Search
  → New / Occurrence / Evidence / Revision / Contradiction
  → Validate
```

### 7.4 成熟度

```text
candidate
  → provisional
  → validated
  → repeated
  → established
```

一次事件通常不高于 `provisional`；`repeated` 至少需要两个独立事件；`established` 需要多场景证据、稳定边界和正式批准。

### 7.5 生命周期

- `active`：当前表述可使用；
- `revised`：新证据要求修改边界或原则；
- `deprecated`：环境变化使其不再作为当前依据。

生命周期变化不删除历史证据。

### 7.6 Occurrence 与冲突

同一次事件的聊天摘要、日志和截图只能算一个 Occurrence 的多个来源。新证据与旧洞见冲突时，应检查 Context、增加 Exclusion，或执行特化、修订和废弃，不能静默覆盖。

## 8. 资产边界

```text
Skill
  = 提炼方法、Schema 和 Evals

Engineering Insight Registry
  = 成熟度、生命周期、Occurrence、关系和来源主记录

本文
  = 面向人类和飞书的综合阅读视图

项目代码、测试、日志和复盘
  = 具体事件证据
```

本文不得反向覆盖 Registry 状态。
