# CTX-001 ai-agent-platform 项目总览
> **资产状态**：本文正文已在 Batch 02 交付包中完成内容 Review；进入仓库后先标记为 `partial / unpublished`，待真实 Commit 整体复审通过后再升级为 `accepted`。

> `ai-agent-platform` 是一个服务于 Agent 工程学习、真实平台建设和职业转型证明的长期工程项目。它的目标不是把更多 AI 工具接在一起，而是让目标、任务、执行、知识、证据和恢复形成可追踪闭环。

## 1. 项目为什么开始

项目起点不是一个抽象的“做 Agent 平台”愿望，而是一个现实问题：前端工程背景需要转向 Agent 开发或全栈 Agent 工程方向，单纯学习产品菜单、复制 Prompt 或拼接工具不能形成足够可信的职业证明。

早期探索分散在 ChatGPT、Codex、手机、本地模型、飞书、GitHub 和 AI 视频创作等多个方向。每个方向都有价值，但共同暴露出五个长期摩擦：

1. 历史聊天承担了太多项目事实，新会话很难稳定恢复；
2. ChatGPT 能规划，Codex 能执行，但二者之间缺少稳定任务契约；
3. 工具调用和实验结果没有统一状态、权限、证据和回滚边界；
4. 文档、代码、飞书和会话之间容易形成多个“看起来都是真的”版本；
5. 即使做了很多工作，也难以用代码、测试、决策和 Demo 讲清真实工程能力。

因此项目逐渐从“ChatGPT × Codex Bridge”扩展为一个可持续演进的平台：用 Git 保存正式事实，用 Agent + Skills 组织专业能力，用 Runtime 和 Contracts 承接动态任务，用审批、证据和恢复治理高风险执行，再用真实上层产品验证平台。

## 2. 用户现实目标

项目同时服务三个目标，但优先级不同：

| 目标 | 说明 | 验收方式 |
| --- | --- | --- |
| 职业转型 | 从前端工程经验迁移到 Agent / 全栈 Agent 工程 | 能解释系统边界、完成真实实现、形成简历项目故事 |
| 工程学习 | 按 Interface、Brain、Runtime、Tool、Knowledge、Infrastructure 六层学习 | 每个概念能映射到仓库资产、代码或明确的未来状态 |
| 平台建设 | 建立可运行、可追踪、可复审、可恢复的协作系统 | Task、Gateway、Runtime、Git、测试和证据形成闭环 |

“学习”不是独立课程，“知识库”不是资料仓，“平台”也不是空架构图。三者必须互相转化：学习形成正式知识；知识指导实现；实现产生证据；证据反过来修订知识。

## 3. 六层架构与横向治理

长期六层模型为：

```
Agent Interface → Agent Brain → Agent Runtime → Tool Layer → Knowledge Layer → Infrastructure
```

当前项目又补充了横向治理：Approval、Evidence、Health、Snapshot、Handoff、Audit。它们不属于某一个 GPT 或 Skill，而是跨 Runtime、工具、知识和基础设施的公共机制。

当前 Chat 是总体大脑、规划与复审入口；Custom GPT 是专业角色入口；Codex / Work 是真实环境执行器；Gateway / Runtime 管理认证、授权、状态和调用；Git 保存正式资产；飞书发布人类可读投影。

## 4. 已走过的阶段

### Phase 1：Knowledge Foundation——已交付

建立 Git 唯一真源、`context/`、四层文档结构、AI Knowledge Skill、飞书单向 Projection 和图片 Publisher 方向。历史上曾考虑 Git + Feishu 双源，也曾直接使用 GitHub Raw 图片，但最终都因冲突、不可控和飞书渲染失败而被替代。

### Phase 2：AI Coding Workflow——进行中

当前仓库已经实现六个 workspace：Contracts、Auth、Policy、Action Gateway、Local Runtime 和 Dev Tunnel。`runtime.status` 已完成本地、公网、Builder Preview 和正式 Custom GPT 自然语言调用验证。当前能力仍然很窄，但它第一次证明了“专业 GPT 入口 → 受控公网接口 → 本地安全 Runtime → 结构化结果”的真实链路。

### Phase 3：AI Video Workflow——未开始

AI 视频工作流不是当前已实现产品，而是未来用来验证平台复杂性的上层业务：故事理解、人物场景、分镜提示词、多模型 Provider、评估重试、成本记录和 Demo。平台先建立共性机制，再由业务产品验证是否真的有用。

## 5. 当前主线

当前主线不是继续扩展更多入口，而是把已经打通的窄链路演进为可信工程闭环：

```
Chat / 专业 GPT
→ Task Contract
→ Gateway / Runtime
→ Codex / Work / Skill
→ 测试与 Result
→ Git / Evidence
→ Review / 下一任务
```

近期需要补齐的不是“更多模型”，而是 Task State、动态权限、审批、Evidence、恢复、Agent Profile、Knowledge Pack 和 Platform Registry。

## 7. 成功标准

项目成功不以目录数量、文档页数或概念完整度判断。最少满足：

- 新 Agent 能在有限上下文中恢复当前事实；
- 任务输入、权限、执行和结果有稳定 Contract；
- 已实现、部分实现、设计和 superseded 清晰分开；
- 关键调用有测试、日志、回执或可复现实验；
- 高风险操作有审批和副作用边界；
- 上层业务能在平台上形成真实 Demo；
- 求职展示只引用可以追溯的工程证据。

## 8. 当前限制与下一步

当前 Dev Tunnels 只是开发期 Public Preview，不是生产入口；当前 Key 为本机静态 Key，没有自动轮换；Runtime 只有两个安全 Capability；AI 视频工作流未开始；Registry、Agent Profile 和 Knowledge Pack 还只是目标设计。

下一步优先完成知识入口与产品体系定稿，再由 Codex 分批落盘和修复 Context Drift；随后推进 Task Control、Evidence 和 Recovery，而不是一次性创建所有未来包。
