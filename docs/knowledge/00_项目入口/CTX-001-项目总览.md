# CTX-001 ai-agent-platform 项目总览

> `ai-agent-platform` 是服务于 Agent 工程学习、真实平台建设和职业转型证明的长期工程项目。它的目标不是把更多 AI 工具接在一起，而是让目标、任务、执行、知识、证据和恢复形成可追踪闭环。

## 1. 项目为什么开始

项目发起者具有前端工程背景，需要通过真实项目补齐 Agent 工程、后端、运行时、工具集成和全栈交付能力。单纯学习产品菜单、复制 Prompt 或拼接工具，无法形成足够可信的职业证明。

早期探索分散在 ChatGPT、Custom GPT、Codex、本地模型、GitHub、飞书和 AI 视频创作等方向，共同暴露出长期摩擦：

- 历史聊天承担过多项目事实，新会话难以稳定恢复；
- Planner 能规划、Executor 能执行，但缺少稳定交接合同；
- 工具调用和外部副作用缺少统一状态、权限、证据和恢复边界；
- 文档、代码、会话和飞书容易形成多个“看起来都是真的”版本；
- 大量工作难以用代码、测试、决策和 Demo 讲清真实工程能力。

因此项目从单一 Bridge 探索演进为一个长期 Agent 工程平台：Git 保存正式事实，Agent + Skills 组织专业能力，Gateway / Runtime 承接受控调用，Task、Approval、Evidence 和 Recovery 治理动态执行，上层真实产品负责验证平台价值。

## 2. 第一用户与平台愿景

近期第一用户是项目所有者本人，也可逐渐服务类似的个人开发者和小型多 Agent 项目，但当前不包装成通用 SaaS。

平台愿景是：

> 让个人开发者能够把 ChatGPT、专业 Agent、Codex、Skills、知识和本地执行环境组织成一个可继续、可验证、可解释、可复用的工程系统，并把真实过程转化为职业证明。

北极星不是 Agent 数量或自动化率，而是：

> 一项工程工作在窗口变化、执行失败、角色接力和产品变化后，仍能基于可信事实继续推进，并留下可复审证据。

## 3. 六层能力栈

```text
Agent Interface
  ↓
Agent Brain
  ↓
Agent Runtime
  ↓
Tool Layer
  ↓
Knowledge Layer
  ↓
Infrastructure
```

- Interface 接收目标、展示状态和人工审批；
- Brain 理解目标、规划、选择知识和生成任务；
- Runtime 管理任务、权限、状态、证据和恢复；
- Tool Layer 调用 Codex、CLI、API、MCP、Browser 和 Skills；
- Knowledge Layer 提供 Context、正式知识、Registry 和未来 Knowledge Pack；
- Infrastructure 提供 Git、设备、网络、Secret、存储、测试和发布环境。

Approval、Evidence、Health、Snapshot、Handoff 和 Audit 是跨层治理能力，不归属于某一个模型或工具。

## 4. 三层协作模型

```text
总控 Planner
→ Executor
→ 用户 Review
```

- 总控 Planner 负责目标、规划、语义资产、Context 和复审；
- 其他专业 Agent 只报告变化和证据，不直接改写 Context；
- Executor 只按冻结完整文件执行落盘、验证、Commit 和 Push；
- 用户负责重要变化审批和最终确认。

核心原则：

> Context 由总控 Planner 维护，Executor 只执行，其他 Agent 只报告变化，用户最终确认。

## 5. 平台与上层产品

`ai-agent-platform` 是当前主产品、底层平台和仓库主体。AI 视频工作流是首个计划验证的上层产品。其他潜在方向保持在机会池，只有通过问题证据、产品形态、最小切片和停止条件后，才成为正式产品概念。

当前不创建根级 `products/`。只有真实产品进入设计或开发阶段后，才按实际资产类型在 `apps/`、`packages/`、`docs/`、`agents/`、`skills/` 等目录建立子资产，并由 Registry 表达归属。

## 6. 建设主线

1. Knowledge Foundation；
2. AI Coding Workflow；
3. Task Control and Trusted Execution；
4. 上层真实产品工作流；
5. Portfolio Release。

精确阶段状态见 `context/current-status.md` 和 `context/roadmap.md`，本文不重复保存易漂移的批次、Commit 和即时进度。

## 7. 产品承诺

- Git 是正式知识、代码、状态和治理规则的唯一真源；
- 当前实现、目标设计、假设和 superseded 历史清晰分开；
- 新 Agent 能在最小上下文内恢复当前事实；
- Task 输入、权限、执行、结果和证据具有稳定边界；
- 高风险操作具有人工审批和副作用边界；
- 模型、Provider、设备和执行器可以替换；
- 上层产品复用平台共性能力，不把业务领域塞入平台核心；
- Portfolio 中的能力可以回查代码、测试、实验、ADR 或正式状态。

## 8. 成功标准

项目成功不以目录数量、文档页数或概念完整度判断，至少需要：

- 有可运行、可验证的端到端链路；
- 任务在失败、暂停和角色切换后能够恢复或安全终止；
- 知识、代码、决策和证据保持可追踪关系；
- 一个真实上层业务在平台上形成可演示 Demo；
- 求职叙事只引用有证据的实现或明确标记的设计。

## 9. 非目标

- 当前不建设通用 Agent SaaS；
- 不用 LangGraph 等重型框架替代尚未完成的领域设计；
- 不让 Custom GPT Builder 或飞书成为配置或知识真源；
- 不为未来能力预建大量空目录和空包；
- 不用“更多 Agent”掩盖 Task、Evidence 和 Recovery 的缺失；
- 不自动执行删除、公开权限、Force Push 和其他不可逆副作用。
