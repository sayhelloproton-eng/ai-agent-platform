# CTX-007 当前实现与目标架构

> 当前架构是一条窄而真实的安全 Action 链路；目标架构是认知、控制、执行、知识和基础设施分平面协作的平台。二者必须明显分开。

## 1. 当前真实调用链

```
用户自然语言
→ Custom GPT
→ getRuntimeStatus Action
→ Microsoft Dev Tunnel
→ Action Gateway（127.0.0.1:8787）
→ Local Runtime（127.0.0.1:8790）
→ runtime.status Capability
→ Contract v1 TaskResult
→ Custom GPT 回答
```

这个链路已经验证本地、公网、Builder Preview 和正式 GPT 对话。当前价值不在能力多，而在边界清楚：外部与内部 Key 分离、两层 Policy、Loopback 限制、Timeout、Body/响应大小限制、Rate Limit、并发保护、TaskId 对应和结构化错误。

## 2. 当前组件职责

| 组件 | 当前职责 | 明确不负责 |
| --- | --- | --- |
| Custom GPT | 专业入口、自然语言理解、Action 选择 | 动态状态、数据库、可靠后台调度 |
| Dev Tunnel | 开发期持久公网入口 | 生产 SLA、业务认证、边缘安全策略 |
| Action Gateway | 外部认证、Gateway Policy、Task 构造/转发、限流 | 真实能力执行、长期任务状态 |
| Local Runtime | 内部认证、Runtime Policy、Contract 校验、Capability 调度 | 完整工作流引擎和业务编排 |
| Contracts | Task / Result / Error 与 validator | 决定业务优先级 |
| Auth / Policy | 静态 Key 和 Capability allow/deny | 动态角色、组织 RBAC、审批 |
| Skills | 稳定程序性知识与运行规则 | 运行时任务数据库 |

## 3. 已实现安全边界

- Gateway 与 Runtime 只监听 Loopback；
- Tunnel 只公开 Gateway；
- 匿名 Tunnel 访问不替代 Bearer 认证；
- 外部 Action Key 与内部 Runtime Key 分离；
- Gateway 和 Runtime 均执行默认拒绝 Policy；
- Runtime Client 禁止非 Loopback 目标；
- Timeout、请求/响应大小、并发和 Rate Limit 有上限；
- Runtime Busy 映射为受控错误，不透传内部 Body；
- `/v1/tasks` 只接受 `custom-gpt` requester 并覆盖不可信 Request ID；
- 正式调用可通过 taskId 和日志对应。

这些边界是当前最重要的工程成果，也是后续扩展 Capability 时不能破坏的基线。

## 4. Context 一致性治理

早期 Context 曾把 Runtime 描述为尚未建设，Batch 01 已根据真实代码、测试和 Action 验收完成修正。

后续若 Context、正式知识和代码再次冲突，应以代码、测试、真实调用和正式 ADR 为优先证据，并在同一逻辑批次更新 Context、Registry 和相关知识文章。

## 5. 目标架构的五个平面

### 认知平面

Chat、总控 Agent 和专业 Agent 负责理解目标、研究、规划、复审和专业判断。角色配置从 Git 中的 Agent Profile 发布，不绑定单一产品。

### 控制平面

负责 Goal、Task、Task Version、State、Dependency、Resource Lease、Approval、Policy、Evidence、Side-effect Ledger、Health Event、Snapshot 和 Recovery。它是当前最大缺口。

### 执行平面

Codex、Work、Skills、本地脚本和未来其他执行器通过 Execution Lane 接受明确 Task。写入任务绑定 Branch / Worktree；Session 和 Executor 可替换，Task 才是稳定身份。

### 知识与资产平面

Git 保存正式文档、ADR、Agent Profile、Knowledge Pack、Skill 和 Registry。外部 RAG 提供实时检索；飞书提供人类投影。Registry 维护资产关系、状态和变更影响。

### 基础设施平面

本地设备、GitHub、网络入口、Provider、存储、日志和观测。上层依赖 Port / Contract，不直接绑定某个 Tunnel、模型或云服务。

## 6. 当前到目标的差距

| 差距 | 当前 | 目标 |
| --- | --- | --- |
| Task 状态 | 请求内 Task，缺少持久状态 | Goal/Task/Version/State/Event |
| 权限 | 静态 Key + Capability allowlist | Agent/Client/Executor 身份、Scope、状态校验 |
| 审批 | 高风险操作靠人工外部控制 | 结构化请求、决定、版本和执行证据 |
| 执行 | 两个安全 Capability | Codex/Work/Skill 多执行器与 Execution Lane |
| 证据 | 测试、日志、TaskResult | Evidence Registry、有效性和副作用账本 |
| 恢复 | 进程级失败和快速失败 | Health、Checkpoint、Snapshot、Handoff、Compensation |
| 资产 | 基础 Platform Registry 已管理资产、关系、路径和迁移 | Agent Profile、Knowledge Pack、生成索引与自动影响分析 |
| 业务 | 无业务工作流 | AI 视频工作流真实验证 |

## 7. 演进阶段

1. **知识治理**：迁移其余知识栏目并完成全库 Review；
2. **任务治理 MVP**：Task State、expected\_version、幂等命令、Evidence；
3. **人工在环**：Approval、风险分级、Side-effect Ledger；
4. **多执行器**：Codex Adapter、Execution Lane、Worktree 隔离；
5. **资产化**：Agent Profile、Knowledge Pack、Registry；
6. **业务验证**：AI 视频工作流最小纵向切片；
7. **生产化评估**：公网入口、动态权限、观测和部署。

## 8. 为什么不一次性建全

当前项目资源有限，且许多领域对象需要从真实任务中验证。一次性建立完整通用 Runtime 会产生空包、伪状态和维护负担。正确方式是让每个抽象至少有一个真实调用方、测试和失败案例，再晋升为公共能力。

因此当前不采用 LangGraph 作为核心，不是拒绝状态机思想，而是先把 Task、Evidence、Approval 和 Recovery 的领域边界做清楚。

## 9. 已确定和待验证的领域对象

已确定：Task、Result、Error、Capability、Policy、Agent Role、Execution Lane、Evidence、Approval、Snapshot、Knowledge Asset。<br>
仍待验证：Resource Lease 的最小模型、Side-effect Ledger 粒度、Health Event 分类、跨执行器 Session 映射、动态权限存储和业务领域适配方式。

## 10. 结论

当前链路证明平台方向可行，但它只是可信地“打通一条线”。下一阶段的核心不是增加更多 endpoint，而是把状态、审批、证据和恢复变成独立、可测试、可复用的控制面能力。
