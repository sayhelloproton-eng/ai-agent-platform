# CTX-006 知识库阅读导航
> **资产状态**：本文正文已在 Batch 02 交付包中完成内容 Review；进入仓库后先标记为 `partial / unpublished`，待真实 Commit 整体复审通过后再升级为 `accepted`。

> 知识库的目标不是让所有人从头读完，而是让不同角色在最小上下文内获得足够可信的事实，并知道下一步去哪里验证。

## 1. 先判断你要解决什么

| 问题 | 首选入口 |
| --- | --- |
| 项目是什么、为什么存在 | `CTX-001`、`PRD-001` |
| 当前真实做到什么 | `context/current-status.md`、`CTX-005` |
| 当前链路和目标平台如何区分 | `CTX-007` |
| 为什么做出某个重要选择 | `DEC-001`、相关 ADR |
| 某个产品/配置是什么 | `02_基础产品与能力/`、`docs/learning/` |
| 某个机制怎样实现 | `docs/technical/`、代码、测试 |
| Agent 应怎样执行任务 | 根/目录 `AGENTS.md`、相关 Skill |
| 能否用于求职展示 | `09_作品集/`，并回查代码和实验证据 |

## 2. 所有人共同的最小入口

新用户或新 Agent 默认按以下顺序：

1. 根 `README.md`：项目方向、当前 Phase 和入口；
2. 根 `AGENTS.md`：Project Constitution、权限和禁止事项；
3. `context/README.md`：最小上下文顺序；
4. `context/current-status.md`：当前真实完成项、限制和下一步；
5. 与任务相关的最近一级 README；
6. 目标文件、测试和必要的技术方案/ADR。

不要默认扫描全部文档。只有任务明确要求全量审计、目录重构或跨资产影响分析时，才扩大读取范围。

## 3. 角色化阅读路径

### 新用户

`CTX-001 → PRD-001 → CTX-005 → CTX-007 → DEC-001`。先理解项目故事，再判断当前能力，最后理解架构和决策。

### 新 Agent

`README → AGENTS → current-status → roadmap → 目标目录 README → 目标代码/测试`。Agent 需要的是最小、当前、可执行上下文，不是完整历史聊天。

### 产品角色

`PRD-001 → PRD-003 → PRD-004 → PRD-005 → PRD-006/007 → EXP/Portfolio`。关注用户价值、非目标、验证方式和业务证据。

### 架构角色

`CTX-007 → DEC-001 → ARC 系列 → Technical → ADR → Code Mapping`。必须把长期方向和当前实现分开。

### 开发角色

`current-status → AGENTS → package/app README → Contract/Schema → tests → technical solution`。代码和测试优先于概括性知识文章。

### 知识治理角色

`knowledge-strategy → KNO 系列 → platform-registry → projection → read-back`。重点是资产身份、来源、关系、状态、发布和影响分析。

### 求职展示

`PRT 项目故事 → 核心架构亮点 → Demo → 工程能力证明 → Git/测试/实验`。未实现设计可以展示思考，但必须显式标为设计。

## 5. 四层文档边界

| 层 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `docs/knowledge/` | 长期解释、Agent 可查询上下文、飞书发布源 | 详细运行命令和临时实验日志 |
| `docs/learning/` | 教程、来源、认知演进、产品学习 | 平台当前事实真源 |
| `docs/technical/` | 实施方案、治理、调研、运维、迁移 | 面向所有读者的总体叙事 |
| `docs/adr/` | 长期重要决策和替代方案 | 日常变更日志或未确认设想 |
| `context/` | 当前高密度启动上下文 | 完整教程和历史归档 |
| `platform-registry/` | 资产 ID、关系、状态、迁移、Projection、影响 | 人类正文解释 |

## 6. 最小上下文读取法

执行一个具体任务时，采用“五问法”：

1. 任务目标和允许范围是什么？
2. 当前状态与目标文件是否一致？
3. 哪个 Contract / Schema / ADR 约束它？
4. 实际验证命令是什么？
5. 变更会影响哪些 README、知识和 Registry 关系？

只读取能回答这五问的资料。上下文不足时补读；上下文冲突时报告 Drift，不自行选择方便的版本。

## 7. 怎样判断一篇内容是否可信

证据优先级：

```
真实调用与外部回执
> 实际测试
> 代码与配置
> accepted ADR / 已确认决策
> current-status
> 正式知识解释
> 学习笔记与调研
> 会话推断和未来设想
```

旧文档并不等于无价值。它可能解释“为什么曾经这样做”，但不能覆盖当前实现。`superseded` 应保留历史，并指向替代资产。

## 8. 图片、Registry 与飞书

正文引用正式 PNG，SVG 是可编辑源。图片源资产最终进入 `knowledge-assets` 分支，由 `asset://` 和 Publisher 上传飞书。Registry 记录媒体、关系、Projection 和变更影响，但不把大段 YAML 放在正文开头。

飞书仅是人类阅读投影。阅读飞书时遇到冲突，必须回到 Git；飞书 Native 讨论影响项目时，先晋升为 Git Draft，经 Review 后再发布。

## 9. 推荐阅读顺序

本批次建议：`CTX-001 → PRD-001 → CTX-005 → CTX-007 → DEC-001 → CTX-006`。最后阅读导航，是为了在理解内容后掌握长期使用方式。
