# DEC-001 架构决策演进摘要

> 本文记录影响项目方向的关键决策、替代关系和当前结论，不替代正式 ADR。即时状态见 `context/current-status.md`。

## 1. 从模糊协作到 Planner、Executor、用户 Review

- **原问题**：Chat、Codex、Work 和本地 Agent 被模糊地当成同一执行主体，语义决策、真实写入和最终审批混在一起。
- **当前方案**：总控 Planner 负责目标、规划、语义资产、Context 和复审；专业 Agent 只报告变化；Executor 只按冻结完整文件执行；用户负责重要变化审批和最终确认。
- **影响**：形成 Planner Executor Handoff、Context Access、Scope Lock、完整覆盖文件和确定性交付流程。
- **状态**：现行决策；Handoff v0.5.1 已 `accepted`。

## 2. Context 采用唯一语义负责人

- **原问题**：多个 Agent 都可能“顺手更新” Context，容易造成状态漂移和语义冲突。
- **当前方案**：只有总控 Planner 能决定和生成 `context/**` 内容；Executor 默认只读，只在获得完整冻结文件和明确路径授权后覆盖。
- **影响**：仓库规则、Handoff Schema / Validator 和正式知识共同约束。
- **状态**：已实现并接受。

## 3. Monorepo 与渐进式 Workspace

- **原问题**：Gateway、Runtime 和共享 Contract 分散，或为未来能力预建空包。
- **当前方案**：npm workspaces，只物化有真实调用方和测试的应用或共享包。
- **影响**：Node 20 / npm 10、`tsconfig.base.json` 和根级 `verify` 成为工程基线。
- **状态**：已实现并验证。

## 4. Custom GPT Actions + Gateway + Local Runtime

- **原问题**：普通 Chat 不能可靠直接操作本机，Custom GPT 也不应充当动态任务数据库或 Runtime。
- **当前方案**：Custom GPT → Actions → Gateway → Local Runtime；OpenAPI、认证、Policy 和 Contract 可独立测试。
- **影响**：形成 `runtime.status` 专用入口、双层 Key / Policy 和结构化 TaskResult。
- **状态**：窄链路已验证；完整 Task Control 未实现。

## 5. Git 唯一真源与 Feishu 单向投影

- **原问题**：Git 与 Feishu 都可编辑会导致冲突、合并和责任不清。
- **当前方案**：Git 是正式真源；只允许 Git → Feishu overwrite；不读取旧正文、不合并、不反向同步。
- **影响**：Feishu Native 内容必须先晋升为 Git Draft，正式发布需独立授权和回读。
- **状态**：ADR-002 已接受，ADR-001 已 superseded。

## 6. 图片从独立资源分支演进为 Document Bundle

- **原问题**：Raw URL 不稳定；后续 `knowledge-assets + asset://` 又造成正文、资源、Review 与版本分离。
- **当前方案**：资源型正式文档采用 Document Bundle，SVG / PNG 与 `README.md` 同目录、同分支、同 Commit；正文使用 `./assets/...`，图片下方保留 AI 可读语义镜像。
- **投影方式**：Publisher 在 Git → Feishu 覆盖发布时上传本地图片并插入媒体块，Feishu Token 不回写 Git。
- **状态**：ADR-003 已接受；首批 10 个正式视觉资产已迁移，最终 Feishu 发布尚未执行。

## 7. Agent + Skills，而不是当前引入 LangGraph

- **原问题**：状态、检查点和人工介入需要工程化，但领域对象尚未稳定。
- **当前方案**：Agent + Skills + Contracts + 轻量 Task Control + Approval + Evidence + Recovery。
- **原因**：避免用框架结构代替领域设计和真实验证。
- **状态**：现行技术路线；保留对 LangGraph 思想的研究。

## 8. 多 Agent 通过 Task State 协作

- **原问题**：多个 GPT 不能可靠程序化互调，也不共享稳定会话记忆。
- **当前方案**：通过 `goal_id`、`task_id`、状态、事件、审批、Artifact 和知识引用协作；Session 和 Executor 可替换，Task 是稳定身份。
- **状态**：核心设计，完整控制面尚未实现。

## 9. 两层 Knowledge Pack

- **原问题**：每个 Agent 既需要共同项目事实，也需要角色专属知识；复制整个知识库会浪费 Token 并模糊边界。
- **当前方案**：通用基础包 + 角色专属包，均从 Git 正式知识派生；外部 Knowledge Service 负责实时共享知识。
- **状态**：已确认设计，尚未物化 `knowledge-packs/`。

## 10. Cloudflare 当前路线被 Microsoft Dev Tunnels 替代

- **原问题**：Cloudflare Edge / Bridge 路线产生配置漂移、远端 Secret 和实现复杂度。
- **当前方案**：开发期使用持久 Microsoft Dev Tunnel，只公开本地 Gateway，并保留 Bearer 认证。
- **状态**：当前开发期实现；非生产方案。

## 11. 不创建根级 `products/`

- **原问题**：平台是当前仓库主体，AI 视频工作流尚未进入实现，提前建立多产品树会产生空壳结构。
- **当前方案**：产品产生真实资产后，按资产类型在现有目录创建子目录，归属由 Registry 表达。
- **状态**：现行目录原则。

## 12. Platform Registry

- **原问题**：文档、代码、Agent、Skill、ADR、测试和 Feishu 节点关系分散，大段 Front Matter 污染正文。
- **当前方案**：根级 Registry 统一 Asset ID、关系、路径、实现状态、Migration、Projection 和 Release。
- **状态**：基础 Registry 与校验已实现；生成索引和自动影响分析仍待完善。

## 13. 复杂图正式资产化

- **原问题**：简单方框图无法表达跨层关系、状态、证据和治理闭环。
- **当前方案**：复杂图先写图稿规格，输出可编辑 SVG + 发布 PNG，正文解释图中结构；Mermaid 只用于简单局部关系。
- **状态**：治理原则已执行，首组十张视觉资产已接受。

## 14. Project Knowledge Synthesis 从人工方法物化为 Skill

- **背景**：知识 Review 需要同时处理多文档 Claim、重复、冲突、状态、目标落位、链接和 Registry 影响，普通摘要无法稳定完成。
- **原方案**：由 Chat 依靠长上下文人工综合，Skill 仅保留 Future 占位。
- **当前方案**：物化 `project-knowledge-synthesis v0.1.0`，使用结构化请求、综合结果 Contract、离线 Validator、Self-test 和真实目录 Pilot；结果仍需 Planner 与用户 Review。
- **首个 Pilot**：把 `00_项目入口` 六篇正式文章收敛为 `CTX-001`、`CTX-005`、`DEC-001` 三篇，导航归入 README，退役文件进入技术归档。
- **状态**：`in_review`，不具备自动写入、发布或生命周期晋升权限。

## 15. 后续正式 ADR

优先核对或形成：Agent + Skills、Task / Session / Executor 分离、Agent Profile / Knowledge Pack、Platform Registry、Health / Recovery，以及 Project Knowledge Synthesis 的长期治理。ADR 进入 `accepted` 前必须由 Project Owner Review。
