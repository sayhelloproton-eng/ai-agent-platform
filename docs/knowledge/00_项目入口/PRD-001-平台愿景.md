# PRD-001 ai-agent-platform 平台愿景

> 让个人开发者能够把 ChatGPT、专业 Agent、Codex、Skills、知识和本地执行环境组织成一个可继续、可验证、可解释、可复用的工程系统，并把真实过程转化为职业证明。

## 1. 为谁服务

近期第一用户是项目所有者本人：有真实软件工程经验，正在向 Agent / 全栈 Agent 工程转型，需要在有限时间、设备和成本约束下完成可展示成果。平台也可逐渐服务类似的个人开发者和小型多 Agent 项目，但当前不把它包装成通用 SaaS。

## 2. 核心困境

现有 ChatGPT、Custom GPT、Codex、Work、Git 和第三方工具各自有能力，却不能自动组成一个可信系统：

- Chat 擅长理解和规划，但上下文会变长、压缩和漂移；
- Custom GPT 能形成稳定角色，却不应承担动态任务数据库；
- Codex 能修改真实仓库，但需要明确范围、上下文和验收；
- 工具调用可以产生外部副作用，却常缺少幂等、审批和证据；
- Project、Memory、Files、Knowledge 和飞书解决不同问题，不能混成一个“知识库”；
- 多窗口并行时，窗口和 Session 很容易被误认为任务本身。

平台要消除的不是“模型不够聪明”，而是这些边界之间的工程摩擦。

## 3. 长期愿景与近期使命

### 长期愿景

形成一个模型、Provider、设备和执行器可替换的 Agent 工程平台。专业角色可以由 Custom GPT、API Agent、Codex、Work 或其他模型承担；任务身份、状态、权限、产物和证据不绑定某一个会话或产品入口。

### 近期使命

在六个月内完成三步：

1. 已完成 Knowledge Foundation；
2. 建立 ChatGPT → Task → Codex → Git 的 AI Coding Workflow；
3. 用 AI 视频工作流验证平台是否能承载真实复杂业务。

近期使命不等于删除长期能力，而是控制实现顺序。

## 4. 北极星价值

北极星不是“自动化率”，也不是“Agent 数量”，而是：

> 一项工程工作在窗口变化、执行失败、人员接力和产品变化后，仍能基于可信事实继续推进，并留下可复审证据。

可以拆成四个可观察结果：

| 结果 | 解释 | 证据 |
| --- | --- | --- |
| 可继续 | Task 不依赖单一会话，能够暂停、移交和恢复 | Task State、Checkpoint、Snapshot |
| 可验证 | 模型结论不直接当事实，执行结果可重放或核对 | 测试、Result、日志、Diff、回执 |
| 可解释 | 为什么这样设计、替代了什么、当前边界是什么 | Knowledge、ADR、Decision Timeline |
| 可复用 | 角色、知识和流程能版本化并用于新任务 | Agent Profile、Knowledge Pack、Skill |

## 5. 产品承诺

平台承诺：

- Git 中的正式事实可以被新 Agent 最小读取；
- 计划、实现、验证、推断和 superseded 不混写；
- 高风险执行经过身份、授权、状态和人工审批；
- 每个执行结果能关联任务、版本、执行器和证据；
- 多任务并行使用 Branch / Worktree / Execution Lane 隔离；
- 知识从 Git 单向投影到飞书，投影失败不改变真源；
- 上层产品只复用平台共性能力，不把业务领域塞入平台核心。

## 6. 非目标

当前明确不做：

- 一次性实现完整通用 Agent SaaS；
- 以 LangGraph 等重型框架替代尚未完成的领域设计；
- 让 Custom GPT Builder 或飞书成为配置/知识真源；
- 通过浏览器自动刷新、接管标签或隐式重试维持系统；
- 自动执行删除、公开权限、Force Push 和不可逆副作用；
- 为尚未开发的产品提前建立大量空目录和空包；
- 用“更多 Agent”掩盖 Task、Evidence 和 Recovery 的缺失。

## 7. 怎样判断愿景实现

近期验收采用递进指标：

1. 新会话依据 Git 在有限读取内恢复当前状态；
2. 一个 Task 能从 Chat 规划进入 Codex 执行并产生测试与 Result；
3. 任务失败后能从 Snapshot 恢复或安全终止；
4. 两个写入任务能通过独立 Worktree 隔离；
5. 一个专业 Agent 可从 Git 配置重建，并加载两层 Knowledge Pack；
6. AI 视频工作流形成可演示链路、成本记录和质量评估；
7. Portfolio 文档中的每项能力都能定位到代码、实验或正式设计状态。

## 8. 主要风险

- 产品能力快速变化导致文档过时；
- 本地设备和免费公网入口不稳定；
- 知识资产增长快于 Registry 和影响分析能力；
- 过度设计控制面，延迟真实业务验证；
- 为追求自动化而削弱人工审批和事实核验。

缓解方式是维持最小可验证批次、官方事实定期核验、状态和证据分级，以及让每个长期抽象都有真实调用方。
