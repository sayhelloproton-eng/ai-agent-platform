# SKL-003 规划者与执行器任务交接技能

## 1. 定位

`planner-executor-handoff` 把当前 Chat 与本地 Codex、GPT Work、OpenCode / DeepSeek、Runtime 及未来执行器之间的任务流转收敛为平台级 Skill。

当前 Chat 是大脑，执行器是执行层。

## 2. 核心分工

Chat 负责：

- 恢复仓库和环境事实；
- 调用工具补齐缺失信息；
- 完成确定性分析与影响分析；
- 选择方案；
- 冻结范围、风险、验收和停止条件；
- 复审真实文件、Diff、测试、Commit、远端和副作用。

执行层负责：

- 按冻结合同执行；
- 观测实际结果；
- 提交证据；
- 结构化反馈；
- 在阻断时停止；
- 从获准的安全续跑点继续。

执行器不能替代 Chat 选择目标、架构、方案或范围。

## 3. 单一真源

每个任务只有一个 Canonical Handoff Contract。

聊天启动语、ZIP、Context Package、任务书和执行器 Prompt 都必须从该合同派生，不得形成多个任务真源。

## 4. 执行指导档位

### compact_controlled

用于能稳定遵守边界的执行器。

确定性分析仍然完整，只减少重复历史、逐命令教学和无关上下文。

### stepwise_controlled

用于需要更强操作约束的执行器。

在同一分析上增加固定顺序、具体路径、逐步命令、预期结果、多层校验、检查点、停止条件、续跑点和固定报告。

当前经验默认：

```text
Codex → compact_controlled
OpenCode / DeepSeek → stepwise_controlled
```

这不是永久品牌绑定。新模型应由用户经验或只读探测任务重新分类。

指导档位与执行权限是两个独立维度。前者决定说明粒度，后者决定允许实施的范围：`bounded_implementation` 允许在冻结边界内完成实现、验证和获准的 Git 动作；`frozen_artifacts_only` 只允许机械交付已经冻结的 Artifact，不得重写内容或补做设计。任何指导档位都不会自动扩大执行权限。

## 5. 双向反馈

执行层必须支持：

- Reception Ack；
- Clarification Request；
- Progress Checkpoint；
- Failure / Stop Report；
- Execution Result；
- Review Response。

Chat 返回 Review Feedback。

失败必须报告最后成功门禁、失败步骤、原始错误、副作用、安全续跑点和需要的决定。

完成必须报告文件、测试命令和退出码、Diff、Commit、远端 SHA、产物、限制、未完成项和工作区状态。

## 6. Context Access

`context/**` 的语义负责人是总控 Planner，不是 Executor。

每个 Canonical Handoff Contract 必须声明：

```yaml
context_access:
  mode: read_only
  files: []
  content_source: none
  user_approval: not_required
```

需要修改 Context 时，只允许：

```yaml
context_access:
  mode: write_approved
  files:
    - context/current-status.md
  content_source: planner_full_replacement
  user_approval: confirmed
```

Executor 只能机械覆盖 Planner 提供的完整文件，不能根据仓库状态自行编写、补全或改写 Context。其他 Agent 只能提交变化报告。重要目标、架构、阶段、Roadmap 和治理变化由用户最终确认。

正式治理见 `KNO-011-上下文所有权与维护机制.md`。

## 7. Git Operating Policy

每次交接必须由 Chat 冻结：

- 当前分支与目标分支；
- 目标远端；
- 是否允许创建本地或远程分支；
- Commit 数量与消息；
- 是否允许 Fetch、Pull、Push；
- 精确 Push 目标；
- 是否需要 PR；
- 是否允许 Merge、Rebase、Cherry-pick、Squash 或 Force Push；
- 是否允许删除本地分支、远程分支、Worktree 或交付目录；
- 允许删除的精确远程分支列表。

Chat Review 本身不构成创建远程功能分支的理由。用户要求继续在当前分支时，执行器必须在该分支执行，除非新的 Canonical Contract 明确改变目标。

Reception Ack 必须确认实际分支和 Git 策略；Execution Result 必须报告所有创建、Push、Merge、删除和清理动作。

## 8. 与现有 Skill 的关系

```text
planner-executor-handoff
负责任务流转、上下文、反馈、复审、续跑和执行器切换

deterministic-delivery
负责冻结 ZIP、Overlay、Git 范围、Commit、Push 和确定性续跑

ai-knowledge
负责知识语义、生命周期、Registry 和飞书投影
```

## 9. 当前状态

v0.5.0 增加 Context 所有权和 `context_access` 合同，当前状态为 `in_review`，等待本次落库后的 Chat Commit Review。v0.4.0 继续作为上一版已接受基线。

当前合同覆盖八类严格 Artifact、跨 Artifact 一致性、Manifest、Feedback Contract、Executor Switch Checkpoint、Git Operating Policy 和 Context Access，并吸收了缺失上下文、多真源、环境错误假设、Git Rename、Shell 特殊变量、中文路径、空目录、失败续跑、执行器切换和结果缺证据等历史问题。

它仍是人工规划与受控执行之间的交接层，不是自动 Task Store、自动执行器切换或完整 Agent Runtime 编排。
