# ARC-018 项目治理与汇报架构

## 1. 文档定位

本文定义项目治理、状态汇总和阶段汇报如何建立在 Task、Registry、Release、Evidence 与风险事实之上。汇报是治理数据的投影，不是人工重新编写的一套状态。

## 2. 治理视图

项目至少维护 Scope、Milestone、Task、Capability、Asset、Release、Risk、Decision、Dependency、Evidence 和 Resource Usage 视图。不同汇报面向 Project Owner、执行者、Reviewer 和外部展示，但共享同一事实来源。

## 3. 状态模型

```text
planned
→ active
→ at_risk / blocked / paused
→ completed / cancelled
```

状态必须由可验证事件驱动。百分比只能用于有明确可计数分母的工作，不能用主观“完成 80%”替代剩余范围和风险。

## 4. 汇报生成

阶段报告包含：本期目标、已完成事实、证据、未完成项、偏差、风险、资源、决策请求和下一阶段计划。系统从 Registry、Git、测试和 Task Store 聚合候选数据，由治理角色检查后发布。

## 5. 升级与决策

阻塞、预算耗尽、范围漂移、关键测试失败或外部依赖变化必须升级。升级记录影响、已尝试措施、可选方案、推荐决定和最晚决策时间。

## 6. 当前实现边界

当前项目通过 `context/current-status.md`、Roadmap、Registry、Release 和 Git Commit 维护状态，阶段报告仍由 Chat 与执行报告人工综合，且曾发生 Context Drift。

## 7. 目标设计边界

目标建立只读状态聚合器和项目治理智能体，按固定 Commit 生成候选报告；人类 Review 后更新正式 Context。运行中精确状态仍归 Task Control，长期事实归 Git。

## 8. 设计原则

- 汇报从事实生成，不反向创造事实。
- 完成必须有验收和证据。
- 风险、未知和未完成项必须显式。
- 同一指标使用稳定口径和时间范围。
- 对外叙述不得超过真实证据等级。
