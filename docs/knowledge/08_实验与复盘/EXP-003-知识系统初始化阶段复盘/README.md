# EXP-003 知识系统初始化与单一真源收敛复盘

> 核心结论：阶段性成果看似只是把一批 Git 文档发布到飞书，真正建立的是“Git 保存正式事实、飞书负责阅读投影、Agent 按最小 Context 工作、发布结果必须回读”的知识系统边界。

## 1. 复盘范围

本文复盘 2026 年 7 月知识系统初始化阶段。文中“17 个知识页面发布成功”是当时阶段结果，不代表当前知识资产数量。

复盘对象包括：

- Git 与 Feishu 的权威关系；
- 正式知识与普通 Markdown 的边界；
- Markdown 到云文档的内容投影；
- 多模型和多执行器的任务分工；
- 失败、成本和返工如何改变架构。

## 2. 初始目标与隐藏问题

初始目标是“整理 Git 文档并同步到飞书”，实际包含四个未解决问题：

1. Git 和飞书谁是真源；
2. 哪些文件算正式知识；
3. Git Markdown 怎样变成飞书文档；
4. 多个 Agent 怎样协作而不重复消耗上下文和 Token。

飞书页面是最直观的成果，因此早期先建设目录和页面；但知识模型尚未稳定，越早物化页面，后续返工越大。

## 3. 阶段时间线

### 3.1 先证明能力可用

第一阶段完成：

- 公开仓库清理；
- GitHub CLI、提交身份、Remote 和 Push 修复；
- README、Context、治理规则和 Skill 初版；
- 飞书 Wiki / Docx / 跨租户读取实验；
- 飞书知识库和初始目录；
- 双源协作模型候选。

这一阶段解决“能不能跑”，没有解决“谁拥有正式事实”。

### 3.2 推翻双源模型

旧模型尝试维护：

- `feishu-map.yaml`；
- 逐页面 Mapping；
- sync / merge；
- 多种发布模式；
- Drift 和冲突处理。

只要飞书也可以独立修改正式内容，Agent 就无法可靠判断 Git 和飞书谁正确。最终收敛为：

```text
Git Canonical Knowledge
  → build / transform
  → Feishu overwrite projection
  → readback
```

飞书不回写、不合并、不成为第二真源。

### 3.3 从“所有文档”收敛为“正式知识资产”

仓库中的 Context、Task、实验、运维、技术证据、Archive 和个人信息都可能是 Markdown，但职责不同。

最终发布源收敛为 `docs/knowledge/**`：

- 正式文档进入知识目录；
- Context 继续承担项目短入口；
- 技术证据、运行记录、迁移和 Archive 不自动发布；
- 私密内容不进入正式发布源。

### 3.4 从复制 Markdown 收敛为内容投影

真实发布暴露：Front Matter、图片、Mermaid、相对链接和部分成功回执等问题。

最终形成：

- 过滤仓库元数据；
- 按目标平台转换结构；
- 图片由 Publisher 上传为原生媒体块；
- 已发布资产使用内部链接；
- 其他链接固定到 Git 版本；
- 发布后逐页回读；
- Git 与 Feishu 追求语义等价，不要求物理格式相同。

### 3.5 从“强模型全包”收敛为按任务不确定性分工

强模型同时承担架构判断、机械改名、发布和失败修复，会快速消耗高价值上下文。最终形成：

- Planner 负责事实、判断、边界和完整文件；
- Executor 负责冻结 Scope 内的机械操作；
- Script / CI 负责可确定校验；
- 高风险副作用需要明确授权和回读；
- Handoff 和冻结 Artifact 替代重复解释。

## 4. 已形成的正式决定

| 问题 | 收敛决定 | 当前正式落位 |
|---|---|---|
| Git / Feishu 权威冲突 | Git 唯一真源，Feishu 单向覆盖投影 | `ARC-005`、`KNO-006`、ADR-002 |
| 普通 Markdown 与知识混杂 | 正式知识集中在 `docs/knowledge/**` | Knowledge Governance、Registry |
| Markdown 直接复制失败 | 构建面向目标平台的语义投影 | Publisher、Document Bundle |
| Agent 重复理解与高成本执行 | Planner / Executor / Script 分工 | `WFL-005`、`WFL-006`、Handoff Skill |

## 5. 失败与限制

- 早期飞书目录和映射在模型未稳定前物化，产生返工；
- 发布“成功响应”与页面真实完整性不完全等价；
- 跨租户可读依赖有效身份和权限；
- 异构 Wiki 节点需要不同 Provider；
- 当时的页面数量和工具状态是历史事实，不应被描述为当前状态。

## 6. 可复用经验

1. 先确定 Canonical Model，再建设投影目标。
2. 每个系统只拥有一种明确职责。
3. 发布必须固定源版本并执行回读。
4. 外部全文、运行状态和正式知识不能混库。
5. 可脚本化的检查不依赖模型抄写。
6. 复盘只有推动架构、工作流或工具变化才算闭环。
