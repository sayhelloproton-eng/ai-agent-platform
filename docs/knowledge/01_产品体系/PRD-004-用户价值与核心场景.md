# PRD-004 用户价值与核心场景

> 用户购买的不是“更多 AI 功能”，而是减少上下文搬运、执行不确定性、事实漂移和作品集证明成本。

## 1. 用户价值模型

下表同时列出已经实现的机制和目标机制；具体成熟度以 [CTX-005 当前能力与演进差距](../00_项目入口/CTX-005-当前能力与演进差距.md) 与 [PRD-005 能力地图与演进路线](./PRD-005-能力地图与演进路线.md) 为准。

| 摩擦 | 平台机制 | 直接价值 |
| --- | --- | --- |
| 每次新会话重新解释项目 | Git Context Root、最小读取、Registry | 减少重复上下文和认知偏差 |
| Chat 的方案难交给 Codex | Task Contract、目标/约束/验收 | 降低误执行和返工 |
| 多窗口并行互相覆盖 | Execution Lane、Branch/Worktree | 降低写冲突和污染 |
| 工具调用有副作用 | Auth、Policy、Approval、Ledger | 降低误操作和不可逆风险 |
| 失败后不知道从哪里继续 | Checkpoint、Snapshot、Recovery | 减少任务丢失 |
| 文档、代码、飞书不一致 | Git 真源、Projection、Drift 检测 | 提升事实可信度 |
| 做了很多却难以展示 | Evidence、Experiment、Portfolio Mapping | 将工作转成职业证明 |

## 2. 场景一：从 Chat 规划到 Codex 执行

用户在 Chat 中讨论目标。Chat 读取当前事实，生成明确 Task：背景、目标、输入、允许文件、禁止范围、步骤、验证和交付物。用户把任务交给 Codex/Work。执行器读取仓库规则、修改、测试并返回 Diff 与证据。Chat 再复审结果和下一步。

当前已具备规划/执行角色边界、Contracts 和安全 Runtime 链路；尚缺完整 Codex Adapter、持久 Task State 和自动证据登记。

## 3. 场景二：专业 Custom GPT 查询和提交任务

架构、产品、知识治理等专业 GPT 通过独立 Instructions、两层 Knowledge 和最小 Actions 工作。它可以查询 Goal/Task/Knowledge，提交专业结果或请求审批，但不能直接修改任意状态。

目标状态下，Gateway 将 Agent 身份映射到 Profile 和 Scope，由 Task State 与 Policy 判断命令是否合法。当前 Gateway 只有固定外部 Key、Capability Policy 和 `runtime.status` 窄链路。

## 4. 场景三：多任务并行开发

一个稳定 Task 可以拥有 Planning、Implementation、Testing、Review 和 Integration Lane。需要并行隔离时，可由当前任务 Git Operating Policy 授权写入 Lane 绑定独立 Branch / Worktree 和单一写入者；普通迁移或当前分支落库不默认创建。Session 崩溃时可以换执行器，不改变 Task 身份。

价值是避免把“窗口”误当“任务”，同时使移交和合并有明确边界。该场景目前已完成架构设计，尚未进入 Runtime 实现。

## 5. 场景四：任务失败、暂停与恢复

系统检测上下文不可信、执行器异常、网络/权限失败、资源不足或状态冲突时，不无限重试。它应：诊断 → 暂停/降级 → 保存 Snapshot → 建议处置 → 人工审批 → 修复或移交 → 验证 → 继续/终止。

用户价值不是“永不失败”，而是失败可理解、现场不丢失、后续动作安全。当前只有进程 Timeout、Busy 和快速失败等底层边界，完整恢复治理未实现。

## 6. 场景五：知识沉淀和飞书发布

学习、调研、代码和实验先形成 Git Draft，经 Review 后进入正式知识或 ADR。Publisher 根据 Projection 规则把 `docs/knowledge/` 覆盖发布到飞书，上传 `asset://` 图片并回读。

用户无需在 Git 和飞书之间手工合并，飞书也不能反向改变项目事实。Phase 1 已验证该方向，新知识树在全库 Review 完成前保持 unpublished。

## 7. 场景六：形成求职 Portfolio

系统从代码、测试、实验、决策和 Demo 中构建证据索引。作品集文章回答：问题是什么、为什么选择该方案、遇到什么失败、怎样验证、当前限制和下一步是什么。

远期架构可以展示思考深度，但必须标为设计；简历中的“已实现”只能引用可定位的 Git 和运行证据。

## 8. 核心用户旅程

```
提出目标
→ Chat 澄清与任务化
→ Gateway 校验身份/权限/状态
→ 执行器工作
→ 测试与证据登记
→ Chat/人工 Review
→ 知识与状态更新
→ 下一 Task
```

任何一步失败，都应回到结构化 Task 和证据，而不是依赖模型记忆猜测。

## 9. 当前优先场景

近期只优先验证三条：

1. Chat → Task → Codex → Git；
2. 专业 GPT → Gateway → Runtime → 安全 Capability；
3. 完成 Git Knowledge 正式化，并在全库 Review 后恢复 Feishu Projection。

多 Agent 自循环、完整自动修复和通用产品孵化属于后续，不应挤占核心闭环。
