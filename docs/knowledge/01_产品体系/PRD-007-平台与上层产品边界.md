# PRD-007 平台与上层产品边界
> **资产状态**：本文正文已在 Batch 02 交付包中完成内容 Review；进入仓库后先标记为 `partial / unpublished`，待真实 Commit 整体复审通过后再升级为 `accepted`。

> 平台解决跨产品重复出现的工程机制；上层产品解决特定用户、领域对象和体验。Provider 和设备属于可替换基础设施。三者混在一起会导致平台臃肿、产品失焦和代码无法验证。

## 1. 三层边界

### 平台核心

负责 Task/Result Contract、身份、Policy、状态、Execution Lane、Approval、Evidence、Health/Recovery、Knowledge、Registry、Provider Port 和通用 Skill 治理。

### 上层产品

负责产品目标、用户旅程、业务领域模型、专属 Agent、专属 Skill、业务数据、业务 UI、质量标准和产品 Demo。AI 视频工作流属于这一层。

### 外部 Provider / Infrastructure

模型 API、本地模型、GitHub、飞书、Dev Tunnels、云服务、设备、存储和第三方工具。它们通过 Adapter/Port 接入，不成为 Domain 真源。

## 2. 判断一项能力归属的平台测试

当一个能力满足以下多数条件，才进入平台：

- 至少被两个不同业务场景需要；
- 语义不依赖具体产品领域；
- 可以定义稳定 Contract；
- 需要统一安全、证据或恢复；
- 更换 Provider 时上层无需改变；
- 有真实调用方和测试。

否则先留在产品或实验目录，不急于抽象。

## 4. 为什么不创建根级 products/

当前仓库主体就是平台，AI 视频工作流尚未开发。根级 `products/` 会提前复制文档、Agent、Skill 和代码结构，并让平台与产品关系更难理解。

产品真正开始后，按资产类型落位：

```
apps/ai-video-workflow/
packages/<video-domain-package>/
docs/knowledge/.../AI视频工作流/
docs/technical/.../AI视频工作流/
agents/profiles/AI视频工作流/
knowledge-packs/roles/AI视频工作流/
skills/<video-related-skill>/
```

跨目录归属由 `platform-registry/` 的 `belongs_to_product` 和 `supports_product` 关系表达。

## 5. Agent、Skill 与 Knowledge 的边界

- Agent Profile 定义“谁、目标、行为、权限和输出”；
- Knowledge Pack 定义“稳定知道什么”；
- Skill 定义“怎样按可复用程序完成某类工作”；
- Product 定义“为谁解决什么业务问题”；
- Runtime 定义“怎样安全执行和持续”；
- Registry 定义“这些资产怎样关联”。

不要把完整产品知识全部放进 Instructions，也不要让 Skill 承担动态任务状态。

## 6. 数据和资产边界

Git 保存代码、配置、文本知识、Schema、Prompt 模板、轻量样例和元数据。大型媒体、运行时数据库、Secret 和个人敏感数据不直接进入公共 Git。媒体资产需要对象存储/本地存储与哈希、来源和 Registry 关系，具体方案在视频 MVP 前设计。

## 7. 变更影响

平台 Contract 变化可能影响所有产品、Agent、Skill 和执行器；产品领域变化通常只影响该产品及专属 Agent/Knowledge；Provider 变化应主要限制在 Adapter。Registry 和自动校验应帮助识别影响，而不是让正文作者手工记住全部关系。

## 8. 演进原则

1. 产品内先验证，再抽取平台共性；
2. 平台接口稳定后再支持第二个产品；
3. Provider 变化不穿透 Domain；
4. 每次抽象同时更新代码、测试、知识和 Registry；
5. 远期能力可以保留边界，但不创建空实现；
6. Portfolio 清楚区分“平台已实现”和“产品概念设计”。

## 9. 结论

`ai-agent-platform` 的价值是让未来产品共享可信工程机制，而不是吞并所有业务。AI 视频工作流的价值是用真实复杂问题检验这些机制，而不是反过来把平台变成视频专用代码库。
