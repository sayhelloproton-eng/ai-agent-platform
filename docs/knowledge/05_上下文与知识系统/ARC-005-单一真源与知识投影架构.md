# ARC-005 单一真源与知识投影架构

## 一句话结论

项目知识只在 Git 中生产和修改；飞书不再作为第二套知识源，而是由 Git
生成的人类阅读版本。

```text
Git 正式知识
     |
     | 发布
     v
飞书阅读投影
```

这不是“把两个系统保持同步”，而是“从一个真实来源生成另一个阅读视图”。

## 1. 为什么会有这篇文档

项目最初希望同时利用两个平台的优点：

- Git 适合版本管理、代码协作、Diff、回滚和 Agent 读取；
- 飞书适合中文阅读、目录浏览、分享和日常查看。

因此，早期设想是让 Git 和飞书共同保存项目知识，并设计：

- `sync`；
- `mapping`；
- `merge`；
- 逐页面 Node Token；
- 不同资产使用不同 `feishu_mode`。

这个方案看起来完整，实际很快出现了一个无法绕开的疑问：

> 同一篇文档在 Git 和飞书都能修改时，哪一份才算真的？

## 2. 项目中实际遇到的问题

### 2.1 同一个事实出现两个版本

例如，平台架构既存在于 Git，也存在于飞书。

当 Git 中的架构已经修改，而飞书还是旧内容时，Agent 会面临两个答案：

```text
Git：新版架构
飞书：旧版架构
```

反过来，如果人在飞书里顺手修了一段描述，Git 又不知道这次修改存在。

此时问题已经不再是“同步脚本有没有写好”，而是：

- 谁能修改正式事实；
- 谁拥有最终解释权；
- 冲突时谁覆盖谁；
- 历史版本在哪里；
- 新 Agent 应该相信哪一份。

### 2.2 为了同步，额外维护了一套同步状态

双源模型需要长期维护：

- Git 路径；
- Asset ID；
- 飞书 Node Token；
- 最后一次同步 Commit；
- 内容 Hash；
- 飞书 Revision；
- 同步模式；
- Drift 状态；
- 冲突处理结果。

这些信息本身又会过期，最后形成“为了管理知识，又制造了一套新的知识”。

### 2.3 飞书目录反过来影响 Git 目录

早期曾尝试先设计飞书目录，再把 Git 文档迁过去。

结果是 Git 的工程结构开始迁就飞书的阅读结构：

- 目录需要编号；
- 页面需要映射；
- Git README 和飞书目录页混在一起；
- 技术材料、学习记录、运行日志都想进入同一知识树。

这说明展示层正在反向控制事实层。

### 2.4 已经创建的飞书页面最终需要清空重建

因为权威模型和目录结构没有先稳定，前一天创建的飞书目录和页面第二天失去继续维护的价值。

最后只能：

1. 清空飞书知识库中的旧节点；
2. 保留知识库本身和权限；
3. 重新以 `docs/knowledge/**` 为来源发布。

这次返工证明：知识模型没有定下来之前，越早写入外部系统，返工成本越高。

## 3. 市面上常见的三种做法

### 3.1 做法一：Docs as Code，Git 负责生产，阅读站点负责展示

Backstage TechDocs 的基本流程是：

```text
Git Markdown
    |
    v
Prepare
    |
    v
Generate
    |
    v
Publish
    |
    v
Reader
```

源文档和代码一起进入 Git，通过构建和发布流程生成阅读站点。阅读端不拥有原始事实。

这种方式的优点是：

- 文档能走 Pull Request、Diff 和 Review；
- 发布结果坏了可以重建；
- 文档和对应代码能绑定同一个版本；
- 不需要处理阅读站点反向修改源文件。

它最接近本项目最后采用的模式。

### 3.2 做法二：双向同步，让工程人员和内容人员在两端编辑

GitBook Git Sync 支持 GitHub / GitLab 与 GitBook 编辑器双向同步。

这种方式适合：

- 开发者在 Git 中写；
- 内容人员在可视化编辑器里写；
- 团队愿意承担双向转换、权限和冲突处理。

但双向能力不是免费得到的。平台必须负责：

- 两端格式转换；
- 冲突检测；
- 提交与权限；
- 同步失败恢复；
- 编辑器与 Markdown 的能力差异。

对于当前单人、Agent 驱动、Git 已经是工程中心的项目，这套复杂度没有必要。

### 3.3 做法三：Wiki 自己就是独立知识仓库

一些 Wiki 产品也提供版本历史，甚至底层就是独立 Git 仓库。

它能解决“Wiki 内容有历史”的问题，却不能自动解决：

- 代码仓库和 Wiki 仓库之间谁是真源；
- 项目状态和架构事实分散在两个版本空间；
- Agent 需要跨两个仓库恢复上下文。

## 4. 本项目为什么选择单向投影

本项目当前有四个现实条件：

1. 项目由一名 Owner 主导，正式修改不需要多人同时在飞书编辑；
2. Agent、Codex、OpenCode 和脚本都更容易读取本地 Git；
3. 架构、代码、Skill、测试和知识需要在同一个 Commit 下审计；
4. 飞书的主要价值是阅读，不是承担工程版本管理。

因此最终决策是：

```text
Git = 权威来源
飞书 = 阅读模型
Publisher = 确定性转换器
```

具体规则：

- 正式知识只在 `docs/knowledge/**` 中生产；
- 飞书只接受 Git → 飞书发布；
- 不做飞书 → Git 回写；
- 不合并飞书现有正文；
- 同名页面采用覆盖发布；
- 飞书内容可以删除后从 Git 重建；
- 目录 README 只服务 Git 和 Agent 导航，不作为正式飞书正文；
- 正式发布应基于已经 Commit、Push 的固定版本；
- 发布后必须回读，不只相信写入接口返回值。

## 5. 最终落地结构

```text
Git Repository
|
├── docs/knowledge/**       正式知识源
├── docs/technical/**       工程证据与治理
├── docs/adr/**             架构决策
├── context/**              Agent 启动摘要
└── skills/ai-knowledge/**  知识治理与发布规则
          |
          v
Feishu Publisher
          |
          v
飞书知识库「智能体工程探索」
```

最终正式发布验证结果：

- 首页：1；
- 正式知识资产：16；
- 内容页面：17；
- 结构节点：12；
- 根节点：10；
- 总节点：29；
- 发布失败：0；
- 相对链接残留：0。

## 6. 从这次实践抽象出的理论

### 6.1 一个事实只能有一个正式修改入口

系统可以有很多副本、缓存、索引和阅读端，但一个事实只能有一个正式生产入口。

否则所谓“同步问题”，最后一定会变成“权威问题”。

### 6.2 区分事实模型和展示模型

事实模型关心：

- 正确；
- 版本；
- 审计；
- 回滚；
- 关联。

展示模型关心：

- 好读；
- 好找；
- 好分享；
- 适配平台。

两个模型不需要长得一模一样。

### 6.3 下游必须可以重建

判断一个系统是不是投影层，可以问：

> 把它删掉以后，能否只靠权威源完整恢复？

飞书内容可以从 Git 重建，所以它是投影。

Git 不能从飞书可靠恢复代码、历史和工程关系，所以 Git 不能是投影。

### 6.4 单向并不等于低级，反而减少了长期状态

双向同步看起来能力更多，但每增加一个可写端，都会增加：

- 冲突；
- 权限；
-格式转换；
- 错误恢复；
- 审计成本。

只在确实需要多人跨平台共同编辑时，才值得付出这个成本。

## 7. 适用边界

当前方案适合：

- Git 已经是项目工程中心；
- Agent 主要在仓库中工作；
- 飞书主要用于阅读；
- 正式修改可以走 Git Review；
- 需要保证版本、链接和来源可追踪。

未来出现以下需求时，可以重新评估：

- 非技术人员必须直接在飞书创作正式内容；
- 存在多人同时编辑同一知识资产；
- 飞书成为业务流程入口，而不仅是阅读端；
- 已经具备可靠的冲突合并和格式转换能力。

在这些条件出现前，不重新引入双向同步。
