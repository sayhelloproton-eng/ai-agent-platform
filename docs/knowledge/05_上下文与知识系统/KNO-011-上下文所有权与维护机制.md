# KNO-011 上下文所有权与维护机制

## 1. 问题

长期任务、自循环和多 Agent 协作都依赖 `context/` 恢复项目目标、架构、当前阶段和下一步。如果 Context 过期，Agent 即使每一步都执行正确，也可能在错误方向上持续循环。

同时，如果所有思考者和执行器都能直接修改 Context，会出现新的风险：

- 多个角色对同一项目事实给出不同解释；
- Executor 根据局部实现重写长期目标；
- 任务日志、推测和临时状态污染共享上下文；
- Custom GPT 内置 Knowledge 与 Git 最新状态分叉；
- 用户无法确认何时发生了目标、阶段或治理变化。

本机制的目标不是建立复杂状态系统，而是用最少的角色与写入规则保证 Context 持续可信。

## 2. 核心原则

> Context 由总控 Planner 维护，Executor 只执行，其他 Agent 只报告变化，用户最终确认。

Context 是项目级共享启动上下文，不是：

- Runtime Task Store；
- 单个任务的 Checkpoint；
- ChatGPT 用户 Memory；
- Agent 私有记忆；
- 完整知识库；
- 执行日志。

任务级动态状态应进入 Task Store、Checkpoint 或 Evidence；只有项目级共享事实变化才进入 Context。

## 3. 三层职责模型

### 3.1 思考者

思考者包括总控 Planner 和各类专业 Agent，但权限不同。

只有总控 Planner拥有 Context 语义修改权，负责：

- 判断变化是否属于项目级共享事实；
- 判断影响哪个 Context 文件；
- 区分已实现、部分实现、已确认设计和未来候选；
- 生成完整覆盖文件；
- 对重要变化向用户汇报并申请确认；
- 在 Executor 落盘后复审真实 Diff、测试和 Commit。

专业 Agent、Reviewer 和 Research Agent可以读取 Context、识别漂移并报告证据，但不能直接修改。

### 3.2 执行者

Codex、GPT Work、OpenCode、Claude Code 和 Runtime Executor属于执行层。

Executor 负责：

- 接收冻结 Contract；
- 核对基线和 Scope Lock；
- 机械覆盖 Planner 提供的完整文件；
- 运行验证；
- 在获准范围内 Commit 和 Push；
- 返回 Diff、SHA、测试和限制。

Executor 不负责：

- 判断项目目标和阶段；
- 自行总结仓库并重写 Context；
- 选择 Context 叙事；
- 将修改建议扩写为完整正文；
- 给自己增加 Context 写入权限。

### 3.3 用户 Review

Project Owner负责：

- 最终目标和优先级；
- 重要 Context 变化审批；
- 对 Planner 生成内容的最终确认；
- 对落库结果的最终 Review。

## 4. 权限矩阵

| 角色 | 读取 Context | 报告变化 | 生成完整替换文件 | 执行覆盖 | 重要变化审批 |
|---|---:|---:|---:|---:|---:|
| 总控 Planner | 是 | 是 | 是 | 否 | 向用户申请 |
| 专业 Agent / Reviewer | 是 | 是 | 否 | 否 | 否 |
| Executor | 是 | 是 | 否 | 仅精确授权 | 否 |
| Project Owner | 是 | 是 | 可直接修订 | 可手动覆盖 | 是 |

## 5. Context 文件与触发条件

| 文件 | 保存内容 | 更新触发 |
|---|---|---|
| `project-context.md` | 项目目标、范围和产品关系 | 目标或范围变化 |
| `architecture-context.md` | 当前实现、目标架构和边界 | 架构、应用、Package 或能力边界变化 |
| `current-status.md` | 当前阶段、已实现能力、限制和下一步 | 阶段、Release、Skill、主要工作或阻塞变化 |
| `knowledge-strategy.md` | Knowledge、Memory、Task State、Knowledge Pack、Registry 和投影边界 | 知识或发布治理变化 |
| `roadmap.md` | 阶段顺序、完成门槛和延期项 | 优先级、阶段或门槛变化 |
| `README.md` | 目录导航和读取顺序 | 文件、职责或入口变化 |

普通 Bug 修复、内部重构、测试补充和不改变项目级共享事实的小改动，不要求更新 Context。

## 6. 变化报告

非总控角色发现 Context 可能过期时，只输出变化报告：

```yaml
context_change_report:
  required: true
  reason: 新实现的 Runtime 能力未反映在 current-status.md
  evidence:
    - commit: <sha>
    - path: apps/local-runtime/...
    - validation: <command and result>
  suggested_files:
    - context/current-status.md
    - context/architecture-context.md
```

变化报告用于触发 Planner 判断，不构成写入授权。

## 7. Planner 维护流程

```text
接收任务结果或变化报告
→ 判断是否属于项目级共享事实
→ 对照代码、测试、Registry、Release 和 Migration
→ 确定影响文件
→ 生成完整覆盖文件
→ 重要变化向用户申请确认
→ 冻结 Context Access 与 Scope Lock
→ Executor 机械覆盖、验证、Commit、Push
→ Planner 与用户 Review
```

没有项目级变化时，不修改 Context。

## 8. Executor 写入协议

Context 只采用完整覆盖文件，不采用“根据仓库自行更新”或开放式修改清单。

Canonical Handoff Contract 使用：

```yaml
context_access:
  mode: read_only
  files: []
  content_source: none
  user_approval: not_required
```

需要写入时：

```yaml
context_access:
  mode: write_approved
  files:
    - context/current-status.md
    - context/roadmap.md
  content_source: planner_full_replacement
  user_approval: confirmed
```

约束：

- 没有 `context_access` 或模式不是 `write_approved` 时，Executor 不得修改 `context/**`；
- `files` 必须是精确文件，不允许目录通配授权；
- 每个文件必须由 Planner 提供完整替换内容；
- `files` 还必须包含在 Scope Lock 的允许路径中；
- Executor 不得修改覆盖内容，也不得增加其他 Context 文件。

## 9. 用户审批边界

以下变化需要 Planner 先汇报并取得用户确认：

1. 项目目标或产品范围变化；
2. 核心架构或角色边界变化；
3. 阶段完成、取消或切换；
4. Roadmap 主优先级变化；
5. Git、Knowledge、Memory、Feishu 或安全治理变化。

明确事实的小范围同步、链接修正、数量更新和已确认状态修正，可以按既有授权维护。

## 10. 总控 Custom GPT 如何获得职责

仓库规则只能约束进入仓库的执行器，不能自动告诉 Custom GPT 自己是总控 Planner。

总控 Custom GPT 的职责来自：

```text
Agent Profile
+ Instructions
+ 通用基础 Knowledge Pack
+ 运行时读取 Git 最新 Context
```

Instructions 必须明确：

- 自己是总控 Planner；
- 自己拥有 Context 语义维护职责，但不直接执行仓库写入；
- 规划前读取 Git 最新 Context；
- 其他 Agent 只报告变化；
- Executor 只接受完整替换文件；
- 重要变化需要用户确认。

稳定职责进入 Instructions；易变项目状态仍从 Git Context 读取，不能只依赖 Builder 内置 Knowledge。

未来 Agent 资产化后，正式真源应落入：

```text
agents/control-planner/profile.yaml
agents/control-planner/instructions.md
```

在首批真实 Agent 资产准备好之前，不创建空目录。

## 11. 冲突与停止

出现以下情况时，停止基于旧 Context 继续规划：

- Context 与代码、测试或真实调用证据冲突；
- `current-status.md` 与 Roadmap、Release 或 Migration 冲突；
- Executor 声称完成但缺少证据；
- 非总控 Agent 试图直接修改 Context；
- Executor 未获 `write_approved` 却修改 `context/**`；
- 重要变化尚未获得用户确认。

处理方式不是让 Executor 自行修复语义，而是返回证据，由总控 Planner 重新生成完整替换文件。

## 12. 最小闭环

```text
所有角色读取 Context
→ 其他 Agent / Executor 报告变化
→ 总控 Planner 判断和编写
→ 用户确认重要变化
→ Executor 完整覆盖
→ 测试、Commit、Push
→ Planner 与用户回读 Review
```

该机制只依赖角色规则、完整替换文件、Handoff Contract 和既有 Scope Lock，不引入独立的复杂状态机或额外 Context Registry。
