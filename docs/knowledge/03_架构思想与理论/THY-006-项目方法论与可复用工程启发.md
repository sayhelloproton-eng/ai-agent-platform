# THY-006 项目方法论与可复用工程启发

## 1. 文档定位

本文总结 `ai-agent-platform` 已有仓库证据支持的方法。它们是带适用条件的工程启发，不是永远正确的定律。

洞见成熟度仍以 Engineering Insight Registry 为准。

## 2. 固定 SHA

### 方法

执行前固定本地和远端 Commit。

### 价值

- 防止输入漂移；
-让交付包可复现；
-使 Review 有明确基线。

### 不适用

纯临时讨论无需固定 SHA。

### 证据

知识重构和 Gateway 任务都使用固定起始 Commit。

## 3. Scope Lock

### 方法

明确：

- 允许已有文件；
-允许新增文件；
-禁止范围；
-外部动作；
-停止条件。

### 价值

防止 Agent 顺手重构和误提交。

### 失败案例

范围检查只看已跟踪文件，遗漏未跟踪新增文件，导致假失败。正确门禁必须组合：

```text
git diff --name-only
+ git ls-files --others --exclude-standard
```

## 4. 单逻辑批次

一个 Commit 只表达一个完整目的。

优点：

- Review 清楚；
-容易回滚；
-Release 和 Registry 可对应；
-失败范围小。

但批次过小也会浪费 Token 和时间。应按“逻辑完整且可审阅”确定粒度，而不是每篇文章一个 Commit。

## 5. 设计与执行分工

### 高不确定性

由强模型和人类完成：

-事实恢复；
-架构；
-正文；
-冲突判断；
-Review。

### 确定性落盘

由弱模型或脚本完成：

-复制文件；
-更新明确字段；
-运行测试；
-Commit；
-Push。

这不是按模型品牌分工，而是按任务不确定性分工。

## 6. 程序负责确定性判断

适合脚本：

- Schema；
-路径；
-ID；
-链接；
-空白；
-文件数量；
-范围；
-测试。

模型不应反复阅读大量文件来判断可以由程序得到的布尔结果。

## 7. 真实 Commit 后复审

完成报告可能遗漏：

-未提交文件；
-错误路径；
-内容 Drift；
-范围外修改；
-远端 Push 失败。

因此正式 Acceptance 必须基于真实 Commit 快照，而不是执行者摘要。

## 8. 风险增量决定 Review 强度

### 低风险

文档格式、明确字段更新：差异 Review + 自动门禁。

### 中风险

跨文档语义、Registry 关系：相关资产 Review。

### 高风险

认证、权限、数据、外部写入、不可逆操作：完整链路和人工批准。

已有可信基线后，不需要每次从零审计整个仓库。

## 9. Phase-fit

技术方案先匹配当前阶段。

MVP 优先验证：

-最高风险假设；
-最小真实路径；
-可观察结果；
-退出条件。

不要在核心假设未通过前建设大量未来治理，也不要把开发期 Tunnel 描述为生产架构。

## 10. Token 是系统资源

Token 浪费通常来自：

-重复扫描；
-模糊任务；
-让执行模型重新设计；
-门禁脚本错误；
-批次过碎；
-失败后堆叠 Prompt；
-用强模型做复制。

优化方式：

```text
事实一次恢复
→ 内容一次冻结
→ 本地模拟
→ 确定性执行包
→ 一次落库
→ 风险级 Review
```

## 11. 停止条件是可靠性机制

Agent 遇到以下情况应停止：

-基线不一致；
-范围冲突；
-需要新决策；
-验证失败且原因未知；
-权限未授权；
-Token 不足以完成验证。

停止不是失败。带着未知继续写入，才是更大风险。

## 12. 洞见成熟度

一次事件通常只支持 Candidate 或 Provisional。

升级需要：

-独立重复事件；
-明确 Precondition；
-反例；
-稳定检查项；
-正式 Review。

当前五条初始洞见中，风险分级复审仍为 Candidate，不能写成普遍定律。

## 13. 方法总表

| 方法 | 主要解决 |
|---|---|
| 固定 SHA | 输入漂移 |
| Scope Lock | 越界 |
| 单逻辑批次 | Review 和回滚 |
| 强弱模型分工 | Token 与判断质量 |
| 程序门禁 | 确定性错误 |
| 真实 Commit Review | 完成声明失真 |
| 风险增量 Review | 审计成本 |
| Phase-fit | 过度设计 |
| Stop Rules | 错误扩大 |
| Insight Maturity | 一次事件过度抽象 |

## 15. 结论

可靠 Agent 工程不是让模型永不停下，而是让不确定性在正确层被发现，让确定性工作由程序完成，让每次正式状态变化都有证据。
