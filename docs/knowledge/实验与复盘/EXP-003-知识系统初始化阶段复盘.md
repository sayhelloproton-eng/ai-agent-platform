# EXP-003 知识系统初始化阶段复盘

## 一句话总结

从结果看，这两天只完成了一件事：

> 把 Git 中的 17 个知识页面稳定发布到飞书。

但真正完成的不是一次文档搬运，而是把“Git、飞书、Agent 和知识文档各自负责什么”
这件事弄清楚了。

最终形成了四项可以复用的能力：

```text
单一真源
知识分层
内容适配
多模型执行治理
```

## 1. 最初想解决什么问题

项目希望建立一个长期知识系统，让：

- 人能看懂项目在做什么；
- ChatGPT 能参与需求和架构；
- Codex / OpenCode 能接手仓库任务；
- 飞书能作为中文阅读入口；
- Git 能保存版本、变更和代码；
- 经验、失败和决策不会只留在聊天里。

最初把任务理解为：

> 整理 Git 文档，然后同步到飞书。

实际执行后发现，这句话隐藏了四个更难的问题：

1. Git 和飞书谁是真的；
2. 哪些文件算正式知识；
3. Git Markdown 怎么变成飞书文档；
4. 多个 Agent 如何在不浪费 Token 的情况下协作。

## 2. 2026-07-26：先把仓库和飞书跑起来

第一天主要做了这些事：

- 清理公开仓库中不该提交的本地状态和第三方全文；
- 修复 GitHub CLI、提交身份、Remote 和 Push；
- 建立 README、Context、治理规则和 Skill 初版；
- 调研飞书 Wiki、Docx、公开访问和跨租户读取；
- 创建飞书知识库及初始目录；
- 尝试把 Git 和飞书设计成两个协作知识源。

这一天解决了“能不能跑”的问题，但留下了一个更大的结构问题：

> 正式知识模型还没有稳定，就已经开始建设飞书目录。

### 当时为什么会这么做

因为飞书是最直观的成果：

- 页面能看到；
- 目录能浏览；
- 人会觉得知识库已经建立。

但飞书页面建得越早，后面知识模型一旦变化，返工越大。

### 第一天的重要发现

#### 公开网页、OpenAPI 可读和匿名可读不是一回事

WaytoAGI 公开知识库实验发现：

- 网页能打开；
- 有身份的 Token 可以通过 API 读取；
- 不等于匿名 API 可以读取。

#### 飞书 Wiki 节点不全是文档

递归读取时发现：

- `docx` 可以按文档读取；
- `sheet`、`bitable` 需要不同适配器；
- shortcut 需要先解析真实对象。

因此 Feishu Provider 不能把所有节点都当成 Markdown 页面。

#### 创建接口需要自己补幂等

Space 和 Node 创建没有可靠业务幂等键时，执行前必须查重，执行后必须回读。

这些实验后来进入了 EXP-001、EXP-002 和 Skill 规则。

## 3. 2026-07-27：推翻旧模型并重新发布

第二天开始审计仓库，发现当时同时存在：

- Context；
- 正式知识；
- 任务输入；
- 执行结果；
- 调研报告；
- 实验记录；
- 运维记录；
- 私人信息；
- 飞书映射；
- 多种同步模式。

这些内容虽然都叫“文档”，但职责完全不同。

随后连续发生了四次关键收敛。

## 4. 第一次收敛：从双源改为 Git 唯一真源

### 遇到的问题

旧模型认为：

```text
Git + 飞书 = 两个协作来源
```

为此设计了：

- `feishu-map.yaml`；
- 逐页面 Mapping；
- sync / merge；
- 多种 `feishu_mode`；
- Drift 和冲突处理。

很快发现，只要飞书也能独立修改正式内容，Agent 就无法判断 Git 和飞书谁正确。

### 市面上的启发

Backstage TechDocs 等 Docs-as-Code 方案把 Git 作为源，阅读站点作为构建结果。

GitBook 的双向同步说明双向编辑是可行的，但需要平台长期承担格式转换、权限和冲突成本。

### 最终处理

项目选择符合当前需求的简单模型：

```text
Git
 |
 | overwrite publish
 v
Feishu
```

- Git 是唯一真源；
- 飞书是阅读投影；
- 不回写；
- 不合并；
- 不维护逐页面 Mapping；
- 飞书可以清空后从 Git 重建。

对应理论：ARC-005。

## 5. 第二次收敛：从“所有文档”改为“正式知识资产”

### 遇到的问题

仓库里有很多 Markdown，但不是每个 Markdown 都应该进飞书。

例如：

- 目录 README；
- 发布审计报告；
- Task 输入；
- OPS 记录；
- Archive；
- 学习草稿；
- 私人 Context。

如果全部发布，飞书会变成仓库文件浏览器，而不是知识库。

### 最终处理

正式发布源收敛为：

```text
docs/knowledge/**
```

其中：

- 根 README 是飞书首页；
- 16 个正式 Asset 是知识正文；
- 目录 README 只负责 Git / Agent 导航；
- 技术证据、ADR、学习和运行记录不自动进入飞书；
- 私人内容永远不进入正式发布源。

对应理论：ARC-006。

## 6. 第三次收敛：从复制 Markdown 改为内容投影

### 遇到的问题

第一次真实发布暴露：

- Frontmatter 进入正文；
- 图片不能稳定展示；
- Mermaid / 画板不稳定；
- 相对链接失效；
- 写入返回部分成功，但页面实际完整。

### 市面上的启发

CommonMark 只定义基础 Markdown 语法。

Backstage 等文档系统会先生成目标内容，再发布。

飞书官方导入流程也会把 Markdown 转换成云文档，而不是保存原文件。

### 最终处理

建立 Text-first Projection：

- 过滤 Frontmatter；
- 排除图片、Mermaid 和二进制资源；
- 架构图改用文本图；
- 已发布资产链接转换为飞书内部链接；
- 其他链接转换为固定 Commit GitHub 链接；
- 发布后逐页回读。

对应方案：SOL-004。

## 7. 第四次收敛：从“强模型全包”改为按任务分工

### 遇到的问题

同一天里，强模型同时承担：

- 恢复上下文；
- 架构判断；
- 目录迁移；
- 文件改名；
- Skill 修改；
- Preview；
- 飞书发布；
- 失败修复；
- 大段执行报告。

结果是：

- Codex Token 快速耗尽；
- 多轮方案被推翻；
- 机械修改也占用高级额度；
- 后续只能改用较弱模型；
- 每个 Agent 又要重新理解仓库。

### 市面上的启发

主流 Agent 工程强调：

- 清晰指令；
- Guardrails；
- 失败阈值；
- 高风险动作人工介入；
- 多 Agent 只在复杂度确实需要时使用。

### 最终处理

形成分工：

- ChatGPT：调研、问题定义、架构、任务合同和 Review；
- Codex：高不确定性、多模块实现；
- DeepSeek / OpenCode：范围和内容已确定的机械修改；
- Script / CI：路径、链接、YAML、Asset 和 Diff 校验；
- Project Owner：接受决策和授权不可逆动作。

对应工作流：WFL-004。

## 8. 最终发布结果

知识库清空旧节点后，按最终模型正式发布。

结果：

- 知识库：智能体工程探索；
- 首页：1/1；
- 正式知识页面：16/16；
- 内容页面成功：17；
- 失败：0；
- 根节点：10；
- 总节点：29；
- Frontmatter 过滤：16；
- 飞书内部链接转换：18；
- GitHub 固定 Commit 链接：6；
- 相对链接残留：0；
- 全部 17 页回读验证通过。

API 出现 `partial_success / 1011` 告警，但页面实际生成 Revision，回读内容完整，因此没有盲目重试。

## 9. 为什么看起来“一天只干成了一件事”

因为当天不是在简单搬文档，而是在不断撤销错误假设。

```text
先假设双源可行
        |
        v
发现权威冲突
        |
        v
改成 Git 单源
        |
        v
发现目录和资产边界不清
        |
        v
重新迁移知识
        |
        v
发现格式不能直接复制
        |
        v
建立投影规则
        |
        v
清空飞书重新发布
```

可见结果只有一个知识库，但支撑这个结果的模型已经变了四次。

如果这些决策没有被记录，下一次换 Agent 或换平台时，还会重走一遍。

## 10. 做得不好的地方

### 10.1 外部系统介入过早

应该先稳定 Git 中的：

- 目录；
- Asset；
- 权威关系；
- 发布合同。

再进入飞书创建。

### 10.2 一个任务混合了太多类型

架构决策、机械迁移、Skill 修改和外部发布不应塞进一个长任务。

### 10.3 正式发布前没有先固定 Git 版本

最终报告显示发布时源文件 Hash 未变化，但正式流程仍应是：

```text
Validate
→ Commit
→ Push
→ Publish
```

而不是从未提交工作树发布。

### 10.4 状态文件没有随阶段完成更新

后续 OpenCode 进入仓库时，`current-status.md` 仍显示 Task 001 进行中。

说明“知识发布完成”不等于“Agent 上下文完成”。

### 10.5 规则分散后缺少自动一致性检查

文件改成中文路径后，配置、链接、Asset Index 和旧文档可能继续引用英文路径。

这类问题不能长期依赖模型人工发现。

## 11. 本阶段沉淀出的四条方法论

### 方法一：不要同步知识，要投影知识

同步意味着两边都可能是源。

投影意味着下游可以从上游重建。

### 方法二：不要把所有资料都叫知识

当前状态、长期知识、工程证据、私人信息和运行日志需要不同边界。

### 方法三：不要追求格式完全一致，要追求语义一致

跨平台发布要接受受控降级，并对转换结果进行回读。

### 方法四：不要让强模型承担所有劳动

模型应按任务不确定性和风险分工；确定性问题交给脚本验证。

## 12. 阶段结束后仍需处理的问题

本复盘不把以下事项写成已完成：

- Context 与仓库状态仍可能漂移；
- 中文改名后的路径和链接需要全仓 Integrity Gate；
- `.private-context` 的 README-only 跟踪规则需要复核；
- 旧 Mapping / Feishu Native 描述需要彻底清理；
- 正式发布必须固化 Commit-first 规则；
- 多模型 Task Contract 还需要真正成为日常工作流。

## 13. 下一阶段

飞书知识库初始化已经告一段落。

下一阶段不再继续调整飞书目录，而是：
