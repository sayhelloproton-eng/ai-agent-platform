# EXP-003 知识系统初始化阶段复盘

## 1. 复盘范围

本复盘覆盖 2026-07-26 至 2026-07-27 的知识系统初始化工作。

最终可见结果只有一个：

> 将 Git 中的正式知识资产，以受控方式发布到飞书知识库“智能体工程探索”。

但实际工作不是一次简单的文档搬运，而是连续推翻了不成立的权威模型、目录模型、内容格式和执行流程，并形成了一套可以继续复用的知识工程方法。

本复盘不逐条堆叠所有命令和临时错误，而是按五类问题归纳：

```text
仓库与资产边界
知识权威与目录模型
飞书能力与内容模型
Agent 执行与成本
验证、漂移与可恢复性
```

## 2. 两日时间线

### 2026-07-26：先建立远程闭环

主要完成：

- 清理首次公开仓库的敏感和非必要内容；
- 修复 GitHub CLI、提交身份、Remote 和 Push 链路；
- 建立项目 Context、治理规则和 AI Knowledge Skill 初版；
- 调研飞书 CLI、Wiki、Docx、公开访问和跨租户读取；
- 创建飞书知识库及初始目录；
- 将 Git 和飞书设想为两个协作来源。

当日最大的问题是：

> 在正式知识模型稳定前，过早进入了飞书目录和页面建设。

### 2026-07-27：推翻双源并重建投影

主要完成：

- 审计仓库中混放的 Context、Task、Result、Research、Experiment 和 OPS；
- 迁移并重新分类知识资产；
- 将 Git 与飞书双源模型改为 Git 唯一真源；
- 删除逐页面 Mapping 和多种同步模式；
- 将知识源收敛为 `docs/knowledge/**`；
- 将图片、Mermaid 和资源文件改为文本优先内容；
- 清空旧飞书节点并按新模型正式发布；
- 对 17 个内容页面进行回读验证。

当日最大的问题是：

> 架构决策、文件迁移、发布适配和外部写入同时进行，导致大量强模型 Token 被用于返工和重复验证。

## 3. 问题一：仓库与资产边界没有先定义

### 现象

初始仓库中混合了：

- 项目正式文档；
- 本地 Agent 状态；
- 私人 Context；
- 第三方知识库完整导出；
- 可重建压缩包；
- 飞书初始化任务和执行结果；
- 临时 Prompt；
- XML 快照和本地缓存。

如果直接提交，会同时产生隐私、版权、仓库污染和 Agent 检索噪声。

### 如何发现

通过首次暂存区审计、公开仓库检查和迁移盘点发现。后续 ZIP 迁移又暴露了 `.git`、`.DS_Store`、脚本执行位和中文路径编码风险。

### 根因

当时没有稳定的资产分类模型，只按“这个文件有没有用”判断是否进入仓库，没有回答：

- 谁是作者；
- 是否可以公开；
- 是否可重建；
- 是否是正式事实；
- 是否只对本地 Agent 有意义；
- 是否需要长期审计。

### 失败倾向

最危险的做法是把“以后可能有用”当作提交理由，将所有文件放入仓库再依赖人工记忆区分。

### 最终处理

建立四类边界：

```text
Public Project Asset
Private Context
Secret / Authentication State
External Evidence
```

对应原则：

- 正式项目事实进入 Git；
- 私人 Context 保留本地，正文不提交；
- Secret 和认证状态不进入仓库；
- 第三方全文默认不公开，只保存摘要、结构、脚本和可验证证据；
- 本地运行状态和可重建中间产物不提交。

### 形成的理论

仓库治理的第一步不是目录设计，而是**资产资格判断**。

一个文件进入 Git 之前，至少要回答：

```text
Authority
Ownership
Confidentiality
Reproducibility
Retention
```

### 当前状态

Partially Resolved。

`.private-context` 的 README-only 跟踪规则需要继续核对，避免私人正文安全了，但边界说明也一起消失。

## 4. 问题二：知识权威模型和物理目录相互冲突

### 现象

项目先后出现过三种设想：

```text
Git + Feishu 双源
Git / Feishu 多模式同步与 Mapping
Git 唯一真源 + Feishu 单向投影
```

同时，目录结构也在以下方案间变化：

- 编号式知识目录；
- 按 Feishu 阅读目录组织 Git；
- 按 Git 工程职责组织；
- `context/`、`docs/knowledge/`、`docs/technical/` 内容重复。

### 如何发现

当架构、ADR、当前状态和 Skill 边界在 Git 与飞书都有版本时，Agent 无法判断冲突时信任哪一份。

迁移文件名和目录后，又出现：

- 配置仍引用旧英文文件名；
- Markdown 链接失效；
- 资产索引和路径不一致；
- Context 状态停留在旧阶段。

### 根因

把“存放位置”误当成“事实权威”，并让飞书阅读结构反向决定 Git 工程结构。

### 被放弃的方案

#### 双源事实

优点是两端都方便编辑，缺点是必须解决冲突、版本、覆盖和晋升。

对当前单人项目而言，治理成本高于收益。

#### 逐页面 Mapping

需要维护路径、Token、Commit、Hash、Revision、Sync Mode 和 Drift Status。当前阶段并不需要这么多持久状态。

#### 编号式大目录

插入新分类会导致整体改名，历史上已经发生 ADR 目录编号漂移。

### 最终处理

确立：

```text
Git
= 唯一正式事实源

docs/knowledge/**
= 人类知识发布源

Feishu
= 可重建阅读投影
```

Git 内部继续按职责分层：

```text
context/
docs/knowledge/
docs/technical/
docs/learning/
docs/adr/
skills/
```

飞书阅读目录只由 `docs/knowledge/**` 映射，不反向控制其他工程目录。

### 形成的理论

权威模型应先于目录模型。

```text
Authority
    |
    v
Lifecycle
    |
    v
Physical Location
    |
    v
Projection
```

只有先定义谁拥有最终解释权，才能决定目录、同步方向和冲突规则。

详见：

- [`ARC-005 单一真源与知识投影架构`](../知识系统/ARC-005-单一真源与知识投影架构.md)
- [`ARC-006 项目知识分层与 Agent 上下文架构`](../知识系统/ARC-006-项目知识分层与Agent上下文架构.md)

### 当前状态

Partially Resolved。

现有 `knowledge.config.yaml`、部分治理文档、旧 Solution 和 Context 仍需要执行一致性修复。

## 5. 问题三：飞书不是 Git Markdown 的等价渲染器

### 现象

实际发布暴露了：

- YAML Frontmatter 进入飞书正文；
- 本地图片无法自动上传；
- GitHub Raw 图片不能稳定转成飞书图片块；
- Mermaid 不能稳定呈现；
- `.mmd`、draw.io 和二进制资源不能直接投影；
- 相对链接在飞书失去目标；
- 目录 README 产生无价值页面；
- Wiki Node 可能指向 `docx`、`sheet`、`bitable` 或 shortcut；
- API 返回 `partial_success` 时，页面仍可能已经写入完整内容。

### 如何发现

通过三类证据：

1. 官方 CLI Schema 和 OpenAPI 调研；
2. WaytoAGI 公开 Wiki 的递归读取实验；
3. 项目自身的 Preview、正式发布和 17 页回读验证。

### 根因

最初把“飞书支持 Markdown 导入”误解为“飞书支持 Git 中的全部 Markdown 语义”。

实际上，飞书最终保存的是文档和块对象，不是原始 Git Markdown 文件。

### 被放弃的方案

- 直接镜像整个 `docs/knowledge`；
- 通过 Raw URL 自动补图片；
- 自动把 Mermaid 变成画板或截图；
- 将目录 README 当知识页面；
- 看到写入告警后立即重试。

这些方案要么不稳定，要么引入不可审计的 AI 转换，要么可能创建重复页面。

### 最终处理

建立文本优先的 Portable Profile：

允许：

```text
标题
正文
列表
表格
引用
代码块
普通链接
文本图
```

过滤或阻止：

```text
Frontmatter
图片
Mermaid
draw.io
二进制资源
```

链接处理：

```text
已发布知识文档
→ 飞书内部链接

未发布 Git 文档
→ 固定 Commit GitHub 链接

外部网页
→ 保持原链接
```

验收从“API 返回成功”改为“目标页面回读完整”。

详见：

- [`SOL-004 跨平台文档可移植性与发布适配`](../技术方案/SOL-004-跨平台文档可移植性与发布适配.md)

### 当前状态

Resolved for current scope。

当前方案明确牺牲图片和 Mermaid 的直接展示，以换取可重复、可审计、对人和 Agent 都可读的文本投影。

## 6. 问题四：Agent 执行过程没有按不确定性分工

### 现象

一天内大量 Codex Token 被用于：

- 重复恢复仓库上下文；
- 多轮讨论目录；
- 先创建飞书再清空；
- 同一批文件反复改名和校验；
- 多个分支和 Worktree 中重复实现；
- 机械任务仍由强模型执行；
- 每轮都输出长篇审计报告。

最终，Codex 额度耗尽，而项目仍有路径和 Context Drift 需要收尾。

### 如何发现

通过执行时间、提交历史、分支状态和最终剩余额度直接观察。

### 根因

任务没有先拆成：

```text
架构决策
确定性改动
机器验证
高风险外部写入
```

强模型同时承担了设计、搬运、扫描、格式转换、验证和汇报。

### 被放弃的方案

- 让单个 Agent 从模糊目标一直做到外部发布；
- 只用长 Prompt 约束，不建立脚本门禁；
- 多个 Worktree 并行修改同一知识层；
- 每次 Drift 都重新全仓阅读。

### 最终处理

形成分工：

```text
ChatGPT / 强推理模型
→ 问题定义、架构、任务合同、验收

Codex / 强执行 Agent
→ 高不确定性仓库修改

DeepSeek / 确定性执行模型
→ 路径明确、范围锁定、低风险修改

脚本 / CI
→ 路径、链接、YAML、Asset、Diff 校验

Project Owner
→ 决策、外部写入和最终接受
```

详见：

- [`WFL-004 多模型 Agent 执行治理与 Token 预算`](../工作流/WFL-004-多模型Agent执行治理与Token预算.md)

### 当前状态

Decision Recorded，尚未完全自动化。

## 7. 问题五：执行成功和业务成功没有分开

### 现象

曾经容易使用以下信号判断完成：

- 命令退出码为 0；
- Dry-run 通过；
- API 返回成功；
- 文件已经写出；
- 页面节点已经创建。

但这些信号不能证明：

- 内容正确；
- 没有重复页面；
- 链接可用；
- Frontmatter 已过滤；
- 飞书页面与目标 Commit 一致；
- 修复已经进入最终分支。

### 如何发现

- 飞书写入出现 `partial_success / 1011`，但回读完整；
- 多分支并行后，某些修复没有进入 `main`；
- 文件改名完成，但配置和链接仍然失效；
- `context/current-status.md` 与实际阶段不一致。

### 根因

缺少统一的 Definition of Done，且验证被分散在人工记忆、Prompt 和临时命令中。

### 最终处理

验收形成五层证据：

```text
Syntax
→ Structure
→ Reference
→ Behavior
→ External Read-back
```

正式发布顺序调整为：

```text
Validate
→ Review
→ Commit
→ Push
→ Projection Preview
→ Publish
→ Read-back
```

外部系统返回码只作为信号，不作为最终事实。

### 当前状态

Partially Resolved。

飞书发布已经采用回读，但仓库路径、链接、Context 和多分支一致性仍需要统一 Integrity Gate。

## 8. 为什么“两天只干成一件事”

从功能数量看，确实只完成了一个飞书知识库初始化和发布。

从工程价值看，两天实际完成了四次模型纠偏：

```text
文件搬运
→ 知识治理

双向同步
→ 单向投影

平台兼容
→ 可移植内容适配

单模型执行
→ 多模型与机器门禁协作
```

返工的主要原因不是实现速度，而是前置决策顺序错误：

1. 先建飞书，再稳定 Git Knowledge Model；
2. 先设计同步，再决定权威源；
3. 先迁移文件，再建立全仓路径校验；
4. 先调用强模型执行，再区分机械任务和架构任务；
5. 先写外部系统，再固化 Source Commit。

## 9. 当前遗留问题

以下问题不能写成已经解决：

- `knowledge.config.yaml` 仍存在旧英文路径和旧目录引用；
- 全仓 Markdown 链接仍需完整扫描和修复；
- `context/current-status.md` 与当前真实阶段不一致；
- `.private-context` README-only 跟踪规则需要核验；
- ADR、Solution、AGENTS 和 Skill Profile 中仍可能残留 Mapping 或 Feishu Native 旧合同；
- 正式发布所用 Source Commit 与发布时工作树的一致性需要核验；
- 多分支和 Worktree 的任务协议尚未由自动化强制执行。

## 10. 后续动作

### 第一优先级：一致性修复

建立 Repository Integrity Gate，至少验证：

- 配置路径存在；
- Markdown 链接有效；
- Asset ID 唯一；
- Canonical Path 与文件一致；
- Relation 端点存在；
- Context 阶段状态有效；
- Private Context 跟踪符合规则。

### 第二优先级：收敛正式决策

更新 ADR-002 和 SOL-002，删除已废弃的：

- Feishu Native 正式事实；
- 逐页面 Mapping；
- 多种同步模式；
- 自动 Drift Merge。

### 第三优先级：执行治理

将 `WFL-004` 转换为：

- 任务 Prompt 模板；
- Git 分支和 Worktree 规则；
- Token 预算；
- 自动停止条件；
- 外部写入门禁。
