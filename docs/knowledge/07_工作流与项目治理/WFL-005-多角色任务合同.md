# WFL-005 多角色任务合同

## 1. 文档定位

本文定义多个角色共同执行任务时使用的统一 Task Contract。合同锁定目标、版本、范围、角色、权限、验收和停止条件，是协作和恢复的基础。

## 2. 合同字段

```text
task_id
version
goal
context_commit
scope
allowed
forbidden
inputs
role_assignments
dependencies
capability_set
approvals
acceptance
evidence_requirements
stop_conditions
report_format
```

## 3. 角色分配

合同区分 Owner、Planner、Executor、Reviewer、Approver 和 Integrator。一个主体可以承担多个低风险角色，但必须显式记录；高风险写入优先分离执行与批准。

## 4. 版本与变更

执行器使用 `expected_version` 接受任务。目标、范围、权限、输入 SHA 或验收变化时产生新版本，并使旧审批和未提交结果失效。

## 5. 完成条件

完成必须满足 Acceptance、必要测试、Evidence、Side-effect 状态和范围检查。文本报告不能替代真实文件、Commit、回读或外部 revision。

## 6. 当前实现边界

当前专业工程提示词已经包含 Goal、Scope、Allowed、Forbidden、Acceptance 和 Report，但尚未成为持久机器 Contract。

## 7. 目标设计边界

目标在 Task Control MVP 中实现最小 JSON Contract、版本检查和结果 Schema，再连接 Execution Lane、Approval 和 Evidence。

## 8. 设计原则

- 任务目标和长期仓库规则分离。
- 版本变化使旧授权失效。
- 角色、执行器和会话分别记录。
- 完成由验收和证据决定。
- 合同不能超出当前已授权能力。

### Git Operating Policy

任务合同必须明确当前分支、目标分支、Push 目标、PR 与 Merge 策略，以及本地/远程分支、Worktree 和交付目录的删除权限。未明确授权的 Git 副作用一律禁止。

合同还必须分别声明 Guidance Tier 与 Execution Authority。`compact_controlled` / `stepwise_controlled` 只调整操作说明粒度；`bounded_implementation` / `frozen_artifacts_only` 决定执行器能否在冻结范围内实现，二者不得互相推导。
