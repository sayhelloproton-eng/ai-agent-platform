# ARC-005 单一真源与知识投影架构

## 1. 问题定义

当同一项目同时使用 Git、飞书、Wiki、聊天历史和 Agent Memory 时，最容易犯的错误是把“能够保存内容”理解为“能够定义事实”。

多个系统都能存储文档，但正式知识必须回答：

- 哪个版本具有最终解释权；
- 谁可以修改；
- 修改经过什么 Review；
- 冲突如何处理；
- 下游内容能否重新生成；
- 新 Agent 从哪里恢复项目。

如果两个系统都能独立修改正式事实，系统就不是双存储，而是双权威。

## 2. 核心理论：Authority 与 Presentation 分离

知识系统至少分成两类模型。

### 2.1 Authority Model

负责：

- 正式事实；
- Review；
- 版本；
- Diff；
- 回滚；
- 审计；
- 与代码、Schema、测试的一致性。

在本项目中是 Git。

### 2.2 Presentation Model

负责：

- 阅读；
- 导航；
- 搜索；
- 协作展示；
- 面向特定平台的格式。

在本项目中是飞书。

两者关系：

```text
Authority Model
      |
      | deterministic build
      v
Presentation Model
```

Presentation 可以删除后重建；Authority 不依赖 Presentation 才能恢复。

## 3. 市面方案对比

### 3.1 Backstage TechDocs：单向 Docs-as-Code

Backstage TechDocs 从代码托管平台获取 Markdown，经过 Prepare、Generate 和 Publish 生成阅读站点。

```text
Git Source
   |
   v
Prepare
   |
   v
Generate
   |
   v
Publish
   |
   v
Reader
```

优点：

- 文档与代码共同 Review；
- 发布结果可重建；
- 适合工程团队；
- 发布层不拥有原始事实。

限制：

- 非工程角色直接编辑门槛较高；
- 需要构建和发布基础设施。

与本项目的相似点：

> `docs/knowledge/**` 类似 Source，Feishu Publisher 类似 Prepare + Publish，
> 飞书类似 Reader。

### 3.2 GitBook Git Sync：双向协作

GitBook Git Sync 支持 GitHub / GitLab 与 GitBook 编辑器双向同步。

优点：

- 开发者在 Git 修改；
- 内容人员在可视化编辑器修改；
- 适合多角色共编文档。

代价：

- 两端都能产生写入；
- 必须处理同步冲突；
- 需要清楚谁能合并；
- 不适合把外部编辑器视为无状态投影。

本项目当前没有独立技术写作团队，也不需要飞书反写，因此不选择该模型。

### 3.3 GitLab Wiki：独立 Git 仓库

GitLab Wiki 本身由独立 Git 仓库支持。

优点：

- Wiki 也有 Git 版本；
- 可克隆和本地编辑；
- 适合与代码相对独立的项目文档。

代价：

- 代码仓库和 Wiki 仓库仍然是两个版本空间；
- 原子提交和跨仓库 Review 更复杂；
- Agent 需要知道去哪里读取哪类事实。

### 3.4 本项目：单一真源 + 受控投影

```text
Git Repository
└── docs/knowledge/**
          |
          v
Validation
          |
          v
Projection Build
          |
          v
Feishu Knowledge Base
```

本项目采用 Backstage TechDocs 更接近的单向模式，同时使用飞书作为阅读界面。

## 4. 知识投影不是同步

### 4.1 同步

同步关注：

- 两端变化；
- 冲突；
- 合并；
- 增量复制；
- 两端身份。

### 4.2 投影

投影关注：

- 唯一输入；
- 确定性转换；
- 目标读模型；
- 可重新生成；
- 验收。

```text
Synchronization
A <----> B

Projection
A ------> B'
```

`B'` 不是第二个正式版本，而是 A 的阅读视图。

## 5. Authoritative Knowledge Pipeline

推荐将知识发布视为编译流水线：

```text
Source Markdown
      |
      v
Source Validation
      |
      v
Projection Manifest
      |
      v
Content Adapter
      |
      v
Target Write
      |
      v
Read-back Verification
```

### 5.1 Source Markdown

必须满足：

- 位于允许的 Knowledge Root；
- 有稳定 Asset ID；
- 有 Canonical Path；
- 已 Review；
- 已进入固定 Commit；
- 不依赖未提交本地资源。

### 5.2 Source Validation

验证：

- Frontmatter；
- H1；
- 链接；
- 资源；
- Asset Index；
- 关系；
- 内容 Profile。

### 5.3 Projection Manifest

每次发布应记录：

- Repository；
- Commit SHA；
- Source Path；
- Asset ID；
- Content Hash；
- Target Path；
- Create / Update / Skip；
- 过滤项；
- 链接转换；
- 验收方法。

### 5.4 Content Adapter

Adapter 只能执行确定性转换，不得临时创作知识。

允许：

- 移除 Frontmatter；
- 改写链接；
- 转换平台支持的结构；
- 跳过禁止资源。

禁止：

- AI 总结；
- 自动解释图片；
- 改写技术结论；
- 静默补全缺失章节；
- 合并两个来源的正文。

### 5.5 Read-back Verification

目标平台返回成功不等于业务成功。

必须回读：

- 标题；
- 关键正文；
- 章节；
- 列表；
- 表格；
- 代码块；
- 链接；
- Revision。

## 6. 架构不变量

### 6.1 单写路径

正式知识只有一个写入入口：

```text
Git Change
→ Review
→ Merge
```

飞书人工编辑不改变正式事实。

### 6.2 投影可重建

飞书页面丢失时，能够从 Git 固定 Commit 重建。

### 6.3 转换确定性

相同 Source Commit 和 Publisher Version 应产生语义相同的目标内容。

### 6.4 目标幂等

同一 Source Path 不应创建多个页面。

### 6.5 外部系统晚绑定

Agent 启动、架构理解和项目恢复不依赖飞书在线。

### 6.6 历史保留

被推翻的决策通过 Superseded ADR 保留，不从历史中删除。

## 7. 投影边界

本项目的正式投影源：

```text
docs/knowledge/**
```

发布：

- `docs/knowledge/README.md`：首页；
- 普通知识 Markdown：正文；
- Git 目录：飞书结构节点。

不发布：

- 目录 README 正文；
- `docs/technical/**`；
- `docs/learning/**`；
- `docs/adr/**`；
- `skills/**`；
- Schema、测试和运行日志；
- 图片、Mermaid 和二进制资源。

这不是因为 Technical 或 ADR 不重要，而是它们属于工程证据层，不适合默认进入人类知识阅读面。

## 8. 什么时候应选择其他方案

### 选择双向 GitBook 类模型

适用于：

- 有独立技术写作团队；
- 可视化编辑是核心入口；
- 有成熟冲突和 Review 流程；
- 接受外部编辑器产生 Git Commit。

### 选择独立 Wiki Git 仓库

适用于：

- 文档生命周期与代码明显独立；
- 需要 Wiki 权限和协作；
- 团队能维护跨仓库关系。

### 选择单向投影

适用于：

- 正式结论必须与代码和 ADR 原子审计；
- Agent 需要稳定启动源；
- 外部知识平台主要承担阅读；
- 团队不希望维护双向冲突。

## 9. 当前项目的决策

采用：

```text
Git Single Source of Truth
+
One-way Deterministic Projection
+
Human-readable Feishu Read Model
```

拒绝：

- Git / Feishu 双源；
- 自动双向同步；
- 逐页面多模式 Mapping；
- 从飞书自动覆盖或合并 Git；
- 未提交工作树正式发布。

## 10. 需要修正的旧合同

现有 ADR-002 和 SOL-002 中仍可能包含：

- Feishu Native 正式知识；
- Capture 晋升；
- 逐页面 Mapping；
- 多种 Mode；
- Drift Merge。

这些内容应根据最终模型收敛为：

```text
Git 正式事实
→ docs/knowledge 发布源
→ Feishu 覆盖式投影
```

保留历史 ADR，但当前规则只能有一套。
