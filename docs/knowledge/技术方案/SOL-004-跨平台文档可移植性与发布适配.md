# SOL-004 跨平台文档可移植性与发布适配

## 1. 问题定义

“平台支持 Markdown”不代表“平台能够无损接收 Git Markdown”。

Markdown 生态存在三层差异：

```text
Core Markdown
Platform Extensions
Target Native Model
```

例如：

- CommonMark 定义基础语法；
- GitHub 增加表格、任务列表和特定链接行为；
- Markdown 文件还可能包含 YAML Frontmatter、Mermaid 和本地图片；
- 飞书最终保存的是文档和 Block，不是原始 Markdown 文件。

因此，跨平台发布的目标不应是字节一致，而应是：

> 在可控损失范围内保持知识语义一致，并能确定性验证。

## 2. 市面方案

### 2.1 CommonMark：定义最小语法基线

CommonMark 解决的是 Markdown 解析歧义，为标题、段落、列表、引用、代码块和链接提供较稳定的共同语义。

它不能保证：

- YAML Frontmatter；
- Mermaid；
- 图片上传；
- 附件；
- 平台内部链接；
- 文档权限；
- 目标 Block 类型。

因此 CommonMark 是基础，不是完整发布协议。

### 2.2 Backstage TechDocs：先生成，再发布

Backstage 不要求阅读端直接理解源 Markdown，而是：

```text
Source
→ Generator
→ Static Output
→ Publisher
```

这说明跨平台发布应存在独立构建层，而不是让目标平台承担所有源格式兼容。

### 2.3 GitBook：通过产品级转换吸收差异

GitBook Git Sync 将 Markdown 与可视化编辑器连接，但双向编辑意味着平台需要维护自己的格式转换和冲突逻辑。

适合多角色共编，不适合无状态单向投影。

### 2.4 飞书 / Lark：导入和 Block API

飞书提供文件导入和文档 Block API。导入入口可以接收 Markdown 等文件，但目标仍会转换为飞书文档对象。

因此需要分别验证：

- 导入支持的文件类型；
- 转换后的 Block；
- 图片和附件上传；
- 链接；
- 不同对象类型；
- 写入后的实际正文。

## 3. Portable Knowledge Profile

为避免每篇文档临时处理，定义项目级 Portable Knowledge Profile。

### 3.1 必须支持

```text
H1-H6
Paragraph
Bold / Italic
Ordered List
Unordered List
Table
Quote
Code Block
External Link
Reviewed Text Diagram
```

### 3.2 Git-only Metadata

以下信息保留在 Git，发布时移除：

```text
YAML Frontmatter
Canonical Path
Asset Status
Evidence Level
Owners
Tags
Relations
```

它们用于治理，不是人类阅读正文。

### 3.3 禁止自动投影

```text
Local Image
Remote Image Proxy
Mermaid
draw.io
Binary Attachment
Embedded HTML
Unknown Macro
```

禁止不等于永远不能表达，而是不能由 Publisher 自动猜测。

信息必须在 Git Review 阶段转成：

- 文字说明；
- 表格；
- 文本图；
- 外部已审阅链接。

## 4. Canonical Content 与 Destination Payload

### 4.1 Canonical Content

Canonical Content 是 Git 中完整、可审计的知识资产。

它可以包含平台不会发布的治理元数据，但不能依赖只有本机才能解释的关键语义。

### 4.2 Destination Payload

Destination Payload 是为目标平台生成的临时结果。

```text
Canonical Markdown
       |
       v
Projection Filter
       |
       v
Destination Payload
```

Payload：

- 不反写 Git；
- 不成为第二真源；
- 可以随时重新生成；
- 必须记录来源 Commit 和 Publisher Version。

## 5. 固定转换顺序

```text
Parse Source
    |
    v
Validate H1 and Asset
    |
    v
Remove Frontmatter
    |
    v
Detect Unsupported Resources
    |
    v
Resolve Document Links
    |
    v
Render Portable Markdown
    |
    v
Write Target
    |
    v
Read Back
```

顺序不可随意变化。

例如，先改写链接再判断资源类型，可能把图片路径错误地变成 GitHub 链接。

## 6. 资源降级策略

### 6.1 图片

Publisher 不负责：

- 上传；
- 下载；
- OCR；
- 解释；
- 重绘；
- 生成 Alt Text。

如果图片包含关键知识，源文档在 Review 前不满足发布条件。

### 6.2 Mermaid

Mermaid 是源代码，不是跨平台通用文档块。

推荐：

```text
Mermaid
→ 保留在 Engineering / Learning Layer

关键知识
→ 在正式 Knowledge 中提供文字和 text diagram
```

### 6.3 表格

飞书可能对列宽和换行归一化。

验收关注：

- 表头；
- 行列数量；
- 单元格语义；

不要求字节和空格完全一致。

### 6.4 代码块

保留语言标签和正文。

文本图统一使用：

```text
```text
...
```
```

每行建议不超过 80 个字符。

## 7. 链接适配矩阵

| 源链接 | 目标行为 |
|---|---|
| 本批正式知识文档 | 飞书内部文档链接 |
| `docs/knowledge/README.md` | 飞书首页 |
| 目录 README | 固定 Commit GitHub URL |
| `docs/technical/**` | 固定 Commit GitHub URL |
| `docs/adr/**` | 固定 Commit GitHub URL |
| 外部 HTTP / HTTPS | 保持原链接 |
| 图片或二进制 | 移除或阻止发布 |
| 目标不存在 | 发布失败 |

禁止使用 Branch URL 作为正式不可变证据，应使用完整 Commit SHA。

## 8. 写入告警和重试策略

### 8.1 错误分类

```text
Source Error
Adapter Error
Transport Error
Target Warning
Read-back Error
```

不同错误不能使用同一重试逻辑。

### 8.2 `partial_success` 处理

当 API 返回部分成功或告警时：

1. 不立即重试；
2. 按幂等键查找目标；
3. 检查 Revision；
4. 回读标题和关键正文；
5. 内容完整则判定业务成功并保存告警；
6. 内容不完整才执行受控修复；
7. 重试前再次确认不会创建重复页面。

### 8.3 重试上限

同一页面只允许一次确定性修复重试。

第二次仍失败时停止整批或标记 Pending，不让 Agent 无限消耗 Token。

## 9. 回读验收

发布成功至少验证：

- 页面存在且目标唯一；
- 标题来自第一个 H1；
- Frontmatter 未进入正文；
- 关键章节存在；
- 文本图和代码块完整；
- 图片与 Mermaid 不存在；
- 内部链接和固定 Commit 链接可解析；
- Revision 已生成；
- 没有相对链接残留。

回读语义一致即可，不要求目标平台序列化结果与源文件字节一致。

## 10. 可移植性测试集

建议为 Publisher 增加 Fixture：

```text
heading.md
lists.md
table.md
quote.md
code.md
text-diagram.md
internal-links.md
external-links.md
frontmatter.md
image-blocked.md
mermaid-blocked.md
missing-h1.md
broken-link.md
```

每次 Publisher 变更必须运行相同测试集。

## 11. 发布门禁

```text
Source Gate
- fixed commit
- clean source
- valid asset

Content Gate
- portable profile
- no unsupported semantic dependency

Target Gate
- correct knowledge base
- idempotent target
- no permission changes

Acceptance Gate
- read-back complete
- no duplicate
- warning recorded
```

## 12. 当前项目方案

采用：

```text
Text-first Canonical Knowledge
+
Deterministic Projection Filter
+
Target-specific Link Adapter
+
Read-back Acceptance
```

不采用：

- 目标平台无损镜像假设；
- AI 自动解释资源；
- 图片代理；
- Mermaid 自动画板；
- API 返回码直接等同于成功；
- 未提交工作树正式发布。
