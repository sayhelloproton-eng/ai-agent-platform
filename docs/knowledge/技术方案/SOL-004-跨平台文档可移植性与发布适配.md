# SOL-004 跨平台文档可移植性与发布适配

## 一句话结论

“飞书支持导入 Markdown”不等于“Git Markdown 可以原样搬进飞书”。

本项目最终采用：

```text
Git Markdown
     |
     | 解析、过滤、改写
     v
可移植内容
     |
     | 写入并回读
     v
飞书文档
```

发布目标不是格式完全一样，而是让核心知识在人和 Agent 看来保持同一个意思。

## 1. 为什么会有这篇文档

项目最初把飞书发布理解成“把 Markdown 文件同步过去”。

第一次真实发布后发现：

- 页面能够创建；
- 普通正文基本可用；
- 但 YAML Frontmatter 进入了正文；
- 图片没有按预期展示；
- Mermaid 和画板不稳定；
- 相对链接离开 Git 后失效；
- 写入接口返回 `partial_success / 1011`，但页面实际已经生成；
- 如果只按返回码重试，可能创建重复内容。

这说明问题不是某个 API 参数没写对，而是源格式和目标平台的数据模型不同。

## 2. Git Markdown 和飞书文档到底差在哪里

### 2.1 Git 保存的是文件

Git 关心：

- 文件路径；
- 文本内容；
- Commit；
- Diff；
- 相对链接；
- 图片文件；
- Mermaid 源码；
- YAML Frontmatter。

### 2.2 飞书保存的是云文档对象

飞书导入 Markdown 后，会将源文件转换成在线文档。

飞书真正保存的是：

- 文档对象；
- Block；
- 云空间节点；
- 图片和附件对象；
- 飞书内部链接；
- Revision；
- 权限。

因此，飞书不是 Git Markdown 的另一个渲染器，而是另一个内容系统。

## 3. 项目中实际踩到的格式问题

### 3.1 Frontmatter 被当成正文

Git 文档使用：

```yaml
---
asset_id: ARC-001
status: active
canonical_path: ...
---
```

这些字段用于机器治理，不是给飞书读者看的。

直接发布后，飞书把它显示成正文，读者打开页面先看到一段元数据。

最终处理：

- 发布前识别文件开头的 YAML Frontmatter；
- 用于发布选择和校验；
- 不写入飞书正文。

### 3.2 图片不是一个 Markdown 语法问题

Git 中：

```text
Markdown 图片引用：`./assets/architecture.png`
```

这只是对仓库文件的引用。

飞书要显示图片，通常需要：

- 上传图片；
- 获得飞书素材或文件 Token；
- 创建对应 Block；
- 处理权限和失败重试。

把路径改成 GitHub Raw URL 也不能保证飞书导入器会自动生成图片 Block。

本项目第一阶段没有必要为了图片引入一套媒体上传系统，因此选择暂不发布图片。

### 3.3 Mermaid 不是通用 Markdown

Mermaid 是特定渲染器支持的扩展代码块。

GitHub、编辑器、静态网站和飞书对 Mermaid 的支持能力不同。即使能创建画板或代码块，也不代表能得到稳定、可回读、可重建的架构图。

最终处理：

- `docs/knowledge/**` 不使用 Mermaid 作为正式知识的唯一表达；
- 核心结构改成 `text` 代码块；
- 文本图宽度控制在约 80 字符以内；
- 保证 Git、飞书和 Agent 都能直接理解。

### 3.4 相对链接离开 Git 后失效

GitHub 会根据当前文件和分支解析相对链接。

飞书没有同样的仓库路径语义。

最终建立链接转换规则：

- 目标也是正式发布资产：转换成飞书内部页面链接；
- 目标不发布飞书：转换成包含固定 Commit SHA 的 GitHub 永久链接；
- 不允许残留相对链接；
- 不使用会随 `main` 变化的普通链接作为证据链接。

最终发布结果：

- 飞书内部链接转换：18；
- GitHub 固定 Commit 链接：6；
- 相对链接残留：0。

### 3.5 `partial_success` 不能直接当作失败

最终发布时写入 API 返回：

```text
partial_success / 1011
```

但回读发现：

- 所有页面都存在；
- Revision 已生成；
- 标题正常；
- 正文完整；
- Frontmatter、图片和 Mermaid 过滤正确。

如果只看返回码直接重试，反而可能制造重复页面。

最终处理：

```text
写入响应
    |
    v
查找目标页面
    |
    v
检查 Revision
    |
    v
回读标题和正文
    |
    v
决定成功、失败或受控重试
```

## 4. 市面上的成熟做法

### 4.1 CommonMark：只定义基础语法，不承诺平台扩展

CommonMark 规范主要解决标题、段落、列表、引用、代码块、链接等基础 Markdown
解析一致性。

它没有替项目解决：

- YAML Frontmatter；
- Mermaid；
- 文件上传；
- 权限；
- 平台内部链接；
- 飞书 Block；
- 导入后的内容损失。

因此“符合 Markdown”只能作为最低语法基线，不能作为跨平台兼容承诺。

### 4.2 Backstage TechDocs：先生成，再发布

Backstage TechDocs 不要求阅读端原样理解源 Markdown，而是经过：

```text
Prepare
→ Generate
→ Publish
```

它把格式适配放进独立构建过程，而不是把责任交给最终阅读端。

本项目的 Projection Filter 本质上是同一个思路，只是目标平台从静态网站换成飞书。

### 4.3 GitBook：双向产品需要承担双向转换成本

GitBook 能让 Git 和可视化编辑器双向同步，是因为产品本身承担了：

- Markdown 导入；
- 编辑器格式导出；
- 提交；
- 权限；
- 失败恢复；
- 冲突处理。

这说明跨平台兼容不是简单调用一个导入接口，而是一项独立产品能力。

当前项目不需要双向编辑，因此不复制这套复杂度。

### 4.4 飞书官方导入：Markdown 会被转换成云文档

飞书官方导入流程包括：

1. 上传本地文件；
2. 创建导入任务；
3. 查询导入结果；
4. 将 Markdown 转成在线文档。

这个过程已经明确说明：源文件会转换成另一个对象模型。

因此发布后必须验证转换结果，而不能只验证上传成功。

## 5. 本项目形成的“可移植内容规范”

第一阶段允许进入飞书的内容：

- H1–H4 标题；
- 普通段落；
- 有序和无序列表；
- 表格；
- 引用；
- 普通代码块；
- `text` 架构图；
- 普通外部链接；
- 已转换的飞书内部链接。

第一阶段不进入飞书：

- YAML Frontmatter；
- Markdown 图片；
- PNG、JPG、SVG；
- Mermaid；
- `.mmd`；
- draw.io；
- 二进制附件；
- Git 专属相对链接；
- 目录 README；
- 发布审计报告。

这不是说这些内容永远不能支持，而是：

> 在没有完整媒体适配、测试和回读能力前，不把不稳定能力写进正式发布合同。

## 6. 标准发布流程

```text
1. 扫描 docs/knowledge/**
2. 区分首页、正式资产和目录 README
3. 解析 Frontmatter
4. 取第一个 H1 作为页面标题
5. 过滤不发布内容
6. 转换内部链接
7. 校验无相对链接、图片和 Mermaid
8. 基于固定 Commit 生成 GitHub 备用链接
9. Preview
10. 写入飞书
11. 回读标题、正文和 Revision
12. 输出发布统计
```

正式发布顺序应为：

```text
Validate
→ Commit
→ Push
→ Publish
→ Read-back
```

不从未提交工作树执行正式发布，因为飞书页面需要能追溯到确定的 Git 版本。

## 7. 如何判断发布成功

不能只看“API 没报错”。

成功至少包括：

- 应发布页面数量正确；
- 页面标题正确；
- 正文非空；
- Frontmatter 未进入正文；
- 图片和 Mermaid 没有残留；
- 文本架构图完整；
- 内部链接可用；
- 相对链接为 0；
- 页面 Revision 存在；
- 回读内容与转换后预期一致。

第一阶段正式发布最终达到：

- 内容页面 17/17；
- 失败 0；
- Frontmatter 过滤 16；
- 全部 17 页回读通过；
- 图片排除、Mermaid 排除均通过；
- 总节点 29。

## 8. 从这次实践抽象出的理论

### 8.1 跨平台发布追求语义一致，不追求字节一致

源文件和目标文档不可能完全相同。

真正需要保持的是：

- 标题；
- 章节关系；
- 核心正文；
- 代码；
- 关键链接；
- 来源和版本。

### 8.2 每一种非基础能力都必须有适配器

图片、图表、附件、数据库、表格和内部链接都不是“顺便支持”。

每增加一种能力，都需要：

- 转换规则；
- 失败处理；
- 测试样例；
- 回读校验；
- 降级方案。

### 8.3 降级不是失败，是明确的产品选择

第一阶段把 Mermaid 和图片降级成文本图，是为了优先保证：

- 人能读；
- Agent 能理解；
- Git 能审计；
- 飞书能稳定显示；
- 内容能长期维护。

### 8.4 写入成功和内容正确是两件事

外部系统 API 返回成功，只能证明请求被接受。

知识发布必须以内容回读作为最终验收。

## 9. 后续演进

未来确实需要图片时，应单独建设 Media Adapter：

```text
Git Media
   |
   v
Upload
   |
   v
Feishu File Token
   |
   v
Image Block
   |
   v
Read-back
```

并增加：

- 图片 Hash；
- 去重；
- 权限；
- 替换策略；
- Fixture；
- 回读验证。

在这套能力完成前，继续保持 Text-first。
